# Alembic migrations — single additive chain

**Authority:** `design/DATA-MODEL.md` §1.1 (naming conventions) and §21.1 (revision map);
`design/parallel-plan.json` (Δ-PAR §6 migration protocol); `design/FEATURE-SET-FRAMEWORK.md` §6.

One Alembic environment, **one linear chain**. FS-00 owns the platform revisions `0001`–`0003`;
every other feature set owns pre-allocated revisions that the integrator merges in chain order. This
directory contains the environment/template only — **no domain migrations** belong to S0.

## Rules enforced by the chain guard

`python -m app.migrations.chain_guard` (no database required):

- revision ids match `NNNN_slug` with a **4-digit prefix** (e.g. `0004_item_master`);
- **one base**, **one head**, no branches/merges (`down_revision` must be a single string or `None`);
- each revision points at its **immediate predecessor**; prefixes are **contiguous from 0001**, unique;
- filename stem equals the revision id (`0004_item_master.py`);
- the manifest's migration list is valid and the on-disk chain is a **prefix** of it
  (`--require-complete` after the final merge demands equality).

CI/gate commands:

```bash
python -m app.migrations.chain_guard                       # chain only (manifest auto-detected)
python -m app.migrations.chain_guard --json                # machine-readable
python -m app.migrations.chain_guard --require-complete    # after merge train completes
```

## Creating a revision (builders)

```bash
# Use the number pre-allocated in design/DATA-MODEL.md §21.1 — never a random id.
alembic -c alembic.ini revision --rev-id 0004_item_master -m "item master core"

# Apply / verify locally (needs DATABASE_URL)
alembic -c alembic.ini upgrade head
alembic -c alembic.ini downgrade -1 && alembic -c alembic.ini upgrade head
```

`env.py` refuses autogenerated random revision ids and refuses to generate when the chain has
multiple heads; pass `--rev-id <NNNN_slug>` explicitly. Plain `alembic revision` does not load
`env.py` (so it needs no database, but also cannot enforce the id) — use
`scripts/new_migration.sh 0004_item_master -m "item master core"`, which validates the 4-digit id
before creating the file and runs the chain guard afterwards. The chain guard/CI rejects any random
or non-contiguous revision id.

## Environment / URL resolution

`app/migrations/env.py` is async (SQLAlchemy 2.0 + `asyncpg`) and resolves the URL **without storing
secrets in Alembic config**:

1. `ALEMBIC_DATABASE_URL` (migration-only override, e.g. shadow DB in CI),
2. `DATABASE_URL` (`postgresql://` is upgraded to `postgresql+asyncpg://`),
3. `app.core.config.get_settings().database_url`,
4. `alembic.ini` `sqlalchemy.url` (empty by default).

Offline SQL rendering works without a DB: `alembic -c alembic.ini upgrade head --sql` (requires a URL).

## Autogenerate policy (no drift)

- `target_metadata` comes from `app/migrations/base.py` (`discover_metadata()`), which merges metadata
  exported by `app.db.*` / `app.core.db.*` modules as they land; S0 starts with an empty schema.
- `compare_type=True` and `compare_server_default=True` are set in `env.py` **and** `alembic.ini`.
- Autogenerate is a convenience only: reviewed, hand-edited revision files are authoritative. CI runs
  `alembic check` against the migrated DB (no pending ops) where a database is available; the
  database-free `chain_guard` runs everywhere.
- Naming conventions (DATA-MODEL §1.1) live in `app/migrations/base.py`: `pk_`, `uq_`, `fk_`, `ck_`,
  `ix_`. Raw trigger names (`trg_<table>_<action>`) are DDL in the owning revision.

## Downgrades

Every revision ships a working `downgrade()`; the migration test runs `upgrade → downgrade → upgrade`
on empty and seeded databases. **No down-migrations in prod** — rollback is flag-off + forward-fix
(PLAN §7.3), migrations are additive/N-1 compatible.

## S0 empty baseline

`versions/` is intentionally empty in S0. The chain guard treats this as valid (with a warning) so the
scaffold gate can pass before FS-00 merges `0001`–`0003`.
