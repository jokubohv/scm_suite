# Feature-Set Framework — Build, Check, Deploy Contract

Status: **Lead-authored conventions. Binding for all plan artifacts.**
Version: 1.0 (2026-10-21)

This document defines *how* the inventory/SCM backend is decomposed, checked and deployed.
It is deliberately stack- and domain-agnostic at the contract level, but pins a reference stack
and repository layout so the plan is directly executable.

---

## 1. Scope rule: core backend logic first

**Phase 1 (this plan, detailed): all core backend logic.**
In scope:

- Domain model, business rules, invariants, state machines
- Persistence (PostgreSQL schema + migrations), transactions, locking, idempotency
- Service layer / use cases
- REST APIs (OpenAPI 3.1) + domain events (JSON Schema) + async jobs
- AuthN/AuthZ (RBAC), tenant isolation, audit trail
- Recalculation engines, scheduled jobs, reconciliation checks
- Backend test suites, contract tests, migration tests, dependency gates

Out of scope for Phase 1 (envelope only, not detailed):

- Any end-user UI (web admin, transaction screens, dashboards)
- All mobile apps and mobile-device workflows (and **SCM Mobile as a whole is permanently excluded**)
- Analytics/BI workbooks and Item 360 dashboard
- External integrations (EDI, carrier, accounting export), SuiteApp packaging/distribution
- Marketplace features, sandbox/customization tooling beyond what backend needs

"Backend only" does **not** mean "no infrastructure": a minimal runtime (DB, worker, object storage
if needed, reverse proxy) is part of deployability and is included in `FS-00`.

## 2. Definitions

| Term | Meaning |
|---|---|
| **Feature set (FS)** | The unit of planning, checking and deployment. One FS delivers a coherent backend capability, one or more modules/migrations, and a versioned *provided contract*. It can be deployed without any later FS. |
| **Provided contract** | What dependants may rely on: versioned HTTP endpoints, domain events, read-model tables/views, job names, and reference data seeds. Semver-major for breaking change. |
| **Hard dependency** | FS cannot function or pass its exit gate unless the dependency FS is deployed at a contract version inside the declared range. Recorded in the manifest; checked statically and at deploy time. |
| **Soft dependency** | Works without it but gains behavior when present (e.g. quality holds on WMS putaway). Not allowed to hide a functional requirement; use only for optional enrichment. |
| **Entry gate** | Checks run *before* a feature set is deployed to an environment. |
| **Exit gate** | Checks run *after* deploy, before dependants may build/deploy. Passing the exit gate flips the set to `deployed` for that environment. |
| **Wave** | Ordered batch of feature sets released together within a phase. A wave deploys only when every dependency outside the wave is already deployed+verified. |
| **Deployment state** | Per-environment record (`deployment-state.<env>.json`) of FS → contract versions actually deployed and gate results. Generated by the check tool, never hand-edited. |

## 3. Reference stack (fixed for Phase 1)

Rationale: single language for domain + jobs + tooling; strong transactional DB (the inventory
ledger is the hard problem); additive-migration-friendly; Docker Compose deployable on one host.

| Layer | Choice |
|---|---|
| Language/runtime | Python 3.12 |
| API | FastAPI, Pydantic v2, OpenAPI 3.1 |
| DB | PostgreSQL 16 (SQLAlchemy 2.0, Alembic migrations) |
| Transactions/locking | DB transactions; `SELECT … FOR UPDATE`, advisory locks for posting sequences; no cross-service sagas inside Phase 1 |
| Async jobs | Redis 7 + RQ (or Celery) worker process; transactional outbox for domain events |
| Events | Postgres outbox table → relay → Redis Streams; JSON Schema per `event_type@version` |
| Auth | **Dex OIDC identity broker** (per-tenant/company SSO connections to SAML/OIDC/LDAP-AD IdPs) + platform-issued JWT access/refresh sessions + API keys; RBAC scopes; Argon2id local-password fallback; `tenant_id` on every tenant-owned row (`DEX-SSO-ADDENDUM.md`) |
| Tests | pytest, pytest-asyncio; testcontainers-postgres; schemathesis (OpenAPI); jsonschema (events) |
| Deploy | Docker Compose: `api`, `worker`, `postgres`, `redis`, `outbox-relay` + **Dex units** (one isolated Dex issuer per active SSO connection in production; shared Dex for dev/test) and Dex Postgres storage; one `docker compose up` per env; nginx/Caddy TLS terminator optional |
| Observability | structured JSON logs, OpenTelemetry traces/metrics, `/healthz` + `/readyz` + `/internal/deps` endpoints |
| CI | lint (ruff/mypy), unit, contract, migration up/down, manifest validate, integration on compose |

Numbers: quantities `NUMERIC(38,12)`, money `NUMERIC(38,12)`, all timestamps UTC, all quantities
converted to an item's base UoM before posting; rounding rules explicit and tested.

Monorepo layout (implementation root `inventory-platform/app/`):

```
app/
  api/                 # FastAPI app, routers, deps, error handling
  core/                # platform: tenant, authz, audit, outbox, jobs, config
  modules/             # one package per bounded context, each FS adds a module
    item_master/
    pricing/
    inventory_ledger/
    costing/
    traceability/
    counts/
    replenishment/
    procurement/
    wms/
    manufacturing/
    quality/
    consigned/
  contracts/           # OpenAPI fragments, JSON Schemas, contract tests
  migrations/          # Alembic revisions (one chain, additive)
  tests/               # unit + integration + invariant suites
  seed/                # reference data per FS (UoM, statuses, transaction types)
tools/
  feature_sets.py      # manifest validate / order / check-env / gate runner
  deploy_set.sh        # one-command deploy of one FS to one env (calls the checks)
  deployment-state.<env>.json
```

Boundaries: modules may import `core` and their declared dependencies' **contract clients only**
(API client or read-model view), never another module's ORM models directly. One shared database;
schema ownership stays per module.

## 4. Feature-set manifest (single source of truth)

File: `inventory-platform/design/feature-sets.json`. Validated by `tools/feature_sets.py`.

```jsonc
{
  "schema_version": "1.0",
  "plan_version": "1.0.0",
  "feature_sets": [
    {
      "id": "FS-03",
      "name": "Inventory Ledger Core",
      "phase": 1,
      "wave": "1B",
      "backend_only": true,
      "summary": "Double-entry-style inventory transactions, running balances, commitments, idempotent posting.",
      "source_docs": ["https://docs.oracle.com/..."],
      "depends_on": [
        {"id": "FS-00", "contract": "platform.core", "version": ">=1.0.0 <2.0.0"},
        {"id": "FS-01", "contract": "item.master", "version": ">=1.0.0 <2.0.0"}
      ],
      "provides": [
        {"contract": "inventory.ledger", "version": "1.0.0"}
      ],
      "modules": ["modules/inventory_ledger"],
      "migrations": ["alembic:0003_inventory_ledger"],
      "flags": ["inventory.ledger.enabled"],
      "entry_checks": [
        "tools/feature_sets.py check-env --set FS-03 --env $ENV",
        "docker compose run --rm api pytest tests/contracts/test_fs00_fs01_contract.py -q"
      ],
      "exit_checks": [
        "pytest tests/integration/inventory_ledger -q",
        "pytest tests/invariants/test_qty_conservation.py -q",
        "tools/feature_sets.py record --set FS-03 --env $ENV --status verified"
      ],
      "acceptance": ["…Given/When/Then statements…"],
      "rollback": "flag off; forward-fix; migrations are additive and backward-compatible with N-1"
    }
  ]
}
```

Rules enforced by the validator:

1. IDs `FS-\d{2}`, unique; `phase` integer ≥ 0; `wave` non-empty.
2. Every `depends_on.id` exists; no self-reference.
3. **No cycles**; graph is a DAG.
4. Phase is monotonic: a set may depend only on sets with `phase <= own phase`;
   within a phase, wave order must follow the manifest's declared wave sequence.
5. Semantic version ranges parse and are satisfiable.
6. `provides` contract names unique; no two sets provide the same contract+version.
7. Every set has ≥1 entry check, ≥1 exit check, ≥1 acceptance item, a rollback statement,
   and a `source_docs` link (traceability to the official SCM documentation).
8. All `backend_only` must be `true` in Phase 1; UI/mobile/analytics sets are not enumerated
   as deployable backend feature sets.

## 5. Dependency checking protocol ("sets check each other")

Four layers; all must be automatable and scripted.

**L0 — Static plan gate (CI, every commit):**
`python tools/feature_sets.py validate` → JSON-schema + DAG + monotonic phase + contract
satisfiability. Also emits `order --phase 1` topological order. Fails non-zero.

**L1 — Build contract tests (per FS):**
Each FS commits *provider* contract tests (its `provides` surface behaves) and *consumer*
contract tests (it can rely on each dependency's declared contract, run against dependency
mocks or the real compose stack). OpenAPI diff and event-schema compatibility are checked
against the last deployed version: additive-only within a major version.

**L2 — Entry gate (immediately before deploy):**
`python tools/feature_sets.py check-env --set FS-xx --env staging`
reads `deployment-state.<env>.json` (and, in a live env, `/internal/deps` on the deployed API)
and asserts, for every dependency: deployed, version inside range, migrations at expected head,
exit gate `verified`, required seeds present, dependency health `ok`. Any miss → deploy aborts.

**L3 — Exit gate (immediately after deploy):**
Run the set's exit checks: migrations applied, smoke tests through the public API, contract tests
for the provided contract, domain invariant tests (e.g. `Σ ledger lines == balance` per
item/location/status; no orphan FK; outbox drained), plus performance smoke. On pass:
`record --status verified`. Dependants' L2 gates now accept it. On fail: rollback path.

**Cross-set invariant checks (scheduled):** a `reconcile` job recomputes balances/costs from the
transaction ledger and compares to read models; drift is a P1 incident. This is the runtime
"sets check each other" proof, not just a deploy-time formality.

**Change control:** modifying a provided contract requires a manifest version bump, a consumer
impact list (`tools/feature_sets.py who-depends-on --contract X`), and coordinated rollout
(expand → migrate consumers → contract). The validator rejects contract changes that break
declared ranges without a version bump.

## 6. Deployment protocol

Per environment: `dev` → `staging` → `prod`. One FS at a time, wave-by-wave.

1. `make plan` / `feature_sets.py order --phase 1` → deployment order.
2. Pre-flight: L0 validate; confirm git tag `fs-XX-vX.Y.Z`; confirm entry gate L2 for the target env.
3. Deploy: build image → run additive Alembic migrations (shadow DB first for destructive-looking
   ops) → start/refresh `api` + `worker` → run exit gate L3 → `record --status verified`.
4. Enable flag (`inventory.<domain>.enabled`) per tenant; verify golden smoke transaction;
   monitor error rate/latency for 30 min.
5. Update `PLAN.md` status table + `deployment-state.<env>.json` (generated).
6. Rollback: disable flag (fast, no data loss), redeploy previous image; never down-migrate in
   prod — migrations are expand/contract and remain N-1 compatible. A failed exit gate blocks
   every dependent FS automatically.

Waves (finalized by the architecture in `FEATURE-SETS.md` §3; supersedes the earlier expected shape):
`0A platform` → `0B item master + pricing` → `0C storage/status + ledger + costing` → `1A numbered
inventory + counts` → `1B procurement` → `1C manufacturing` → `1D replenishment/planning` → `1E WMS`
→ `1F quality + consigned + extensions` → `2 reporting read models`. Dependency direction forced
manufacturing before replenishment and WMS; the actual wave table and per-wave gates are authoritative
in `design/feature-sets.json` + `design/FEATURE-SETS.md`, not this summary.

## 7. Definition of Done (per feature set, Phase 1 backend)

- [ ] Module code + migrations merged; module boundary respected (no cross-module ORM imports)
- [ ] OpenAPI paths + JSON Schemas for events/jobs published under `contracts/`
- [ ] Unit tests ≥ target coverage for business rules; invariant tests for domain invariants
- [ ] Provider + consumer contract tests green in CI
- [ ] Migration up/down tested on empty + seeded DB; additive/backward-compatible with N-1
- [ ] Entry/exit checks added to manifest and runnable via `tools/feature_sets.py`
- [ ] Feature flag wired, default off; tenant isolation test added
- [ ] Audit events emitted for every state change; RBAC scopes declared
- [ ] Performance smoke within budget on compose stack; no N+1 on hot paths
- [ ] `docs/feature-sets/FS-xx.md` runbook: deploy, verify, rollback, dashboards/alerts
- [ ] `PLAN.md` status table updated; verification report references evidence

## 8. Execution model (who builds what — parallel build, wave-ordered deploy)

Binding execution amendment: [`design/PARALLEL-IMPLEMENTATION-ADDENDUM.md`](PARALLEL-IMPLEMENTATION-ADDENDUM.md)
(Δ-PAR); machine-readable task graph: [`design/parallel-plan.json`](parallel-plan.json); validator:
`python tools/check_parallel_plan.py` (add `--s0` for the execution-ready check).

- **S0 scaffold first (precondition).** Seven scaffold cards (repo/toolchain/CI, local stack + Dex dev,
  Alembic base, contract-first infrastructure with **contract skeletons for all 16 feature sets**, test
  harness, gates/scripts, seed/reference bootstrap) must pass **S0-GATE** before FS-00 starts.
- **Parallel build:** feature sets may be built concurrently when their write scopes are disjoint and the
  dependency contracts are frozen (contract-first, freeze points C0–C5). Up to **8 concurrent FS builders**
  in the wide build wave (plus integrator, verifier and e2e); DSH's 8-durable-teammate cap means use
  `workflow` fan-out or batching for extra short-lived work.
- **Wave-ordered deploy:** deployment remains exactly as `feature-sets.json` defines
  (`0A → 0B → 0C → 1A … 1F → 2`), one set at a time (parallel only where the wave plan already says so).
  Build completion never implies deployment; a set is **done** only after L2 entry + L3 exit evidence.
- **Per-card workflow:** each card is a shared task with its write scopes (module dirs, per-FS contract
  fragments, assigned migration revisions), built in a dedicated worktree/branch `feat/PAR-xx`; the
  integrator owns shared files (`app/api/registry.py`, OpenAPI/event aggregation, migrations chain,
  conftest, seed, compose/scripts) and the merge train; independent verifier checks L1–L3 evidence.
- **Contract changes** after a freeze are additive within a major version with contract-owner review;
  breaking changes require a version bump + consumer impact list + re-freeze.
- **Plan changes** (new FS, new dependency) update the manifest/parallel plan and re-run `validate` +
  `check_parallel_plan.py`; no ad-hoc dependency edges.
- **Environment/resource guard:** per-card isolated compose/DB namespace; disk/container headroom is a gate;
  full protocol in the Δ-PAR addendum §§5–7.

## 9. Non-functional targets (Phase 1)

| Concern | Target |
|---|---|
| Ledger posting latency | p95 ≤ 300 ms at 20 tx/s sustained on compose stack |
| Balance read | p95 ≤ 150 ms for item/location/status queries |
| Throughput | ≥ 200k ledger lines/hour batch import |
| Consistency | 0 tolerance for qty/valuation drift; nightly reconcile must be exact |
| Durability | outbox at-least-once + idempotency keys → effectively once |
| Availability | single-node compose for dev/staging; prod target 99.9% with managed Postgres |
| Security | tenant isolation tests on every endpoint; audit trail immutable (append-only) |
| Data retention | ledger append-only; reversals via compensating transactions only |

---

## 10. Change control of this framework

Framework changes are Lead-approved and versioned. Any change must state which feature sets are
affected and re-run the plan validator. Feature-set definitions may not weaken dependency ranges
to make a deployment pass.
