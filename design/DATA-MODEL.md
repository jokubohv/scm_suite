# DATA MODEL — Phase-1 Core Backend (Canonical Schema Specification)

**Status:** design baseline for review · **Version:** 1.0 · **Date:** 2026-10-21
**Owner:** architect-core · **Companion:** `design/ARCHITECTURE.md` (posting/costing/NFR semantics — this document does not repeat them, it references § numbers)
**Binding inputs:** `design/FEATURE-SET-FRAMEWORK.md` (stack §3, DoD §7), `inventory-platform/PLAN.md` §12 (boundaries), research catalogs `iri-*` / `mpw-*` (traceability via the source key at the end).
**Scope:** PostgreSQL 16 logical schema for **all Phase-1 backend contexts**. No UI, mobile, analytics or integration tables. `FS-xx` = feature-set slot for sequencing/ownership (final ids are the feature-set architect's; dependency direction is fixed here). `EXT` = extension beyond documented NetSuite behaviour; `ASSUMPTION` = design choice requiring review.

## 1. Schema conventions (binding for every table)

### 1.1 Naming, schemas, types

| Rule | Convention |
|---|---|
| Schemas | One schema per bounded context, matching `ARCHITECTURE.md` §1.4: `platform`, `item_master`, `pricing`, `traceability`, `inventory_ledger`, `costing`, `counts`, `procurement`, `wms`, `manufacturing`, `replenishment`, `quality`, `consigned`, `extensions`, `reporting` (views only). Alembic owns one chain; revision names are prefixed by schema (`0042_ledger_commitment_guards`). |
| Tables | `snake_case`, **singular**, no prefixes inside a schema (`inventory_ledger.inventory_transaction`, `procurement.purchase_order`). Join tables are `<owner>_<member>` (`item_category_member`). |
| Columns | `snake_case`; FK column `<entity>_id` (`item_id`); booleans `is_*`/`has_*`; dates `*_date` (`DATE`), timestamps `*_at` (`TIMESTAMPTZ`); money `*_base`/`*_txn`; quantities `qty_*`. |
| Constraint names | `pk_<table>`, `uq_<table>_<cols>`, `fk_<table>_<ref>`, `ck_<table>_<rule>`, `ix_<table>_<cols>`, `trg_<table>_<action>`. |
| Closed enums | `TEXT` + `CHECK (col IN (…))`, with the value list generated from Python `Enum`s at migration time (no PostgreSQL `ENUM` types: additive values would need type migrations). A `ck_*` name states the domain. |
| Open lookups | Lookup tables with `code`, `name`, `is_system`, `sort_order`, `is_active` (e.g. `item_type_definition`, `inventory_status`, `uom`, `inventory_reason_code`, `cost_category`). Seeded per tenant or shared system rows (`tenant_id IS NULL` for global reference data, per §1.2). |
| Extensible fields | `custom_field_def` + `custom_field_value` (EAV with typed value columns and validation); used only where the docs describe customisability (item/serial/lot fields [iri-098, catalog "custom fields"]); no per-tenant DDL. |
| JSON | `JSONB` only for: custom-field definitions/values, event payloads, audit diffs, document snapshots, import raw rows, strategy/rule criteria. Never for quantities, money, keys or anything reconciled. |
| Comments | Every table and every non-obvious column has `COMMENT ON` text = purpose (migration lint requires it for tables). |

### 1.2 Standard columns and keys (apply unless explicitly excluded)

| Column | Type | Rule |
|---|---|---|
| `id` | `UUID` PK | **UUIDv7** generated by the application (time-ordered, non-guessable). Internal-only identity; never a business key. |
| `tenant_id` | `UUID NOT NULL` | Present on **every** tenant-owned row. Global reference rows (`currency` catalogue, `permission_scope`, global `uom_type/uom` seeds) may use a reserved `SYSTEM_TENANT_ID`. |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | set by DB default; immutable |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | maintained by trigger `trg_<table>_touch`; never set by clients |
| `created_by`, `updated_by` | `UUID NULL` | `app_user.id` or service principal id; `NULL` only for migrations/seeds |
| `version` | `INTEGER NOT NULL DEFAULT 1` | optimistic locking; incremented by trigger on every `UPDATE`; API `If-Match` uses it |
| `inactive_at`, `inactive_reason` | `TIMESTAMPTZ`, `TEXT` | master data only (soft inactivation, §1.5) |

Every table additionally has `UNIQUE (tenant_id, id)`. This redundant unique key enables **composite FKs** `(tenant_id, x_id) → (tenant_id, id)` everywhere, so a row can never reference a row of another tenant at the database level (defence in depth behind RLS).

**Global-scope exception (EXT, Δ-MT):** `platform.user_identity` is the only table without `tenant_id`: it is the auth-only global identity table (addendum `MULTI-TENANT-USERS-ADDENDUM.md` §2.1), accessed exclusively by the auth service role, never RLS-tenant-scoped and never reachable through tenant business routes. All other tables follow the tenant rules above.

### 1.4 Precision, time and quantity rules

| Data | Type | Rule |
|---|---|---|
| Quantities | `NUMERIC(38,12)` | all ledger quantities in the item's **base UoM**; UoM-presented quantity stored beside conversion inputs |
| Money / unit cost | `NUMERIC(38,12)` | base-currency value; transaction-currency value stored alongside; rounding per ARCHITECTURE §3.7 |
| Percentages / rates | `NUMERIC(38,12)` | e.g. `exchange_rate`, `yield_percent`, `tax_rate` (if ever needed) |
| Dates | `DATE` | business dates; tenant timezone resolves period membership |
| Timestamps | `TIMESTAMPTZ` | always UTC; client-supplied `posted_at` is rejected |
| Conversion factors | `NUMERIC(38,12)` | > 0; exact base units per unit |
| Quantities on the wire | JSON strings | e.g. `"12.500000000000"` — never JSON floats |

### 1.5 Append-only, immutability and soft-delete policy

| Class | Tables | Policy |
|---|---|---|
| **Append-only** (`†` in the tables below) | `inventory_transaction`, `inventory_transaction_line`, `inventory_transaction_detail`, `cost_ledger_entry`, `cost_layer_consumption`, `audit_event`, `outbox_event`, `serial_number_history`, `inventory_commitment` history rows, `approval_action`, `document_link` (when "link" events) | `INSERT` only. DB trigger raises on `UPDATE/DELETE`; application role is granted `SELECT, INSERT` only on these tables. No soft delete, no exceptions. |
| **Immutable after posting** (`‡`) | all posted documents and their lines/detail rows, posted receipt/bill/PO/WO quantities and statuses, `item_inventory.costing_method`, `item.item_type`, `item_matrix_member` identity, `standard_cost` once effective | trigger `trg_<table>_immutable_posted` checks `OLD.posting_at IS NOT NULL` and rejects changes except whitelisted status/audit columns |
| **Master data** | `item`, `vendor`, `location`, `bin`, `uom`, `inventory_status`, `role`, `app_user`, `price_level`, … | **No hard delete.** `inactive_at`/`inactive_reason`; references remain valid; new transactions reject inactive master data (`422 INACTIVE_REFERENCE`) except where docs allow (e.g. historical reporting). |
| **Documents** | all header/line tables | No hard delete. Drafts never posted may be purged by retention job after N days (config, audited). `status=CANCELLED/VOID` only from unposted states; posted docs immutable; correction = reversal/compensating document. |
| **Operational** | `idempotency_key`, `job_run`, `event_consumer_checkpoint`, `attachment_metadata`, `device_session` | purgeable per retention policy (ARCHITECTURE §5.12) with audit. |

`INV-DM-01`: no `ON DELETE CASCADE` on any ledger/cost/audit reference. Cascades are allowed only for pure child compositions of *draft* documents (e.g. deleting a draft document deletes its draft lines) and must be reviewed in migration.

### 1.6 Index and partitioning conventions

| Rule | Content |
|---|---|
| Tenant first | every secondary index starts with `tenant_id`; every unique business key is `(tenant_id, …)`. |
| FKs | every FK column has a supporting index (required; migration lint checks). |
| Read models | balance/read-model tables use the posting key as their PK (no surrogate id) and covering indexes for the documented query shapes. |
| Partial indexes | for "active" subsets: `WHERE inactive_at IS NULL`, `WHERE status IN ('OPEN','PARTIALLY_…')`, `WHERE published_at IS NULL`. |
| Time scans | `BRIN` on append-only time columns (`transaction_date`, `occurred_at`) in addition to btree for point lookups. |
| Partitioned from day 1 | `inventory_ledger.inventory_transaction_line`, `inventory_ledger.inventory_transaction_detail`, `costing.cost_ledger_entry`, `costing.cost_layer_consumption`, `platform.audit_event`, `platform.outbox_event`, `traceability.serial_number_history`, `replenishment.demand_history`: `PARTITION BY RANGE (<time column>)`, monthly partitions created 3 months ahead by maintenance job; PK `(id, <time column>)`; unique keys include the partition key; no incoming FKs point *to* partitioned tables (children reference them logically with validated constraints at service level, or reference their parents instead). Non-partitioned now but designed for it: `inventory_transaction` (header), `inventory_balance*` (hot rows, must stay unpartitioned). |
| Archive | partitions older than retention-open window move to `archive` schema (same database, read-only role) then export; never dropped without audit approval. |
| Vacuum/bloat | append-only partitions: autovacuum tuned for insert-only; balances: fillfactor 85 + HOT updates. |

### 1.7 Cross-context reference integrity

- Composite FKs are created only in the direction of the declared dependency (ARCHITECTURE §1.4). A lower-layer table never has an FK to a higher-layer table.
- Where a dependency would be circular (e.g. `inventory_transaction_line.lot_id` exists in a later FS slot `FS-06`), the column is created nullable with **no FK** in the earlier FS; the FK + backfill is added by the later FS in an additive migration (`D-15` expand/contract). This is recorded per table in the `Ext-deps` column (`deferred FK`).
- Opaque external ids (`external_ref`) never get FKs (order boundary).
- **Cross-scope exception (EXT, Δ-MT):** `platform.app_user.identity_id → platform.user_identity.id` is the single FK from a tenant-scoped table to the global identity table (documented exception, addendum §2.2/DM-PLAT-12). `platform.user_session.identity_id` is a denormalized logical reference **without FK**, keeping DM-PLAT-12's "only app_user links to identity" rule literal.

**WMS invariants/rules**

| ID | Rule |
|---|---|
| DM-WMS-01 | WMS tasks never change inventory by themselves; completion calls the ledger posting command (receipt/transfer/status change/pick-completion) and stores the resulting `posted_transaction_id`. |
| DM-WMS-02 | A task can be in at most one active assignment; assignment history is audited. Task state machines in §19. |
| DM-WMS-03 | Putaway/pick suggested bin comes from the highest-priority applicable strategy (putaway/pick), then item stock location, then default receiving/pick bin; the resolution is stored on the task for reproducibility [mpw-821/824, mpw-910]. |
| DM-WMS-04 | Blocked bins cannot be assigned/suggested for picking [mpw-827]; expired lots are rejected at pick [mpw-917]. |
| DM-WMS-05 | Picked qty ≤ requested; short/zero picks are recorded (`qty_short`) and re-released lines with backorders are supported [mpw-899, mpw-905]. |
| DM-WMS-06 | Deferred item receipt posting: receiving/posted tasks may complete before `item_receipt` posts; posting is then triggered manually/async and reversal is supported [mpw-856..mpw-859]. |
| DM-WMS-07 | Wave release generates pick tasks exactly once per wave line (idempotent on wave+line); deleting/voiding a wave cancels not-yet-started tasks only [mpw-909]. |
| DM-WMS-08 | Shipment/manifest records are records of truth for shipping data exchanged with a future integration; no carrier call is made in Phase 1. |
| DM-WMS-09 | Warehouse replenishment tasks move stock via T-29 bin transfer; source bin must have stock ≥ qty and destination is the primary/item stocking bin. |
| DM-WMS-10 | Cart/device sessions carry ids only; no PII beyond user id/client info; retention 30 days. |

**Manufacturing invariants/rules**

| ID | Rule |
|---|---|
| DM-MFG-01 | Work orders are **non-posting** until build/completion; status transitions follow §19 and component commitments are raised on release [mpw-078, mpw-064]. |
| DM-MFG-02 | WIP feature is only valid for assemblies with STANDARD or AVERAGE costing; LIFO/FIFO/SPECIFIC assemblies are rejected at configuration and posting time [mpw-152]. |
| DM-MFG-03 | Component requirements snapshot BOM revision + yield/round-up at WO creation/update; changes after release require an audited revision or new WO. Over-issue beyond `work_order_component.over_issue_tolerance` (%) is rejected unless an approval override is recorded. |
| DM-MFG-04 | Build/unbuild quantities must reconcile with component consumption; phantom assemblies explode with no own stock; matrix assemblies resolve to child items [mpw-011, mpw-007]. |
| DM-MFG-05 | Unbuild requires either the original build link or a new unbuild transaction; cost differences post to the configured unbuild variance account [mpw-019, mpw-020]. |
| DM-MFG-06 | WIP completion with backflush consumes remaining required components; average assembly valuation uses last-purchase-price estimate and the variance is surfaced [mpw-151, mpw-152]. |
| DM-MFG-07 | Work order close reconciles all issues/completions and leaves WIP value zero (± posted variance) [mpw-147]; closed WOs cannot build except documented reopen for non-WIP [mpw-084]. |
| DM-MFG-08 | Outsourced operations link a vendor PO; components transfer/consume at the configured outsourced location and vendor charges are absorbed into build cost [mpw-210..mpw-216]. |
| DM-MFG-09 | ECO changes are applied to BOM revisions only after approval; implementation is audited and effective-dated [mpw-403..mpw-415]. |
| DM-MFG-10 | Scheduling runs are snapshots; they never mutate work-order dates unless explicitly applied (`apply` action audited). |
| DM-MFG-11 | Serialized/lot assembly output requires new identities with quantity equal to built qty; consumption identities must exist and match quantity [iri-095, iri-105]. |
| DM-MFG-12 | **Compatibility evaluation (EXT, Δ-CFG):** evaluated deterministically against **all** matching rule sets (assembly/BOM **and** order/configuration/customer/region/channel scopes), ordered by scope specificity (order/configuration > customer > region/channel > assembly/BOM), then priority, then rule code; enforcement configurable (rule > rule-set `enforcement_mode` > tenant `manufacturing.compat.enforcement_default`, default HARD); HARD blocks the guarded action (`409 COMPATIBILITY_VIOLATION`), WARN records an immutable violation, overrides require `manufacturing.compat.override` + reason and are audited. |

| DM-MFG-14 | **Unbuild dispositions & used parts (EXT, Δ-REUSE):** per `assembly_unbuild_component` line, optional `disposition` default RETURN_TO_STOCK; SCRAP returns no stock (value to scrap/variance via FS-05; serial/lot scrapped); HOLD returns non-committable; `is_used` optional and defaults a USED/REFURB non-sellable/non-committable status; valuation `ORIGINAL_COST` default and configurable (tenant/assembly/line) to NRV/manual; serial/lot identity and quantity/value conservation preserved; line overrides require `manufacturing.unbuild.dispose` and are audited. |
