## 1. Objective and source coverage

Deliver backend registries for three documented SuiteApp capabilities without their UI/workbooks/integrations:
(1) warranty terms per item + serial-keyed warranty registrations + claims validated against coverage + append-only
claim actions + repair-order data; (2) customer part number → item mappings (tenant + external customer scoped, with
import data path and resolution for order/invoice callers); (3) the Auto Assign UPC registry — UPC assignment to new
inventory/assembly/matrix items, UPC↔item linkage, retirement without reuse, batch assignment job and monitoring.
All records are data/logic only; nothing here posts inventory (DM-EXT-05) or creates order/finance documents.

## 2. Scope

**In scope (backend):**
- Default warranty terms per item (`item_warranty`): duration months, terms text, coverage JSONB, active flag.
- Warranty registration data paths: manual API, auto (external invoice ref supplied by the order/invoice boundary —
  no invoice domain is built), and batch import (row-validated backend import contract); serial-keyed validation via
  FS-06 for serialized items; coverage window calculation; ACTIVE/EXPIRED/VOID lifecycle; expiry job.
- Warranty claims: creation, validation against registration/coverage (`validation_result JSONB`), approve/reject with
  explicit override approval, claim action ledger (credit-memo ref/repair/replacement/refund/reject) append-only,
  completed/cancelled lifecycle; vendor linkage for vendor repair/return references (FS-08 vendor refs).
- Repair-order data (backend only): OPEN/IN_PROGRESS/COMPLETED/CANCELLED, labor/parts costs, location/serial refs; no
  inventory movements (normal inventory documents handle stock) and no order/RA UI.
- Customer part number registry: item↔customer part mappings, uniqueness (per customer part number; one per
  item+customer), active/inactive soft state, import data path, resolution by customer+part number for order/invoice
  callers, role/permission scopes.
- Auto Assign UPC registry: eligible-item detection (inventory, assembly, matrix child — the documented
  standard/assembly/matrix scope), UPC-A generation with check digit, assignment/retirement, `upc_registry` audit,
  UPC↔item linkage (mirror to `item.upc_code` via `item.master`), batch assignment job + monitoring/reconcile job,
  tenant enable/disable of automatic assignment.
- Backend read surfaces other sets/dependants rely on (`extensions.registry` contract) incl. registrations/claims/
  customer parts/UPC status.

**Out of scope / deferred:**
- UI/workbooks/reports, saved searches, employee-center/vendor-center screens, warranty/repair reports (FS-15 views only).
- Order management, invoices, RA/credit-memo documents, order/invoice line behavior: only opaque external refs are
  stored (D3). No order UI or document creation.
- External integrations: invoice feed/email capture, vendor portal, barcode printers/label rendering, Auto Assign UPC
  saved searches; SuiteApp packaging/install/roles UI.
- Inventory effects for replacement/repair stock: use normal inventory documents (DM-EXT-05); no posting in FS-14.
- Mobile.

Business rules and invariants:

- `DM-EXT-01`: warranty registration requires a serialized item identity when the item is serialized (FS-01
  `requires_numbering`/`item_type`); serial must exist and belong to the item (FS-06 contract); auto-registration is
  driven by an external invoice reference, never by inventing invoice data (BOUNDARY; §14 C-3).
- `DM-EXT-02`: a claim can be approved only when the registration is ACTIVE and `received_at` within warranty, or with
  an explicit override approval recorded (in `validation_result.override` and/or `warranty_claim_action` with
  `action_type=REJECT`? no — override approval is a platform approval action reference; stored in `validation_result`).
- `DM-EXT-03`: customer part numbers are tenant+customer scoped; customer ids are external refs (no PII); one part
  number per (item, customer) and one item per (customer, part number).
- `DM-EXT-04`: UPC codes are unique per tenant **including retired ones** (never reuse a retired UPC); assignment and
  retirement are append-audited; a retired row is never deleted or edited (only status/retirement fields set once).
- `DM-EXT-05`: warranty/repair data never posts inventory; replacement/repair stock moves go through normal inventory
  documents (T-12/T-07 etc.) outside this set.
- `EXT-RULE-01` (coverage): `warranty_end = warranty_start + (coverage_override.duration_months ?? item_warranty.
  warranty_duration_months) months`; `warranty_start` defaults to `registered_at` (or external invoice date when
  supplied); end < start rejected.
- `EXT-RULE-02` (serial uniqueness): a serialized unit may have at most one ACTIVE registration; a new registration
  requires the prior one to be EXPIRED/VOID; `serial_id` must match the claim/repair item.
- `EXT-RULE-03` (claim actions): actions are append-only with strictly increasing `sequence`; `DONE` transitions are
  one-way; failed external refs remain FAILED for audit; no deleting/editing performed actions.
- `EXT-RULE-04` (UPC eligibility): auto-assign only for tenant items where `item_type ∈ {INVENTORY, SERIALIZED,
  LOT_NUMBERED, ASSEMBLY, MATRIX_CHILD}` and `can_stock=true`; matrix parents and non-stock items excluded; documented
  scope "new inventory and assembly items (standard and matrix)" (iri-387).
- `EXT-RULE-05` (UPC generation): UPC-A (12 digits: 11 data + 1 check digit) with mod-10 check; tenant company prefix;
  deterministic collision handling (retry next sequence value, never reuse); `checksum_valid=true` on generated codes.
- `EXT-RULE-06` (mirror consistency): `upc_registry` is authoritative for assignment/retirement history;
  the primary `UPC_A` `item_barcode` and `item.upc_code` are projections updated through `item.master` in the same
  transaction (FS-01 RULE-ITEM-16 requires the header field to equal the primary barcode); if the mirror update fails
  the whole assignment rolls back (no registry row without mirror for ASSIGNED items).
- `EXT-RULE-07` (customer part import): import is a data path only — no order/invoice creation; resolution is read-only.
- Cross-set invariants: `INV-25` tenant isolation, `INV-26`/DM-GLOBAL-08 state machines, `DM-GLOBAL-01..10`,
  `DM-EXT-01..05`.

State machines:

- `warranty_registration`: `ACTIVE → EXPIRED` [warranty_end < as_of via `extensions.warranty.expiry`];
  `ACTIVE → VOID` [manual, no open claims]; no EXPIRED→ACTIVE (new registration required).
- `warranty_claim`: `OPEN → UNDER_REVIEW → APPROVED|REJECTED`; `APPROVED → COMPLETED` [all actions DONE];
  `OPEN|UNDER_REVIEW → CANCELLED`; REJECTED/CANCELLED terminal. Approval guarded by DM-EXT-02.
- `warranty_claim_action`: `PENDING → DONE|FAILED` (one-way), append-only rows.
- `warranty_repair_order`: `OPEN → IN_PROGRESS → COMPLETED`; `OPEN|IN_PROGRESS → CANCELLED`.
- `upc_registry`: `ASSIGNED → RETIRED` (one-way; no reuse); item assignment creates ASSIGNED row.
- Side effects: every transition writes `audit_event` + one outbox event (per aggregate ordering); UPC assign/retire also
  writes the item mirror via FS-01 contract inside the same transaction.

## 12. Rollback

- Redeploy the previous image; migrations are additive and N-1 compatible; no down-migration in prod.
- Flag off `extensions.registry.enabled`: blocks new registrations/claims/customer-part/UPC writes; existing records
  stay readable; jobs disabled; UPC mirror on items stays as-is (no destructive cleanup).
- Records are append-audited; corrections are new registrations/claims/actions, never edits/deletes; a UPC retirement
  is one-way (no un-retire; a new item assignment uses a new code).
- Migrations additive/N-1 compatible; no prod down-migration.
- If auto-assignment must stop, set `extensions.upc.auto_assign` off (immediate); already-assigned UPCs keep working.
- Dependants (FS-15) blocked by `check-env` until FS-14 verified.
