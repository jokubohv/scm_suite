## 1. Objective and source coverage

Deliver the identity layer of numbering: lot and serial masters, an append-only serial history, and a
**current serial projection** that is a strict function of the ledger and commitment tables. The set also
closes the deferred `lot_id`/`serial_id` foreign keys that FS-04/FS-05 created nullable, adds the
per-position detail contract that makes "line qty = Σ detail qty" enforceable for numbered items, and
publishes deterministic FEFO/expiry selection hooks and traceability search APIs used by counts,
procurement, manufacturing, WMS, quality, consigned inventory and reporting.

## 2. Scope

**In scope (backend):**
- Lot master: lot number (immutable), item, manufacture/expiry dates, lot/specific cost basis, notes,
  active flag, custom fields (FS-00 EAV, entity types `LOT`/`SERIAL`), derived ACTIVE/DEPLETED status.
- Serial master: serial number (immutable), item, current projection (`state`, location, bin, status,
  ownership, `customer_ref`), per-unit specific cost, last transaction; append-only serial history with
  from/to position and event type.
- Numbered-inventory detail contract: every ledger line for a numbered item carries `inventory_transaction_detail`
  rows keyed by `(bin, lot, serial, status, ownership)`; serial rows are single-unit; line qty = Σ detail
  (INV-19); serial count = line qty (INV-18). Enforced at API validation and DB-trigger backstop.
- Serial projection updates and history append **inside the posting transaction** (ledger detail insert /
  commitment allocation insert, release and fulfil effects).
- Commit quantities for numbered inventory: C-01 commitments must allocate serials for serialized items and
  lots/bin for lot items; active serial is reserved at most once (iri-099 mismatch avoidance).
- Selection rules for receipts, fulfilment, transfers (T-09/T-10/T-11), assembly builds/unbuilds
  (T-15/T-16), counts, consigned ownership transfers and adjustments, including FEFO/expiry policy.
- FEFO hooks for allocation/ATP/pick suggestions: deterministic, read-only lot-position recommendation;
  expired-lot rejection (`422 LOT_EXPIRED`).
- Traceability search APIs (serial by customer ref/state/location; lot by item/expiry window; history).
- Interactions with counts (FS-07): snapshot/line positions include lot/serial; count-variance routing
  rules for numbered positions; reconciliation of serial projection vs ledger detail.
- Migration `0013_numbered_inventory`: create 3 tables, backfill deferred lot/serial columns, validate
  FKs, install validation/projection triggers; orphan check must return zero (`DM-GLOBAL-06`).

**Out of scope / deferred:**
- Lot auto-numbering (SuiteApp `iri-108..109`, DEFERRED-SUITEAPP), allergen statements, label printing,
  barcode/GS1 scanning (`iri-406` / mobile), serial-numbered customer portal, serial REST plugins.
- Any UI/mobile workflow (Smart Count/SCM Mobile permanently excluded, D8), SuiteApp packaging.
- Bin/zone topology and status registry (FS-03), posting engine (FS-04), costing math (FS-05),
  manufacturing build semantics (FS-09), WMS pick tasks (FS-11) — consumed by contract only.
- Analytics/read-model presentation (FS-15 owns `v_lot_expiry`/`v_serial_history`).

Business rules and invariants (cite DATA-MODEL/ARCHITECTURE ids):

- `DM-TRACE-04`: a serial's current projection equals its latest `serial_number_history` row and the sum of ledger
  detail for that serial (`INV-18`); projection updates happen only inside the posting/commitment transaction.
- `DM-TRACE-05`: picking/issuing an expired lot is rejected `422 LOT_EXPIRED` when the item's expiry policy requires
  FEFO/expiry; expiry is required when tenant/item policy `require_expiry_for_fefo` is on (`ASSUMPTION`, DMX-15).
- `DM-TRACE-06`: lot and serial numbers are immutable identifiers; renumbering is prohibited (new identity instead).
- `DM-TRACE-07`: `serial_number.ownership` follows the posting dimension; a serial cannot be simultaneously
  OWNED and CONSIGNED; T-21/T-22/T-23 are the only ownership changers.
- `DM-TRACE-08`: direct updates to `serial_number.current_*` outside the posting/commitment engine are rejected
  by trigger; status changes post as qty-neutral T-30.
- `DM-COST-11` / FS-05: SPECIFIC/LOT costing requires numbered identity columns; a `cost_layer` for a serial has
  `qty_original = 1`; `lot.cost_basis`/`serial_number.specific_cost` are authoritative for specific cost when set
  (FS-05 reads them through `costing.engine`).
- `INV-18`: each serial has exactly one current position and quantity 1 per position; serial count per line = line qty.
- `INV-19`: line quantity equals Σ detail (bin/lot/serial/status) quantity — for numbered items the trigger also
  enforces this; mismatch rejects the whole posting `409 SERIAL_QTY_MISMATCH` (`FS-06` acceptance).
- `DM-GLOBAL-06`: no orphan lot/serial values after the backfill; FK constraints validated (`NOT VALID`→`VALIDATE`).
- `T-08`/worksheet prohibition: absolute inventory worksheets are prohibited for lot/serial-numbered items
  (DATA-MODEL §7 worksheet trigger, FS-04 §5.14). Numbered corrections/counts use incremental adjustments
  (T-07/T-20 with explicit lot/serial detail); FS-06 does not provide absolute-count semantics for numbered items
  (resolves FS-04 §14 open question #8).
- FS-05 gating: before FS-06 is verified, FS-05 rejects SPECIFIC/LOT postings (`409 DEPENDENCY_NOT_DEPLOYED` /
  `422 VALIDATION_FAILED`, FS-05 §14 #5); after `0013_numbered_inventory` closes the identity columns/FKs, those
  methods post normally. `item_inventory.costing_method` remains immutable (`DM-ITEM-02`).
- Error contract: FS-06 raises custom SQLSTATE class `TN` (`TN001..TN006`); FS-04's provider contract already
  declares the shared `SERIAL_CONFLICT`/`LOT_CONFLICT` error codes and its posting error translator maps `TN*`
  to them (`409`/`422`). Callers never write ledger/cost tables directly.
- Numbered posting rules: receipt creates identities (T-01/T-13/T-21); issues require existing identities
  (T-03/T-07/T-10/T-12/T-15..T-18/T-23/T-28 has no inventory movement); transfers carry identities unchanged
  (T-09/T-10/T-11); assembly output creates new identities with qty=built qty and consumes component identities
  (`DM-MFG-11`); count variance for numbered positions posts through the incremental-adjustment path provided by
  FS-04/FS-07 (`DM-CNT-06`), not worksheet shortcuts.
- Commit quantities (iri-099): for serialized items, C-01 allocates one serial per committed unit and the number of
  active serial allocations equals `qty_committed`; for lot items, allocation is by lot/bin and Σ allocations =
  `qty_committed`; a serial can be actively allocated at most once (partial unique index in DATA-MODEL §7).
- Status rules: only `inventory_status.is_committable=true` positions may be committed (`DM-TRACE-03`); status
  moves are T-30 and must not cross ownership.
- Query rules: lot/serial search requires tenant + at least one dimension filter and a bounded result; serial history
  queries are cursor-paginated by `(occurred_at, id)`; cost fields returned only with `reporting.cost.view` / cost scope.
- Custom fields (`DM-ITEM-13` pattern, FS-00 EAV): `entity_type` `LOT`/`SERIAL`; required custom fields block
  registration; `is_searchable` fields are filterable on list endpoints.

Numbered-inventory detail contract (with FS-04 / FS-05):
- Posting commands accept a `details[]` array per line: `{bin_id?, lot_id?, serial_id?, inventory_status_id,
  ownership, qty_base}`; for lot-numbered items `lot_id` is required on every on-hand movement; for serialized
  items one detail row per serial with `qty_base=±1`.
- DB-level guard (installed by 0013) validates, inside the posting transaction: item numbering policy vs identity
  presence, serial count = line qty, lot qty allocation ≤ lot on-hand, expiry policy, ownership, serial state
  legality; failures raise custom SQLSTATE `TN001` mismatch, `TN002` serial conflict, `TN003` identity required,
  `TN004` expired, `TN005` projection/history mismatch, `TN006` ownership. FS-04's error translator maps these to
  `409 SERIAL_QTY_MISMATCH` / `409 SERIAL_CONFLICT` / `422 LOT_REQUIRED` / `422 LOT_EXPIRED` / `409 NUMBERED_CONFLICT`.
- FS-05 receives identities through the same transaction; it must not re-resolve lots/serials outside the posting.

State machines (this set owns the serial lifecycle projection and lot active lifecycle):

**Serial (`serial_number.state`)** — derived from ledger + commitment state; every transition is causally triggered
by a posting/commitment command, never by a direct API call:

| From | To | Trigger | Guard |
|---|---|---|---|
| UNKNOWN (registered) | AVAILABLE | T-01/T-13 receipt detail | identity first appears on an inbound detail row |
| AVAILABLE | COMMITTED | C-01 allocation | committable status, serial available, first active allocation |
| COMMITTED | AVAILABLE | C-02 release / C-03 reallocate | allocation released, no other active allocation |
| AVAILABLE/COMMITTED | IN_TRANSIT | T-10 TO fulfilment | serial was allocated to the TO line |
| IN_TRANSIT | AVAILABLE | T-11 TO receipt | destination detail row |
| AVAILABLE/COMMITTED | FULFILLED | T-12/T-14 fulfilment | line qty matches serial detail |
| FULFILLED | RETURNED | T-13 customer return | return status applied (`EXT`: return status configurable) |
| RETURNED | AVAILABLE | T-30 status change / putaway receipt | return-to-sellable configuration (`ASSUMPTION`) |
| any non-terminal | SCRAPPED | T-07 with scrap reason code | reason_type `SCRAP`; terminal state |
| any (reversal) | previous | T-02/reversal | compensating history row; projection restored from latest history |

**Lot lifecycle:** `ACTIVE` ⇄ `DEPLETED` are derived from `inventory_balance_lot` (on-hand/committed) — a lot is
DEPLETED at zero on-hand and re-activates only through a new inbound posting; `is_active=false` is an administrative
soft inactivation that blocks selection for new outbound postings but keeps historical references readable.

Base path `/api/v1`, JSON, UTC timestamps (`Z`), quantities as decimal strings (e.g. `"12.000000000000"`), money as
decimal strings; auth scope per endpoint; tenant resolved from principal (RLS enforced). Errors use the platform
envelope `{code, message, details, correlation_id}` (RFC 9457). All create/state-changing endpoints require
`Idempotency-Key`; `If-Match` on mutable masters.

## 12. Rollback

- Redeploy the previous image; migrations are additive and N-1 compatible; no down-migration in prod.
- Flag off `inventory.numbered.enabled`: numbered writes rejected; lot/serial rows, history and validated FKs remain
  readable; FS-04/FS-05 continue operating (columns are nullable).
- Migrations are additive/N-1 compatible; no down-migration in prod. The down-migration exists and is tested for
  dev/staging only (drops triggers, then tables; FKs must be dropped before tables).
- Data compensation: corrections are compensating postings (reversal / adjustment), never deletes; identities are
  never renumbered or removed.
- Dependants automatically blocked by `check-env` while status ≠ verified.
