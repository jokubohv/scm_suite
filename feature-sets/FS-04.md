## 1. Objective and source coverage

Deliver the append-only system of record and the single atomic posting engine every other Phase-1
context writes through: one posting command = one DB transaction = one immutable
`inventory_transaction` with signed line/detail movements, synchronously maintained balances and
availability, commitments/allocations, transfer-order and one-step transfer flows with in-transit,
adjustments/absolute worksheets, the UNALLOCATED bootstrap distribution, the idempotent import
contract, the external order-boundary implementation (D3), and finance journal intents for every
value-bearing posting (D2). It is the most load-bearing set in the plan: all 31 posting types,
quantity/value conservation and the reconcile-exact target are enforced here.

## 2. Scope

**In scope (backend):**
- The 16 posting dimensions and the canonical `PostingCommand`/posting-plan model; the single atomic
  posting engine (17 steps) used by every posting type; append-only transaction header/line/detail.
- 31 posting-type contracts (T-01..T-31): native implementation for the ledger-owned types
  (T-07/T-08/T-09/T-10/T-11/T-12/T-13/T-14/T-28/T-29/T-30/T-31) plus the generic `PostingPort`
  invocation for types driven by other sets (T-01..T-06, T-15..T-27) — this set owns the ledger rows,
  balance updates, idempotency, events and finance intents for all of them.
- Synchronously maintained quantity models (`inventory_balance`, `inventory_balance_bin`,
  `inventory_balance_lot`, `inventory_in_transit`) and availability derivation; `qty_on_order`
  projection; backorder quantities.
- Commitments, allocations and the 6 non-posting commands C-01..C-06 (C-06’s ledger half only;
  FS-09 owns WO state).
- Documents owned here: `inventory_adjustment`, `inventory_worksheet`, `inventory_transfer`,
  `transfer_order`, `inventory_distribution`, `import_batch`; external order-boundary commands
  (commit/release/reallocate/fulfill/return_receipt) implemented as idempotent commands.
- Reversal/compensation, backdating/period policy, negative-inventory policy (BLOCK/WARN/ALLOW),
  import batches, reason codes, balance/availability/commitment/in-transit read APIs.
- Finance journal intents for every value posting (D2) and `inventory.*` event publication wrapped by
  the `order.supply@0.1.0` outbound envelope (D3), both inside the posting transaction.
- Generic internal posting command (`POST /v1/inventory-transactions`, §5.17.1) — the provider surface
  consumer contexts (FS-07/08/09/11/12/13) and service/test harnesses use to post their allowed
  transaction types through the same 17-step engine, idempotency, locks, events and finance intents.
- Reconcile jobs (balances, open quantities, in-transit, commitments, outbox) and read-model repair.
- Flags, seeds, OpenAPI/event schemas, tests and deployment gates.

**Out of scope / deferred:**
- Costing math, layers, cost ledger, recalculation, landed cost, standard cost, COGS adjustments
  (FS-05 `costing.engine`; this set calls `costing.value_movement` inside its transaction).
- Source documents of other contexts: PO receipts (FS-08), vendor returns/credits/bills (FS-08),
  work orders/WIP/builds (FS-09), counts (FS-07), consigned transfers (FS-13), quality holds (FS-12),
  revaluations/landed costs (FS-05) — each owns its document/state machine and calls this set.
- Lot/serial identity/history tables (FS-06; ledger columns are nullable deferred FKs until then).
- WMS task/wave/bin-block semantics (FS-11; FS-11 calls T-29/T-30).
- Order management/customer master (external boundary, opaque `external_ref` only, D3).
- **Sell-side price snapshot persistence (provider boundary):** the inventory ledger stores inventory
  valuation (`unit_cost`, `value_base`, `value_txn`) only. Sell-side `unit_price`/`price_source`/
  `price_rule_id` snapshots are generated and owned by FS-02 `pricing.engine@1.0.0` and consumed by the
  external order boundary (order lines); there are no sell-side price columns on `inventory_ledger`
  tables and this FS adds none (§5.17).
- GL/journal/period close/tax (finance boundary; intents only, D2), intercompany transfers,
  FX revaluation (deferred).
- UI, mobile (permanently excluded), analytics, integrations.

The engine derives a **posting plan**: header (type/dates/source/idempotency), `movements[]`
(deduplicated by position, sorted), `value_movements[]` (from FS-05), `gl_intents[]` (posting rules
§5.18), `events[]`, `balance_updates[]` (ordered/deduped) and `document_updates[]`. Plan invariants:

change; pure moves value-neutral), `INV-19` (line qty = Σ detail qty), `INV-13/14` rounding
(FS-05-owned math, ledger asserts). **Field boundary:** `unit_cost`/`value_base`/`value_txn` are
inventory valuation fields; sell-side prices are not part of `PostingCommand` or the ledger (FS-02
provider boundary, §5.17).

### 5.5 Atomic posting algorithm — 17 steps, step by step

Normative source: ARCHITECTURE §2.4. Each step below states the FS-04 concrete action, writes and
failure mapping. One DB transaction; `READ COMMITTED` + ordered explicit locks; retry ×3 with jitter on
deadlock/serialization then `503 RETRYABLE`; statement timeout 30 s, lock timeout 5 s.

| Step | FS-04 action | Writes / reads | Failure → HTTP code |
|---|---|---|---|
| 1 | Authenticate/authorise: JWT/API key → tenant; service identity for in-process consumers; enforce RBAC scope of the posting type + data scopes (locations/classes) + flag `inventory.ledger.enabled` | reads auth context, `user_data_scope`, `feature_flag` | `401/403`, `409 DOMAIN_DISABLED` |
| 2 | Idempotency: canonicalise command → SHA-256; `INSERT idempotency_key ON CONFLICT DO NOTHING`; existing same hash → replay stored response; existing different hash → conflict; concurrent in-flight → 409/425 retry hint | `platform.idempotency_key` | `409 IDEMPOTENCY_KEY_REUSED` |
| 3 | Lock and load source document `SELECT … FOR UPDATE` (rank 0); verify state-machine transition, approval prerequisite, feature flag; verify document not already posted (`posted_transaction_id IS NULL` unless reversal) | source doc table (FS-04-owned docs; for external commands a synthetic lock row is the `inventory_transaction` command lock/`idempotency_key`) | `404`, `409 INVALID_STATE_TRANSITION`, `409 DEPENDENT_DOCUMENTS` for reversal |
| 4 | Static validation — accumulate all errors: line/header shape; posting type allowed for item type; UoM conversion exists and is exact; qty sign/direction; location/bin/status via FS-03 `validate_posting_position`; reason code required; lot/serial presence rules; priced lines have FS-02 snapshot (external demand); period date format | FS-01/FS-03 read-only, FS-02 price snapshot | `422 VALIDATION_FAILED` (errors[]) |
| 5 | Build posting plan: explode kits/groups (T-14), resolve matrix children, per-line location, convert qty to base UoM (`qty_base = qty_uom × factor`), compute signed movements, merge duplicate positions deterministically, split details per bin/lot/serial/status/ownership, derive GL posting-rule ids | in-memory | `422` |
| 6 | Date/period resolution: `transaction_date` (must be ≤ today + `inventory.backdating.forward_days` default 0); `posting_at=now()`; `fiscal_period_id` and status from `FinancePort.get_period_status`; backdating flag if `transaction_date < latest_effective_date(item, cost_object)`; closed-period rule (§5.9) | `platform.fiscal_period` via port | `409 PERIOD_CLOSED` / `POLICY_VIOLATION` |
| 7 | Lock acquisition in rank order (§5.6): sorted cost-object advisory locks (rank 2), then balance rows (rank 3), commitment rows (rank 4), cost layers (rank 5 under advisory lock), sequence (rank 6); if a lock cannot be acquired within 5 s → retryable failure | locks only | `503 LOCK_TIMEOUT` |
| 8 | Post-lock revalidation (authoritative): re-read balances/commitments/document quantities; availability & negative policy; serial availability/uniqueness; lot quantity; WIP compatibility (FS-09 guard data); group-average worksheet prohibition; limit-to-committed; over-receipt tolerance; closed-period guard; **FS-05 pre-post cost check** (`costing.assert_postable`) → `409 COSTING_RECALC_REQUIRED` (D5 default block) / `COSTING_INCOMPLETE` | balances, commitments, item cost status via port | `409 INSUFFICIENT_AVAILABLE/INSUFFICIENT_ON_HAND/SERIAL_CONFLICT/LOT_CONFLICT/POLICY_VIOLATION/COSTING_*` |
| 9 | Value computation: for each movement call FS-05 `costing.value_movement(movement, cost_object_lock)` → `{unit_cost, value_delta, layer_actions[], estimated}`; rounding/scale; assign `cost_object_id`; largest-remainder allocation of posting residual; build `value_movements` | FS-05 reads/writes in same tx (cost artefacts persisted in step 13) | `422`, `409 COSTING_INCOMPLETE` |
| 10 | Append ledger: allocate `ledger_sequence` (rank-6 sequence update), insert `inventory_transaction` header, `inventory_transaction_line` rows, `inventory_transaction_detail` rows (no updates/deletes). Set `total_qty_base/total_value_base`, `cost_estimated`, rounding flag | `inventory_transaction*` | rollback on any error |
| 11 | Update derived balances for distinct positions in sorted order (`INSERT … ON CONFLICT DO UPDATE` + row locks): on-hand, committed/backordered (T-12/T-13), bin and lot read models, value, `last_ledger_sequence`, `last_posting_at`; enforce CHECKs (`qty_available ≥ 0`, serial ≤ 1) | `inventory_balance`, `_bin`, `_lot`, `inventory_in_transit` | `409` mapped from constraint violation (should be unreachable after step 8) |
| 12 | Update document/reference state: source doc lines/quantities/status (`qty_received/fulfilled/billed/returned`, TO staged quantities, worksheet/import row state), `posted_transaction_id` (+`UNIQUE` 1:1 guard), `document_link` conversion rows, commitment `qty_fulfilled`/`qty_backordered` | source doc tables + `platform.document_link` | rollback |
| 13 | Persist cost artefacts from step 9: `cost_ledger_entry`, `cost_layer`, `cost_layer_consumption`, `item_cost`, `cost_variance` rows (FS-05 tables; written by FS-05 inside this transaction under its cost-object advisory lock) | costing tables | rollback |
| 14 | Enqueue events: one `outbox_event` per aggregate change (including FS-05-produced events such as `cost.layer.created`), monotonic `aggregate_version`; `order.supply@0.1.0` envelope records for order-boundary commands (the envelope wraps the `inventory.*` event payloads) | `platform.outbox_event` | rollback |
| 15 | Audit: append `audit_event` rows (document state change, privileged fields, reversal reason, negative-policy override, backdating) | `platform.audit_event` | rollback |
| 16 | Persist idempotency result (status/body/resource id) and bump document `version` (optimistic); mark in-flight row completed | `platform.idempotency_key`, source doc | rollback |
| 17 | COMMIT; then emit metrics/traces, enqueue post-posting jobs via outbox/recovery: FS-05 recalculation if backdated (`costing.recalculate`, from `transaction_date`), planning invalidation, report refresh; job enqueue failure is retried by the outbox/recovery job (never affects the committed posting) | jobs | none (async) |

If any step 3–16 fails, the whole transaction rolls back: no ledger row, no balance change, no event,
no idempotency completion. Idempotency in-flight rows are released in the same rollback (re-request
allowed).

### 5.6 Lock ordering (deadlock-free by construction) and batch rules

| Rank | Resource | Acquisition | Notes |
|---|---|---|---|
| 0 | Source document row(s) | `SELECT … FOR UPDATE` by `(tenant, doc_id)` in ascending id order for multi-doc commands | Serialises double-post; hold for transaction. |
| 1 | Idempotency key | `INSERT … ON CONFLICT DO NOTHING` (no long hold) | Early dedupe. |
| 2 | Cost-object advisory locks | `pg_advisory_xact_lock(hashtext(tenant_id), hashtext(cost_object_key))` for **all** cost objects, ordered by `md5(cost_object_key)` numeric ascending | Protects value computation per item/cost group; multi-item postings acquire all keys sorted before proceeding. |
| 3 | Balance rows | `SELECT … FOR UPDATE` ordered by `(item_id, location_id, inventory_status_id, ownership, qty_class, lot_id NULLS FIRST, serial_id NULLS FIRST)` | Sorted batch; no table locks. |
| 4 | Commitment rows | same sort key as balances | Interleaves safely with C-01..C-03. |
| 5 | Cost layers | under rank-2 advisory lock, ordered by `layer_seq` | Belt-and-braces row order. |
| 6 | Number sequence (`ledger_sequence`, `document_number`) | `UPDATE … RETURNING` | Held last, microseconds; gap policy from FS-00. |

Rules: (a) a transaction may only acquire a rank ≥ the highest currently held; (b) validations before
rank 0 use no locks and are re-validated at step 8; (c) lock timeout 5 s, retry ×3 with jitter, then
`503 LOCK_TIMEOUT`/`RETRYABLE`; (d) import batches chunk by item range so a cost lock is never held for
a whole file (C-08); (e) reconcile/repair jobs take an advisory lock on `(tenant, 'reconcile')` and
never lock ranks 0–3 except for read-model repair in short batches.

### 5.7 Idempotency contract

| Aspect | Rule |
|---|---|
| Key source | HTTP `Idempotency-Key` header (required on POSTs that create/post documents/commands); in-process callers must pass a derived key (e.g. `posting:<source_doc_type>:<source_doc_id>:<revision>`); imports use `import_batch.idempotency_key` + row number. |
| Scope | `(tenant_id, endpoint_id, key)` unique in `platform.idempotency_key`; endpoint_id = route template or in-process command name. |
| Fingerprint | canonical JSON (sorted keys, decimal strings normalised to NUMERIC(38,12), dates ISO, UTC timestamps) SHA-256; stored with the key. |
| Hit behaviour | same fingerprint → replay stored `{status, body, resource_id}`; different → `409 IDEMPOTENCY_KEY_REUSED`; concurrent same key → `409/425` with retry hint (`in_progress` + short advisory lock). |
| Second line of defence | `inventory_transaction.idempotency_key UNIQUE (tenant)` partial + `posted_transaction_id UNIQUE` on documents (DM-GLOBAL-07) → a document can post at most once even after key retention expires. |
| Internal callers | If a caller retries after a crash, the derived key returns the original transaction id; callers never generate random keys for the same logical posting. |
| Retention | 7 days default (tenant-configurable); replay of an expired key relies on the second line of defence (returns `409 INVALID_STATE_TRANSITION`/existing resource by source-doc lookup). |
| Imports | Batch-level key = no-op on duplicate batch; row-level posting key = `import:<batch>:<row>`; POSTED row re-post is a no-op (DM-LED-10). |
| Consumers | Event consumers dedupe on `event_id` via `platform.event_consumer_checkpoint`; handlers upsert, never blind-increment (ARCHITECTURE §5.7). |

### 5.8 Reversal, void and compensating rules (R-01..R-09, FS-04 enforcement)

| Rule | FS-04 behaviour |
|---|---|
| R-01 | Ledger tables are append-only: DB triggers `trg_*_append_only` raise on UPDATE/DELETE; application DB role has only `SELECT, INSERT` on `inventory_transaction*`; migration role separate (INV-09, DM-LED-01). |
| R-02 | `PostingService.reverse` builds the exact negated movements (qty and value) of the original; inserts a new header with `reversal_of_transaction_id` (partial unique → at most one reversal per transaction) and `reversal_reason`; assigns a fresh `ledger_sequence`; never mutates the original. Reversal transaction type is `<ORIGINAL>_REVERSAL`-mapped (e.g. `RECEIPT_REVERSAL`, `ADJUSTMENT_REVERSAL`); value replay via FS-05 `value_reverse`. |
| R-03 | Documents that never posted may go `DRAFT/APPROVED → VOID` (no ledger rows). Posted documents cannot be voided; their API returns `409 INVALID_STATE_TRANSITION` for void and offers reversal per state machine. |
| R-04 | Before reversal, check dependants via `platform.document_link`: any non-reversed dependent posting of the original (matched bill, fulfilled serial, consumed layer beyond availability, count snapshot referencing it) → `409 DEPENDENT_DOCUMENTS` with the list. FS-05 supplies the cost-layer/consumption dependency check inside the transaction. |
| R-05 | Reversal value must equal the negated original on the same dimensions. If original layers/lots/serials were consumed and cannot be restored exactly, FS-05 consumes currently available layers/identities and the residual posts as `cost_adjustment` (T-25) with `reversal_cost_drift=true`; the ledger header records `reversal_reason` and the event carries `value_drift` for monitoring. |
| R-06 | Reversal date: original `transaction_date` when its fiscal period is `OPEN`; otherwise earliest open period with `backdated_original_date=<original date>` and `period_shifted=true`; finance port decides period status (never the ledger alone); intent carries both dates. |
| R-07 | Reversal restores open document quantities (e.g. receipt `on_order`), re-evaluates commitments, enqueues FS-05 recalculation from `min(original_date, reversal_date)`, and emits `*.reversed` + `inventory.reversal.posted`. |
| R-08 | Approvals are superseded by audit, never deleted; cancellation of an approved-unposted document requires `inventory.adjustment.approve`-level authority and is audited. |
| R-09 | Import failures never partially post: import posting is per row (independent idempotent commands) with a committed cursor; posted rows are never rolled back by later failures. |

Endpoint/API mapping: reversal is exposed on each owned document (`POST /{resource}/{id}/reverse`) and
generically on ledger transactions for operations (`POST /v1/inventory-transactions/{id}/reverse`,
scope `inventory.transaction.reverse`, `Idempotency-Key` required). The generic route validates the same
R-01..R-09 rules from the transaction’s `transaction_type` and source linkage.

### 5.10 Negative inventory and underwater policy

Tenant setting `inventory.negative_inventory_policy` = `BLOCK` (default) | `WARN` | `ALLOW`, with
per-class overrides (`issue`, `adjustment`, `import`, `transfer`) whose defaults are `BLOCK`,
`WARN`, `WARN`, `WARN` (ARCHITECTURE §2.7). Policy applies at step 8 to any movement that would drive
`qty_on_hand < 0` for the resulting position.

| Mode | Posting behaviour | Costing behaviour | Signals |
|---|---|---|---|
| `BLOCK` | Rejected `409 INSUFFICIENT_ON_HAND`; nothing written. Exception: an incremental adjustment whose *purpose* is to correct a negative position may still be negative when the caller holds `inventory.allow_negative` and sends `negative_policy_override="ADJUSTMENT_CORRECTION"` (audited) | n/a | — |
| `WARN` | Posting proceeds; response `warnings=["NEGATIVE_INVENTORY"]`; header `cost_estimated=true` when the fallback cost is used | FS-05 uses last purchase price or zero if no history, `cost_ledger_entry.estimated=true` | `inventory.underwater.detected` |
| `ALLOW` | Posting proceeds for all types subject to `inventory.allow_negative` role scope | As WARN; on replenishment the true cost is applied and the difference posts as System COGS adjustment (T-25, FS-05) | both events + `cost.underwater.trued_up` (FS-05) |

Hard rules regardless of mode: `qty_available >= 0` always (generated + CHECK, `INV-04`); commitments
against an underwater position are **always** rejected (`409 POLICY_VIOLATION`); a negative position
appears in `v_negative_inventory` (FS-15) and in the `GET /v1/inventory/balances` response with
`underwater=true`; group-average items borrow the group average for underwater issues (FS-05);
underwater duration > tenant threshold raises an operations alert (`ledger.negative_inventory.scan`).
No schema change is needed for the warning: the negative position is authoritative in
`inventory_balance`; the header flag is `cost_estimated` and the API/event carry the warning
(implementation note).

### 5.11 Quantity model, balances and availability derivation

| Quantity | Definition / formula | Stored where | Derived vs stored | Updated by |
|---|---|---|---|---|
| On hand | Σ signed ledger qty per position | `inventory_balance.qty_on_hand`; `inventory_balance_bin.qty_on_hand`; `inventory_balance_lot.qty_on_hand` | **Derived from ledger**, materialised | step 11 of every posting; nightly `reconcile.balances` proves equality (`INV-03`, `INV-07`) |
| Committed | Σ active commitment qty | `inventory_balance.qty_committed` | stored (guarded arithmetic) | C-01/C-02/C-03, T-12/T-13 (`qty_fulfilled`) |
| Available | `GREATEST(qty_on_hand − qty_committed, 0)` | `inventory_balance.qty_available` | **generated column**, read-only | DB generated; CHECK ≥ 0 (`INV-04`) |
| On order | open supply document qty | `inventory_balance.qty_on_order` | projection (not authoritative) | C-04 raises destination on-order; FS-08/09/10 events applied by `OnOrderProjection`; `ledger.reconcile_open_quantities` |
| To order | preferred stock − available (planning) | `replenishment_calculation_line` (FS-10) | planning only | FS-10 job — never here |
| Back ordered | committed qty with no stock at fulfilment | `inventory_commitment.qty_backordered`; `inventory_balance.qty_backordered` read model | stored per commitment | T-12 shortfall path; external order remains responsible for promise dates |
| In transit | `qty_fulfilled − qty_received` per TO line | `transfer_order_line.qty_in_transit`; `inventory_in_transit.qty_in_transit`; `inventory_balance` rows with `qty_class='IN_TRANSIT'` at destination | derived+stored | T-10/T-11; trigger equality (`INV-05`) |
| Allocated (commitment) | specific bin/lot/serial reserved units | `inventory_commitment_allocation.qty` | stored | C-01/C-02/C-03/T-12 |
| Negative/underwater | positions with `qty_on_hand < 0` | `inventory_balance` | derived (view) | any negative-allowed posting; `ledger.negative_inventory.scan` |

Position key = `(tenant, item, location, status, ownership, qty_class, lot, serial)`; **bin is a
sub-position** on `inventory_balance_bin` (quantity only) and on detail rows; cost/commitments are
never bin-scoped. Balance updates are computed per posting plan as `delta` maps, deduplicated by key,
sorted deterministically, applied with `INSERT … ON CONFLICT DO UPDATE` under rank-3 locks; every row
records `last_ledger_sequence` (monotonic, never decreases — DM-LED-05) and `last_posting_at`.
Reads are snapshot-isolated; no in-memory caches. `qty_available` is generated and cannot be written
(DM-LED-06); `serial_id IS NOT NULL` positions hold at most 1 unit (`ck_balance_serial`).

### 5.12 Commitments, reservations and allocations

- **Commit model (C-01):** one active commitment per `(source_type, source_line_ref)`; commitments are
  created from external order-boundary commands or internal TO/WO demand. Fields as DATA-MODEL §7.
  A commitment stores `qty_committed` (promised), `qty_fulfilled` (issued), `qty_backordered`
  (unfillable). `status`: `ACTIVE → PARTIALLY_FULFILLED → FULFILLED` or `RELEASED`.
- **Eligibility:** status must be committable (`DM-TRACE-03`); stock must not be underwater
  (`iri-216`); ownership must match (owned demand cannot consume consigned positions and vice
  versa); location must be in the caller’s data scope; only quantities in statuses with
  `is_available_for_allocation=true` count toward available unless the location’s
  `allow_commit_from_non_available=true` and the status is committable (FS-03 §5.2).
- **Allocation (optional bin/lot/serial reservations):** rows in `inventory_commitment_allocation`;
  a serial can be reserved by at most one live commitment (`uq_alloc_serial` partial); Σ allocation
  qty ≤ commitment qty (`INV-06`); allocations reference live positions (position exists in balances).
- **Release (C-02):** full or partial; release sets `released_at` on allocations and decrements
  `qty_committed`; the row becomes `RELEASED` at zero. Never deletes rows (DM-LED-07). Idempotent by
  `(commitment_id, idempotency key)`/`(source ref, release request)`.
- **Reallocation (C-03):** deterministic order `(priority, required_by_date, committed_at, source_line_ref)`;
  moves availability between commitments of the same `(item, location)` without going negative; if
  infeasible, leaves the set unchanged and returns `409 INSUFFICIENT_AVAILABLE`; audited.
- **Fulfilment (T-12):** consumes on-hand, increments `qty_fulfilled`; `limit_to_committed=true`
  rejects quantities above the active commitment; when on-hand is insufficient, the difference is
  recorded as `qty_backordered` (never negative availability) and the external order is informed via
  the response and the `inventory.fulfilled` payload (`backordered_qty`) exported through the `order.supply@0.1.0` envelope.
- **Auto-commit schedule:** `ledger.commit_orders.schedule` (cron, `inventory.commit.order=SCHEDULE`)
  processes pending order-boundary commit requests in `required_by_date` order [iri-265]; `MANUAL`
  disables it; `AUTO_COMMIT` commits on inbound command acceptance.
- Invariants: `INV-04` availability never negative; `INV-06` Σ allocations ≤ commitment; `INV-07`
  balance committed = Σ active commitment qty; `INV-27` owned/consigned never mixed.

### 5.13 Transfers: one-step (T-09) and transfer orders (T-10/T-11 + C-04/C-05)

**One-step transfer** (`inventory_transfer`, state machine §5.22): document header from/to locations,
per-line item/uom/qty/bins/lot/serials/status/ownership. Posting (T-09) writes a movement pair
`−q` source key / `+q` destination key in one transaction, value-neutral (FS-05 `value_move`); target
location must differ from source; bins/status lot/serial must match quantities; source availability
checked under rank-3 lock. No in-transit state and no document-level commitment; used for
basic transfers [iri-232] and for inventory replenishment/withdrawal [iri-244..247] where the caller
creates a one-step transfer.

**Transfer order** (`transfer_order` + lines) — multi-step flow [iri-233..241]:

| Phase | Action | Ledger / command | State / quantities | Events |
|---|---|---|---|---|
| Create/submit | draft lines, approval routing (declarative approvals via FS-00) | none | `status=DRAFT→PENDING_APPROVAL` | — |
| Approve | C-04 | no ledger rows; creates source `inventory_commitment` (`source_type=TRANSFER_ORDER`, required_by_date) and raises destination `qty_on_order` projection | `status=APPROVED`; line `qty_committed` | `to.approved` |
| Fulfil | T-10 | `−q` source ON_HAND, `+q` destination IN_TRANSIT at source cost; per line `qty_fulfilled += q`, `qty_in_transit += q`; `inventory_in_transit` row upsert | `APPROVED→PARTIALLY_FULFILLED→FULFILLED` | `to.fulfilled`, `inventory.in_transit.changed` |
| Receive | T-11 | `−q` IN_TRANSIT at destination, `+q` destination ON_HAND (bin/status/lot/serial); `qty_received += q`; `inventory_in_transit` decrement; value in-transit → on-hand | `FULFILLED→PARTIALLY_RECEIVED→RECEIVED` | `to.received` |
| Close | C-05 | no ledger rows; `qty_closed` fills shortfalls; releases residual commitments + destination on-order | `RECEIVED→CLOSED`; short close allowed from `APPROVED` with reason | `to.closed` |
| Cancel | — | allowed only before any posting; after posting requires reversal of T-10/T-11 transactions first (`409 DEPENDENT_DOCUMENTS`) | `CANCELLED` | — |

In-transit rules: `transfer_order.in_transit_ownership` (`SOURCE/DESTINATION`) selects which legal
entity owns goods in transit and determines the eventual journal intent dimension (finance boundary;
no intercompany posting in Phase 1). `qty_in_transit = qty_fulfilled − qty_received` enforced by
trigger; `inventory_in_transit` must agree (`DM-LED-08`, `INV-05`). Quantities are base UoM; partial
fulfilment/receipt per line is supported; serial/lot detail must match qty on both legs.
`POST /v1/transfer-orders/{id}/fulfil` and `/receive` accept staging quantities and are idempotent per
call; a call that stages 0 qty is rejected.

### 5.14 Adjustments (T-07) and absolute worksheets (T-08)

- **Incremental adjustment** (`inventory_adjustment`): signed `qty_delta` per line (+/−), reason code
  required (`ADJUSTMENT`/`SCRAP`/etc.), `adjustment_source` provenance. Numbered (lot/serial) items
  **must** use this incremental form [iri-220]; after posting, the ledger has signed movements only
  (no absolute rewrite). Document state machine §5.22; approval required when
  `inventory.adjustment.require_approval=true` (default true for values above tenant threshold via
  FS-00 approval definitions).
- **Absolute worksheet** (`inventory_worksheet`): lines carry `system_qty` (snapshot at line
  lock/snapshot date) and `new_qty` (absolute target); `variance_qty` is generated. At posting the
  engine recomputes `system_qty` from the locked balance and posts `Δ = new_qty − system_qty` as
  T-08; if the re-read snapshot differs beyond `inventory.worksheet.snapshot_tolerance` (default
  `0.000000000001`) the posting fails `409 WORKSHEET_SNAPSHOT_DRIFT` and the document returns to
  `APPROVED` for a refresh. `new_qty >= 0` per line.
- **Documented prohibitions (T-08, D6):** worksheets are rejected for lot/serial-numbered items
  [iri-220], group-average items [iri-064], and consigned items [iri-323]; those paths route to
  incremental adjustment (T-07) / consigned adjustment (T-23) with
  `422 POLICY_VIOLATION` (`PROHIBITED_WORKSHEET_ITEM`). Consigned/group-average checks use item flags
  (FS-01), location group membership (FS-05), and ownership.
- Both document types support `DRAFT→PENDING_APPROVAL→APPROVED→POSTED→REVERSED` and
  `DRAFT→VOID`; `posted_transaction_id` unique; no editing after posting; corrections via reversal or
  a new corrective document (never delete).

### 5.15 UNALLOCATED bootstrap and inventory distribution command

The distribution command API is `POST /v1/inventory/distributions` (owned and implemented here; FS-03
provides the sentinel + `validate_distribution_target` hook, §FS-03 5.5):

```jsonc
// Request (Idempotency-Key required; auth scope inventory.distribution.create/post)
{
  "distribution_mode": "SIMPLE",           // SIMPLE: 100% to one target per item; MANUAL: split
  "bootstrap_mode": true,
  "transaction_date": "2026-10-21",
  "memo": "bootstrap",
  "lines": [
    {"line_number": 1, "item_id": "uuid", "to_location_id": "uuid",
     "inventory_status_id": "uuid", "bin_id": null, "lot_id": null, "serial_id": null,
     "qty": "10.000000000000", "unit_cost": "8.500000000000"}
  ]
}
// Response 201: distribution document + (after /post) posting result
{"id":"uuid","status":"APPROVED","distribution_mode":"SIMPLE","bootstrap_mode":true,
 "posted_transaction_id":"uuid","warnings":[]}
```

Rules: source is always the sentinel location (`location_id` resolved as `is_unallocated=true`; the
request cannot name a source); only one active (DRAFT/APPROVED) distribution per tenant; only while
`bootstrap_state.distribution_completed=false`; negative inventory must already be resolved
(`409 POLICY_VIOLATION` if any negative position remains); SIMPLE has exactly one positive line per
item; MANUAL splits sum ≤ sentinel on-hand (re-checked under lock); target locations active,
non-sentinel, bins/statuses consistent (FS-03 hook); approval per tenant setting
(`inventory.distribution.require_approval`, default true); posting is a value-neutral movement pair
from sentinel to targets using the T-09 template with `movement_type='BOOTSTRAP_DISTRIBUTION'` and
`source_doc_type='INVENTORY_DISTRIBUTION'` (see §14 resolved gap: DATA-MODEL §18 defines no distinct
DISTRIBUTION transaction code, so the T-09 twin-movement template is reused; the event distinguishes
the operation). After posting, `INV-08`: no `inventory_balance` row may reference the sentinel and no
non-bootstrap posting may use it; `GET /v1/traceability/bootstrap` reports
`distribution_completed=true`. Reversal allowed only before any subsequent posting references the
moved stock (otherwise `409 DEPENDENT_DOCUMENTS`); reversal returns stock to the sentinel and requires
`bootstrap_mode` still allowed.

### 5.16 Imports and batches (T-31, `EXT` import tooling)

- **Types** (`import_batch.import_type`): `OPENING_BALANCE` (bootstrap stock into the sentinel; requires
  `options.bootstrap_mode=true` and that distribution has not completed), `ADJUSTMENT` (rows post as
  T-07 incremental adjustments), `COUNT` (rows are accepted as count-reference data for FS-07, not
  posted here), `ITEM`/`PRICE` (validated and routed to FS-01/FS-02 as reference data; no ledger),
  `OPENING_SERIAL` (pre-FS-06 serial references validated later; accepted only when FS-06 available —
  before FS-06 the batch validates and parks rows with `409 DEPENDENCY_NOT_DEPLOYED`).
- **Lifecycle:** `UPLOADED → VALIDATING → VALIDATED → POSTING → POSTED | PARTIAL | FAILED`
  (DM-GLOBAL-08/§19). `VALIDATING→FAILED` = parser/tenant-level error (nothing posted);
  `POSTING→PARTIAL` = some rows failed; `PARTIAL→POSTING` = retry of failed rows only
  (DM-LED-10, R-09).
- **Validation:** parse CSV/NDJSON from object storage (`storage_key`), per-row schema/type checks,
  dimensions complete and resolvable (item/location/status/bin/lot/serial/UoM/reason), UoM conversion
  exact, duplicate row detection, opening-balance rows only while bootstrap is open. Invalid rows
  persist `error_code`/`error_detail`; the batch can still post valid rows (partial success).
- **Posting:** `ledger.import.process` job (queue `default`, singleton per tenant) processes rows in
  `options.chunk_size` chunks (default 500) by item range; each row group becomes **one independent
  idempotent posting command** (posting key `import:<batch>:<row>`), committed per chunk with a durable
  cursor in `job_run.cursor` and a committed row-count so restarts resume (C-08). Per-row failures never
  roll back posted rows; the batch is `PARTIAL` with counts. `options.recalculate` enqueues FS-05
  recalculation per affected item/date when rows are backdated or opening stock needs cost history.
- **Concurrency/bounds:** max rows per batch `inventory.import.max_rows` (default 100 000); chunk
  commits; no cost lock held across a whole file; duplicate batch key = no-op (idempotent batch).
- **API:** `POST /v1/imports` (create/upload reference; `Idempotency-Key`), `GET /v1/imports`,
  `GET /v1/imports/{id}`, `GET /v1/imports/{id}/rows` (cursor, error filter),
  `POST /v1/imports/{id}/validate`, `POST /v1/imports/{id}/post`, `POST /v1/imports/{id}/retry`
  (retry failed rows only). Batches are never deleted; retention purges raw rows per policy after
  posting (audited).

### 5.17 External order boundary implementation (D3, `order.demand@0.1.0` consumer)

The order-management domain is external; this set implements the *inventory side* of the v0 contract
(FS-00 publishes schemas + test doubles; no SO/customer tables or FKs):

| Inbound command (external order system → FS-04) | Endpoint | Inventory effect | Response / idempotency |
|---|---|---|---|
| `commit` | `POST /v1/inventory/commitments` | C-01; optional bin/lot/serial allocations | 201 `{commitment_id, qty_committed, qty_backordered}`; `Idempotency-Key` required; same key replays |
| `release` | `POST /v1/inventory/commitments/{id}/release` | C-02 (full/partial by qty) | 200 commitment state; idempotent |
| `reallocate` | `POST /v1/inventory/commitments/reallocate` | C-03 for an item/location scope | 200 summary `{moved:[...]}`; idempotent per request key |
| `fulfill` | `POST /v1/fulfillments` | T-12 (or T-14 for kit/group lines); commitment fulfilment/backorder; optional immutable price snapshot from FS-02 (pass-through metadata only; the ledger stores no sell-side price columns — see §5.17 provider boundary and §14) | 201 `{transaction_id, fulfilled_qty, backordered_qty}` |
| `return_receipt` | `POST /v1/returns` | T-13 into return status/location; original cost when traceable | 201 `{transaction_id}` |
| read | `GET /v1/inventory/commitments`, `GET /v1/inventory/availability` | none | 200 |

`external_ref` fields are opaque strings; no FK/customer PII. Error mapping: insufficient/underwater/
status → `409` with the domain code and the external refs so the order system can re-plan. Outbound
events implement `order.supply@0.1.0` **as an outbound envelope/schema over the existing inventory
events** (FS-00 contract surface: `inventory.committed.changed`, `inventory.fulfilled`,
`inventory.returned` — there are no separate `order.supply.*` event-type names in the v1 taxonomy).
The envelope adds `external_ref`/`external_line_ref`, `backordered_qty` and `transaction_id` mapping
fields. The contract is preview (`@0`): breaking change requires a version bump +
`who-depends-on --contract order.supply`. Fulfillment/return commands are also the only path for
external demand to cause T-12/T-13; no SO document is stored.

**Provider boundary — sell-side prices (FIX-B, for FS-02 to cite):** inventory ledger lines carry
inventory valuation/unit cost only (`unit_cost`, `value_base`, `value_txn`, `currency_code`,
`exchange_rate`). They do **not** carry sell-side `unit_price`/`price_source`/`price_rule_id`/
`snapshot_hash` values, and `inventory_ledger` has no such columns (DATA-MODEL §7 defines none; this FS
adds no schema change). Sell-side price resolution and snapshot generation are owned by FS-02
`pricing.engine@1.0.0` (`prices.resolve` → `prices.build_snapshot`); the **external order boundary**
persists the snapshot on its order line. FS-04 accepts an immutable `price_snapshot` object on
commitment/fulfilment/return payloads only as **pass-through metadata** for external order
response/event mapping (and, if finance needs it, intent dimension metadata) — it never persists it in
ledger columns and never re-resolves prices (DM-PRICE-04). FS-02's DM-PRICE-01 "document line snapshot"
requirement therefore applies to order/document lines owned by the order boundary, not to ledger lines.

### 5.17.1 Generic internal posting command (`POST /v1/inventory-transactions`)

Provider surface for consumer contexts (FS-07/08/09/11/12/13) and internal service/test harnesses that
must post an inventory transaction whose source document is owned by another context. It is the HTTP
projection of `PostingPort.post(PostingCommand)` and executes the **same** §5.5 17-step algorithm
(validation, locks, idempotency, outbox events, audit, finance intents, document state update). It does
not bypass approvals/state machines: when `source_doc_type/source_doc_id` names a consumer-owned
document, that document must be in a postable state and its `posted_transaction_id` is set in the same
transaction (DM-LED-12).

Request (`GenericPostingRequest`; decimals as strings; `posting_at` never client-supplied):

```jsonc

Idempotency-Key: posting:<source_doc_type>:<source_doc_id>:<revision>
{
  "transaction_type": "T-20",              // one of the allowed T-xx codes (§5.17.1 matrix)
  "transaction_date": "2026-10-21",
  "source_doc_type": "INVENTORY_COUNT",
  "source_doc_id": "uuid",
  "external_ref": null,
  "currency_code": "USD",
  "exchange_rate": "1.000000000000",
  "memo": "count variance",
  "lines": [
    {"line_ref": "1",
     "item_id": "uuid", "location_id": "uuid",
     "to_location_id": null,               // required for transfer-style types (T-09/T-10/T-11)
     "inventory_status_id": "uuid",
     "to_inventory_status_id": null,       // required for status-change type (T-30)
     "ownership": "OWNED", "qty_class": "ON_HAND",
     "bin_id": null, "to_bin_id": null,    // bin pair for T-29; required when item/location bins enabled
     "lot_id": null, "serial_ids": [],     // numbered items (validated by FS-06 once deployed)
     "uom_id": "uuid", "qty": "2.000000000000",

     "cost_object_ref": null,              // optional pre-resolved pointer (DMX-20); FS-05 validates
     "reason_code_id": null,

```

Response `201` (replay returns the identical body):

```jsonc
{"transaction_id":"uuid","ledger_sequence":123456,"transaction_type":"COUNT_VARIANCE",
 "status":"POSTED","posting_at":"2026-10-21T16:05:00Z",
 "source_doc_type":"INVENTORY_COUNT","source_doc_id":"uuid",
 "total_qty_base":"2.000000000000","total_value_base":"21.000000000000",
 "event_ids":["uuid","uuid"],"warnings":[]}
```

Contract notes:
- Ledger transactions are identified by UUID + the per-tenant monotonic `ledger_sequence` (the
  posting number used by consumers and finance); the ledger header has no `document_number`
  (DATA-MODEL §7) — human document numbers belong to the source documents.
- `transaction_type` accepts the **30 movement codes** T-01..T-30 only. `T-31` is a batch wrapper and
  must use `POST /v1/imports`; C-01..C-06 are non-posting commands and use their typed endpoints;
  reversals use `POST /v1/inventory-transactions/{id}/reverse` (a generic reversal cannot be requested
  through this command).
- Callers send **unsigned, type-relative** line quantities; the engine applies the posting-type
  template (§5.3.1) to derive signed movements (receipt-style `+`, issue-style `−`, transfer-style
  twin pair using `to_*` fields, absolute worksheet `new_qty − system_qty`). Raw signed movement pairs
  are rejected (`422 VALIDATION_FAILED`).
- All §5.5 step 4/8 validations apply unchanged: item posting eligibility, FS-03 registry
  (`validate_posting_position`), UoM conversion, FS-05 `assert_postable` (D5), negative policy,
  availability, serial/lot guards, period/backdating, reason codes, approval prerequisites.
- Allowed posting types per consumer service (default deny; `403 POSTING_TYPE_NOT_PERMITTED_FOR_CONSUMER`):

| Consumer | Allowed `transaction_type` values | Notes |
|---|---|---|
| FS-04 own documents / order boundary / test harness | T-07,T-08,T-09,T-10,T-11,T-12,T-13,T-14,T-20,T-28,T-29,T-30 | typed endpoints are preferred in production; the generic route covers the external order boundary (T-12/T-13/T-14) and internal harnesses |
| FS-05 `costing.engine` | T-24,T-25,T-26,T-27 | value-only postings (qty 0); in-process callers use `PostingPort`, cross-process service calls may use this route |
| FS-06 `traceability.numbered` | T-07 | serial/lot creation via incremental adjustment only (identity validation stays FS-06-owned) |
| FS-07 `counts.engine` | T-20 (+T-07 for numbered incremental lines) | count variance posting; no T-13/T-14 (returns/kit fulfilment are order-boundary/FS-04 flows, not counts) |
| FS-08 `procurement.p2p` | T-01,T-02,T-03,T-04,T-05,T-06,T-28 | receipts/bills/credits/returns/drop-ship; each source document state machine stays FS-08-owned |
| FS-09 `manufacturing.execution` | T-15,T-16,T-17,T-18,T-19 | build/unbuild/WIP issue/completion/close |
| FS-11 `wms.execution` | T-29,T-30 (+T-12 for its fulfilment bridge) | task-completion postings; T-01 receipts remain FS-08-driven |

- RBAC: route requires the service-principal scope `inventory.transaction.post` **and** the per-type
  domain posting scope (`inventory.receipt.post` T-01/T-02/T-03/T-28; `inventory.adjustment.post`
  T-07/T-08/T-21/T-23; `inventory.count.post` T-20; `inventory.transfer.post` T-09/T-29/T-30;
  `inventory.fulfillment.post` T-12/T-14; `inventory.to.fulfil`/`inventory.to.receive` T-10/T-11;
  `costing.revaluation.post` T-24; `costing.cogs_adjustment.post` T-25;
  `costing.landed_cost.post` T-26/T-27). The route is **service/machine-only** (not granted to
  end-user roles by default); machine API keys carry only granted scopes; tenant RLS and data scopes
  apply as on every route.
- Idempotency: `Idempotency-Key` required (header, or body `idempotency_key`; if both differ →
  `422 VALIDATION_FAILED`). Key scope `(tenant, endpoint_id='inventory-transactions:post', key)`;
  fingerprint = canonical JSON of the full command; same fingerprint replays the stored 201
  (`transaction_id`, `ledger_sequence`, `event_ids` identical); different fingerprint
  `409 IDEMPOTENCY_KEY_REUSED`; concurrent in-flight `409/425` with retry hint; recommended derived key
  `posting:<source_doc_type>:<source_doc_id>:<revision>`. Second line of defence:
  `inventory_transaction.idempotency_key` unique + source-document `posted_transaction_id` unique
  (DM-GLOBAL-07).
- Error codes: §6.1 plus `403 SERVICE_SCOPE_REQUIRED`,
  `403 POSTING_TYPE_NOT_PERMITTED_FOR_CONSUMER`, `404 SOURCE_DOC_NOT_FOUND`,
  `422 UNSUPPORTED_GENERIC_POSTING_TYPE` (T-31/reversal/non-posting command on this route), plus all

  `POLICY_VIOLATION`, `DEPENDENT_DOCUMENTS`, `COSTING_*`; `422 VALIDATION_FAILED`,
  `INACTIVE_REFERENCE`, `BINS_NOT_ENABLED`, ...).
- Additive contract rule: this route/command model is **additive inside `inventory.ledger@1.0.0`** —
  no existing path/response/event changes, no manifest change, no consumer-impact list. Consumer
  fixtures: `app/tests/contracts/test_fs04_generic_posting_consumer_fixtures.py` (one fixture per
  consumer set: allowed-type success, forbidden-type `403`, idempotent replay, source-doc-state
  guard); they are published for FS-07/08/09/11/12/13 CI.

### 5.20 Reconciliation, replay and repair jobs

| Job | Schedule | Purpose | Repair policy |
|---|---|---|---|

| `ledger.reconcile_open_quantities` | nightly | Recompute PO open qty, WO remaining, TO in-transit, import cursors from postings/documents; compare projections (`qty_on_order`, `inventory_in_transit`) | read-model repair only; document state owned by its context (reports drift to FS-08/09) |

| `ledger.reconcile_in_transit` | nightly | `qty_in_transit = fulfilled − received` per TO line and agreement with in-transit balances (`INV-05`, DM-LED-08) | alert; no auto repair of document quantities |
| `ledger.partition.maintenance` | monthly | Create next monthly partitions (3 months ahead), move partitions older than retention-open window to `archive`, refresh stats/vacuum settings | safe/idempotent; audit |
| `ledger.negative_inventory.scan` | every 15 min | Detect negative/underwater positions, duration thresholds and alert events | read-only |

after a restore/PITR, `ledger.reconcile_balances --repair` recreates read models and the exit gate
stores the reconcile output as evidence (`INV-03/INV-10` joint with FS-05).

### 5.21 Business rules and invariants

Scoped DATA-MODEL rules implemented/enforced here (statuses and ordering follow DATA-MODEL §7/§20):

- `DM-LED-01` ledger header/line/detail append-only (privilege + trigger) — `INV-09`.
- `DM-LED-02` every line has either `qty_base<>0` or a value-only `movement_type`; both zero invalid.
- `DM-LED-03` `qty_class=IN_TRANSIT` lines reference a transfer order line; `ON_HAND` lines do not.
- `DM-LED-04` `ownership=CONSIGNED` requires consignment configuration; consigned/owned never share a
  balance row — `INV-27` (FS-13 configuration guard).
- `DM-LED-05` `inventory_balance` is the only mutable ledger model; `last_ledger_sequence` monotonic.
- `DM-LED-06` `qty_available` generated; direct writes impossible; committed only via commands.
- `DM-LED-07` commitments never deleted; terminal states preserve quantities.
- `DM-LED-08` `qty_in_transit = qty_fulfilled − qty_received` (trigger) agrees with
  `inventory_in_transit` (`INV-05`).
- `DM-LED-09` documents post at most once (`posted_transaction_id UNIQUE`); pre-posting void is a state
  change, post-posting requires reversal.
- `DM-LED-10` import row states immutable once POSTED; duplicate import key is a no-op; row failures do
  not roll back posted rows.
- `DM-LED-11` adjustments/count variances carry a reason code (or tenant default); the reason’s
  account ref is snapshotted into the intent.
- `DM-LED-12` no ledger row references a document that is not in a posted state; posting sets the
  document’s `posted_transaction_id` in the same transaction.

Additional testable rules owned by this spec:

- `RULE-04-01` One posting command = one DB transaction = one `inventory_transaction`; no partial
  posting is observable (`INV-01`, `INV-02`).
- `RULE-04-02` `ledger_sequence` is strictly increasing per tenant with no gaps within committed
  transactions that inserted a header; it never decreases and is unique (`uq_txn_ledger_sequence`).
- `RULE-04-03` For every posting: `Σ ON_HAND deltas + Σ IN_TRANSIT deltas = net external qty change`
  and pure moves sum to zero (`INV-01`); value conservation (`INV-02`) is asserted with FS-05 output.
- `RULE-04-04` `Σ detail.qty_base = line.qty_base` and `Σ detail.value_base = line.value_base` for
  every line (`INV-19`) — enforced by the engine and reconcile.
- `RULE-04-05` Idempotent posting: same key+fingerprint returns the same `transaction_id`; different
  fingerprint is rejected (`DM-PLAT-06`); a document can post at most once (`DM-GLOBAL-07`).
- `RULE-04-06` Lock discipline: ranks acquired in globally non-decreasing order; concurrent
  non-overlapping postings do not block each other; no deadlock escapes the retry budget (§5.6).
- `RULE-04-07` Negative-inventory policy mode is applied per transaction class, override is
  role-gated and audited; commitments are always rejected underwater (§5.10).
- `RULE-04-08` Backdated postings set `is_backdated` and enqueue recalculation for affected items; the
  ledger never silently rewrites history (ARCHITECTURE §2.6, FS-05).
- `RULE-04-09` Reversal is at most one per transaction, carries exact negated movements, is blocked by
  dependent documents, and is period-correct (§5.8).
- `RULE-04-10` Balances equal ledger at all times after commit and are reconciled nightly; on-hand may
  be negative only when policy allows, available never (`INV-03/04`).
- `RULE-04-11` `qty_on_order` is a projection from open supply documents and is never used by the
  posting engine to decide availability (`INV-07`).
- `RULE-04-12` The UNALLOCATED sentinel is used only by bootstrap-mode commands; after distribution no
  balance references it (`INV-08`).
- `RULE-04-13` Order-boundary commands are idempotent per external ref and their inventory events are
  exported through the `order.supply@0.1.0` envelope; no order/customer master data is stored (D3).
- `RULE-04-14` Every value posting emits balanced journal intent(s) via `platform.finance` (D2); the
  ledger transaction id is part of the intent provenance.
- `RULE-04-15` Tenant isolation: RLS + composite FKs; cross-tenant ids return 404 (`INV-25`,
  `DM-GLOBAL-01/10`).
- `RULE-04-16` State changes only via declared transitions (`INV-26`); posted documents immutable
  (`DM-GLOBAL-04`).

Invariants touched: `INV-01`..`INV-09`, `INV-13`/`INV-14` (with FS-05), `INV-17` (joint, no uncosted
line), `INV-19`, `INV-25`, `INV-26`, `INV-27` (joint), `DM-GLOBAL-01..10`, `DM-PLAT-04/06/07`,
`DM-LED-01..12`, `DM-TRACE-03`, `DM-TRACE-08` (status changes only through T-30).

## 12. Rollback

- Flag off `inventory.ledger.enabled` (immediate): posting writes return `409 DOMAIN_DISABLED`;
  ledger/balances/commitment reads stay available; dependants’ postings fail closed (their entries are
  blocked by the entry gate/flag checks).
- Redeploy the prior image; migrations are additive and N-1 compatible; no prod down-migration.
- Ledger rows are never deleted/updated; corrections are compensating postings (reversal) only.
- Balance read models are rebuildable from the ledger by `ledger.reconcile_balances --repair`; if a
  read-model defect is found, the repair is safe and idempotent.
- Imports: stop the `ledger.import.process` job, resume from cursor after fix; posted rows stand.
- Dependants automatically blocked by `check-env` while status ≠ verified.
- Emergency: if outbox/audit write path fails, stop posting endpoints (flag) and preserve ledger;
  never bypass step 14/15.
