## 1. Objective and source coverage

Deliver the procure-to-pay document context end-to-end: vendor master and configuration, item–vendor
pricing and contracts, requisitions/purchase requests/RFQ, blanket POs and releases, the PO lifecycle with
declarative approvals, receipts (partial, advanced-receiving, deferred-posting/ASN-ready), received-not-billed
accrual effects, landed-cost hooks, vendor bills with 3-way match/variances/approvals, vendor credits,
vendor returns and drop-ship/special-order links. All inventory and value effects post through the FS-04
`inventory.ledger` contract (T-01..T-06, T-28) and the FS-05 `costing.engine` contract; finance/GL,
payments, prepayments and payment runs are **external boundaries** (`FinancePort` journal intents only, D2).

## 2. Scope

**In scope (backend):**
- Vendor master: vendor number/name, category, currency, payment terms (text/reference data only),
  tax id / 1099-eligible flag (data only, no tax computation), credit limit (data only, no enforcement —
  finance boundary), default expense/payable account refs (opaque finance refs), embedded addresses/contact
  JSONB, inactive lifecycle, merge (audited data move), multiple vendors per item.
- Vendor configuration/pricing: vendor categories, item–vendor association (vendor item code, preferred
  vendor, purchase UoM, MOQ, lead time, currency), vendor price list with quantity breaks/effective dates.
- Requisitions / purchase requests / RFQ: document creation, submit, declarative approvals (FS-00),
  conversion to PO, bulk order processing hooks; RFQ open/close/award/convert.
- Purchase contracts and blanket POs: contract header/items with quantity/discount terms, releases that
  create standard POs, contracted-vs-used quantity guards.
- Purchase orders: STANDARD/BLANKET/DROP_SHIP/SPECIAL_ORDER types, line quantities (ordered/received/billed/
  returned/cancelled), approvals, status lifecycle, PO status/history APIs, line closing, cancellation/void,
  centralized purchasing at single-legal-entity level via buyer data scopes (see §14 conflict).
- Receiving: item receipts from POs, partial receipts, advanced-receiving semantics (bill never creates
  inventory, O-08), deferred posting (`PENDING_POSTING`, WMS/ASN-ready via `receipt_type=INBOUND_SHIPMENT`),
  receipt reversal, receipt exchange-rate preference, bill-from-receipt data path, expenses as document lines.
- Received-not-billed accounting: T-01 accrual intent, T-04 accrual reclass on bill, unbilled-receipt read
  API, `vendor_bill.amount_paid` read-only projection (0 under `NullFinanceAdapter`).
- Landed cost integration hook: receipt-time estimated landed cost flag/template application (T-27) and bill
  landed-cost lines applying actual cost (T-26) through FS-04 `PostingPort.post_estimated_landed_cost`/
  `post_landed_cost` (value computed by FS-05); allocations only against posted receipt lines; receipt create
  accepts `landed_cost_charges[]` so WMS/asn bridges pass charges without storing landed-cost rows (FS-11 C-14).
- Vendor bills: entry, submit/approve/cancel, 3-way matching against PO+receipt with tolerances and
  exception codes, variance rows and T-06 postings, duplicate-bill guard, validity of bill qty vs received
  qty, approval override with SoD; bills never re-cost received inventory (`DM-PROC-04`).
- Vendor credits: standalone/from bill/from return, apply to open bills, credit ≤ open bill/return.
- Vendor returns: authorization from PO/standalone/drop-ship data, approval, ship (T-03), credit link,
  line close, quantities authorized/shipped/credited.
- Drop-ship/special-order: external `order.demand` refs, `special_order_link` uniqueness per external line,
  T-28 value-only posting (no inventory movement), billed/fulfilled events.
- APIs/events/jobs, flags/settings, approvals, audit, RBAC scopes, idempotency, tenant isolation,
  additive migrations `0015/0016/0017`, deferred-FK closures (vendor refs from FS-01/FS-05).

**Out of scope / deferred:**
- GL/accounting (accounts, journals, period close, tax calculation/1099 filing), vendor payments,
  prepayments, payment runs, in-transit payments, payment approvals — `DEFERRED-INTEGRATION`; Phase 1
  persists `platform.finance_journal_intent` only (D2) and exposes no payment/prepayment resource.
- OneWorld/cross-subsidiary/centralized-purchasing consolidation, intercompany: deferred; single-entity
  buyer data-scope semantics only.
- Vendor-center portal, PO/bill/credit/voucher printing, Employee Center approval screens, dashboard
  (DEFERRED-UI); Bill Capture/email capture, EDI, SuiteProcurement trading-partner network
  (DEFERRED-INTEGRATION); SuiteFlow approval-workflow customisation (`D-23`: declarative approvals only).
- WMS `receiving_order`/putaway tasks (FS-11) and manufacturing outsourced operation execution (FS-09):
  consumed through contracts/events; FS-08 stays deployable without them.
- Landed-cost tables/documents (`costing.landed_cost*`) are FS-05-owned; FS-08 owns the P2P hook/flags only.

Business rules and invariants:

- `DM-PROC-01`: a PO has no accounting/inventory impact until receipt; PO status transitions
  PENDING_RECEIPT→PARTIALLY_RECEIVED→RECEIVED based on line quantities; blanket POs never post.
- `DM-PROC-02`: receipted qty cannot exceed ordered qty unless tenant `allow_over_receipt=true`; over-receipt
  is audited, flagged and must not silently inflate accrued value; PO line `qty_received` is the sum of posted
  receipt lines (allocated on receipt posting).
- `DM-PROC-03`: bill quantities are matched against receipts/PO lines; variances beyond tolerances create
  `vendor_bill_match` exceptions requiring an approved override (`EXCEPTION→OVERRIDDEN`).
- `DM-PROC-04`: a vendor bill never re-costs received inventory (documented receipt-cost basis); price
  differences post as variances/accrued-purchases adjustments (T-04/T-06), never as layer edits.
- `DM-PROC-05`: deferred item receipt posting is `PENDING_POSTING`; posting transitions to POSTED; reversing
  a posted receipt is T-02 and requires no dependent, un-reversed bill/fulfilment (`R-04`).
- `DM-PROC-06`: blanket releases cannot exceed contracted/remaining quantities; each release links the created
  standard PO (`purchase_order_release.created_po_id`).
- `DM-PROC-07`: vendor return authorization ≤ received and not yet returned; shipped ≤ authorized;
  credited ≤ shipped; credit reduces AP/accrual only (`DM-PROC-10` corrections via credit/reversal).
- `DM-PROC-08`: drop-ship/special-order lines require `external_sales_ref`; no inventory posting for
  drop-ship items (T-28 value-only); special-order follows its purchased/manufactured path; links unique per
  external line.
- `DM-PROC-09`: landed-cost bill lines must reference posted receipt lines and allocate per FS-05 (`INV-12`);
  estimated landed cost templates apply at receipt time (T-27, once per receipt line, reversal paired).
- `DM-PROC-10`: vendor bills/credits/returns are immutable after posting; cancel/void only from unposted
  states; corrections are credits/reversals.
- `DM-PROC-11`: vendor payments/prepayments/payment runs are **not in this context** (finance boundary);
  `vendor_bill.amount_paid` is a read-only projection (0 in Phase 1 with `NullFinanceAdapter`); no AP aging,
  no payment instruction resource.
- Additional testable rules:
  - `PROC-PO-OPEN`: for every PO line `open_for_receipt = qty_ordered − qty_received − qty_cancelled` and
    `open_for_billing = qty_received − qty_billed − qty_returned` (never negative); PO status derives from
    these quantities (invariant exit-gate `test_po_open_qty.py`).
  - `PROC-RECEIPT-ONCE`: a receipt posts at most once (`posted_transaction_id UNIQUE`, `DM-GLOBAL-07`);
    posting is idempotent by `Idempotency-Key` and by document state.
  - `PROC-BILL-DUP`: `(tenant, vendor, vendor_bill_number)` unique; a retry with the same key replays.
  - `PROC-BILL-VALUE`: receipt-matched bill posts qty 0 and never changes `inventory_transaction_line.qty_base`
    (value-only T-04); `INV-02` holds per posting.
  - `PROC-MATCH-EXCEPTION`: exception codes are stable strings (e.g. `QTY_BILLED_GT_RECEIVED`,
    `PRICE_DIFF_GT_TOL`, `FX_DIFF_GT_TOL`, `NO_RECEIPT`, `BILL_AFTER_CLOSE`) and are exposed on the bill and
    in `vendor_bill_match.exception_codes` (subset of documented 3-way match exception criteria [mpw-493]).
  - `PROC-ACCrual`: T-01 emits Dr Inventory Asset / Cr Accrued Purchases; T-04 clears accrual to AP; the
    received-not-billed report reconciles to outstanding accrual intents (finance-boundary read only).
  - `PROC-APPROVAL`: declarative approval definitions may require approval on requisition/request/RFQ
    award/contract/PO/return/credit/bill; SoD requester≠approver; approved documents re-enter approval when
    financially sensitive fields change; cancel from `PENDING_APPROVAL` follows DATA-MODEL §19 only.
  - `PROC-NUMBERED`: receipt/return lines for numbered items carry lot/serial details validated by FS-06
    (`TN*` SQLSTATEs mapped by FS-04); mismatch rejects the whole receipt `409 SERIAL_QTY_MISMATCH`.
  - `PROC-DATA`: tax/1099 fields are stored data only; no tax computation, no 1099 filing, no revenue
    recognition; credit-limit value is informational (no enforcement — finance boundary).
  - `PROC-EXPENSE`: expense lines reference an opaque `expense_account_ref` resolved through FS-00
    `FinancePort.get_account_ref`; no expense-category table is created (see §14 conflict).
  - `DM-GLOBAL-*`: tenant isolation (`INV-25`), append-only ledger (`INV-09`, via FS-04), unique posting
    (`DM-GLOBAL-07`), state machines only through declared transitions (`DM-GLOBAL-08`), migrations additive
    (`D-15`).

   resolution and open-qty model; PO status/history APIs; draft-only creation path for FS-10.

   special-order links; close deferred FS-05 FKs (`landed_cost.vendor_id`,
   `landed_cost_allocation.item_receipt_line_id`, `cost_variance.vendor_bill_line_id`).
6. Receipt posting pipeline: T-01 through FS-04 in-process `PostingPort.post_receipt` (lot/serial detail via
   FS-06), deferred-posting state, T-27 via `post_estimated_landed_cost` (+`landed_cost_charges[]` bridge),
   T-02 `reverse_receipt` guards; document-link bookkeeping.
7. Billing pipeline: 3-way matching + exception codes, T-04/T-06 via `post_vendor_bill`/`post_variance`
   (value-only, no re-cost), credit T-05 via `post_vendor_credit`, return T-03 via `post_vendor_return`,
   drop-ship T-28 via `post_drop_ship`; landed-cost T-26 via `post_landed_cost`; received-not-billed read model;
   approvals/SoD; finance intents asserted; FS-13 consignment bill creation joins the caller's transaction.
8. APIs + OpenAPI fragment + idempotency + `If-Match`; events/outbox; four jobs registered; contract tests
   (provider + consumer fixtures); integration + invariant suites; gate wiring and evidence.
9. Enable flags per tenant; run golden smoke: requisition→PO→partial receipts→bill match→credit→return→close.
