## 1. Objective and source coverage

Deliver the server-side execution layer of a NetSuite-style WMS: warehouse/process configuration, pick and putaway
strategy resolution, directed inbound receiving and putaway tasks, wave release + pick/pack/ship task execution, WMS
bin replenishment and directed inventory-status tasks — all as backend task/queue resources whose completions post
through the lower-layer contracts (never through WMS tables). A future mobile client can be attached to these task
resources, but no device protocol/offline sync is built (D8). Carrier/EDI hand-off is a declared port with a null
adapter so shipment/manifest records are captured but no external call is made.

## 2. Scope

**In scope (backend):**
- Warehouse extensions of locations, item process families/groups/assignments, item stock locations/stocking rules,
  order types, UCC code formats, carrier service levels.
- Pick/putaway strategies + rules, WMS preferences, system rules + per-warehouse overrides, bin blocking.
- Inbound: inbound shipments (ASN records), receiving orders, receipt generation through the FS-08 procurement
  contract (including deferred posting PENDING_POSTING and reversal orchestration), landed-cost pass-through,
  staging-at-receiving, putaway task generation/assignment/completion, cart-putaway backend containers.
- Inventory processing: bin/location transfers (T-29 / T-09 via ledger contract), inventory search projections,
  "create inventory" adjustments (T-07), WMS replenishment plans/tasks (T-29), directed status-change tasks (T-30),
  WMS-triggered cycle-count requests delegated to FS-07.
- Work-order component picking (bridge to FS-09 build/completion), vendor-return picking (bridge to FS-08 T-03),
  transfer picking (bridge to FS-04 TO fulfilment T-10).
- Outbound: release-to-warehouse, wave creation, wave release schedules, idempotent pick-task decomposition,
  assignment/queueing, pick execution with partial/zero picks and backorder re-release, packing/cartons, shipments,
  manual shipping, customer-shipment confirmation, ship-manifest records.
- Task engine: task types, assignment/queue semantics, state machines, watchdog/recovery, no mobile endpoints.
- `warehouse_cart` / `device_session` backend records as `EXT` containers (D8; no device protocol/offline sync).
- Carrier/shipping boundary stub (`wms.ShippingPort` + null adapter): record manifests, make no carrier call (D4).

**Out of scope / deferred:**
- All mobile UI/device workflows, scanner protocols, offline sync, Smart Count app, SCM Mobile (D8/permanent exclusion).
- WMS shipping/carrier/EDI integration (rates, labels, ASN transmission, commodity shipment files), custom WMS
  print/label template rendering (D4 `DEFERRED-INTEGRATION`; boundary stub only, §5.6).
- WMS custom print/wave form templates beyond the `wave_release_schedule.filter` criteria JSONB (§14 conflict C-4).
- Analytics/reporting views (FS-15), workbooks, dashboards, Procurement/Manufacturing dashboards.
- Advanced Manufacturing SuiteApp extras, Work Instructions/Traveler, Manufacturing Scheduler admin.
- Screen/print automation for packing lists, pick tickets, warehouse labels (UI deferred; records/data are in scope).
- Any order-management domain: released-order demand arrives via `order.demand` stubs and opaque `source_ref`s (D3).

Business rules and invariants:

- `DM-WMS-01`: WMS tasks never change inventory by themselves; completion calls the ledger/owning-document contract in
  the same request and stores the resulting posting id (`*_task.posted_transaction_id`, `EXT` column §14 C-6).
- `DM-WMS-02`: a task has at most one active assignment; assignment history is audited; reassignment is audited.
- `DM-WMS-03`: suggested bin = highest-priority applicable strategy → item stock location → warehouse default
  receiving/pick bin; the resolved strategy/rule and suggested bin are stored on the task for reproducibility.
- `DM-WMS-04`: blocked bins cannot be assigned/suggested for picking; expired lots rejected at pick (`wms.task.exception`,
  no negative/expired pick). Consumed via FS-03 bin block state and FS-06 expiry projection.
- `DM-WMS-05`: `qty_picked ≤ qty_requested`; `qty_short = qty_requested − qty_picked`; zero/partial pick roll-up:
  all lines ZERO → task SHORT; mixed → PARTIAL; all PICKED → PICKED; re-release of unfilled lines supported.
- `DM-WMS-06`: deferred item-receipt posting: receiving may complete before the receipt posts; receipt moves to
  PENDING_POSTING through FS-08 and manual post/reversal use FS-08 receipt contracts; WMS stores only the receipt ref.
- `DM-WMS-07`: wave release generates pick tasks exactly once per wave line (unique key §4); deleting/voiding a wave
  cancels only not-yet-started tasks.
- `DM-WMS-08`: shipment/manifest records are the record of truth for a future carrier/EDI integration; no carrier call
  is made in Phase 1; manifest payload/response are stored verbatim (JSONB).
- `DM-WMS-09`: replenishment tasks move stock via T-29; source bin stock ≥ qty; destination is the primary/item
  stocking bin; a plan may not generate tasks whose source is blocked.
- `DM-WMS-10`: cart/device sessions carry ids only (no PII beyond user id/client_info); 30-day retention enforced by job.
- Additive cross-set rules: `INV-01` (qty conservation of every bridge posting), `INV-04` (pick never drives available
  negative — enforced by FS-04 at post-lock revalidation; WMS re-checks availability before task completion),
  `INV-09` (append-only ledger), `INV-18` (serial counts match detail), `INV-25` (tenant isolation on every route),
  `INV-26`/DM-GLOBAL-08 (state machines only through declared transitions), `DM-GLOBAL-01/02` (composite FKs, no upward
  coupling), `DM-GLOBAL-06` (no deferred FK orphans), `DM-GLOBAL-07` (single posting per document).
- `WMS-RULE-01` (pick decomposition): a pick task line may reference only one `suggested_bin_id`; multi-bin splits
  become separate lines with the same source ref.
- `WMS-RULE-02` (cart container): `is_cart_putaway=true` requires a `cart_id` in OPEN/IN_USE state and adds the task to
  the cart's task set; closing a non-empty cart is rejected.
- `WMS-RULE-03` (shipment completeness): a shipment may not be confirmed SHIPPED while a linked pick task is not in a
  terminal state (PICKED/SHORT/PARTIAL/CANCELLED) or a pack carton is OPEN.
- `WMS-RULE-04` (wave completeness): a wave may complete only when every wave_line is PICKED/SHIPPED/CANCELLED and all
  generated tasks are terminal; else `409 WAVE_INCOMPLETE` listing blocking tasks.
- `WMS-RULE-05` (idempotent task actions): every mutating task action is idempotent; replaying a completion with the
  same `Idempotency-Key` returns the original posting id and never double-posts (FS-04 guards enforce this too).
- `WMS-RULE-06` (no device protocol): no endpoint accepts scan payloads/offline cursors; `device_session` only records
  session containers (D8) and is gated to `wms.admin` scope with internal-only routes.

State machines (task engine + documents; from DATA-MODEL §19):

- `inbound_shipment`: `DRAFT → IN_TRANSIT → ARRIVED → RECEIVING → RECEIVED`; `DRAFT|IN_TRANSIT → CANCELLED`.
  Guards: transitions recorded in code transition tables; cancel only before receiving starts.
- `receiving_order`: `CREATED → IN_PROGRESS → COMPLETED`; `CREATED → CANCELLED`. COMPLETED requires either a POSTED or
  PENDING_POSTING `item_receipt_id` (DM-WMS-06).
- `putaway_task` / `replenishment_task` / `status_change_task`: `PENDING → ASSIGNED → IN_PROGRESS → COMPLETED`;
  `PENDING|ASSIGNED|IN_PROGRESS → EXCEPTION|CANCELLED`; COMPLETED requires `posted_transaction_id` NOT NULL
  (DM-WMS-01). No reopening; corrections are new tasks/compensating postings.
- `pick_task`: `PENDING → ASSIGNED → IN_PROGRESS → PICKED|SHORT|PARTIAL`; `PENDING|ASSIGNED|IN_PROGRESS → CANCELLED`;
  `PICKED|SHORT|PARTIAL → REVERSED` only before the shipment is SHIPPED; line-level PENDING→PICKED/PARTIAL/ZERO must
  roll up to the task status per DM-WMS-05.
- `wave`: `CREATED → RELEASED → IN_PROGRESS → COMPLETED`; `CREATED → CANCELLED`; completion guarded by WMS-RULE-04.
- `pack_task`: `PENDING → IN_PROGRESS → PACKED`; `→ CANCELLED`.
- `shipment`: `DRAFT → READY → SHIPPED → DELIVERED`; `DRAFT|READY → CANCELLED`; SHIPPED requires WMS-RULE-03.
- `ship_manifest`: `CREATED → SENT → CONFIRMED|ERROR`; with the null adapter manifests stay CREATED.
- `replenishment_plan`: `DRAFT → APPROVED → GENERATING → GENERATED → CLOSED`.
- `warehouse_cart`: `OPEN → IN_USE → CLOSED`; `device_session`: started → ended (not a document state machine).
- Side effects: every terminal transition writes `audit_event`, increments aggregate version, emits one outbox event
  (per aggregate ordering) and — for posting tasks — persists the bridge posting reference in the same transaction.

## 6. API surface

Base path `/api/v1`, JSON, UTC timestamps, quantities as decimal strings (`NUMERIC(38,12)`). Auth scope per endpoint
(scopes registered through the FS-00 permission catalogue). Errors use the platform envelope (`code`, `message`,
`details`, `correlation_id`). Every mutating POST requires `Idempotency-Key` unless marked otherwise; PATCH uses
`If-Match: <version>`. OpenAPI fragment: `contracts/openapi/FS-11.yaml`.

## 12. Rollback

- Redeploy the previous image; migrations are additive and N-1 compatible; no down-migration in prod.
- Set `wms.execution.enabled` off: blocks task/wave/shipment creation and completion (409 `DOMAIN_DISABLED`); existing
  tasks/waves/shipments stay readable as audit records; jobs disabled.
- Posted inventory movements are immutable; corrections are compensating postings (reversal via FS-04/FS-08/FS-09
  contracts); no WMS posting is ever deleted.
- Migrations additive/N-1 compatible; no prod down-migration (down tested only in CI/empty/seed DB).
- Data compensation for a bad task completion: create a new compensating task/bin transfer or reverse through the owning
  contract; in-flight waves may be cancelled (not-yet-started tasks) or completed forward.
- Dependants (FS-15) are automatically blocked by `check-env` while FS-11 status ≠ verified.
