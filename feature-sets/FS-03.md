## 1. Objective and source coverage

Deliver the dimension registry the inventory ledger cannot post without: the location/storage topology
(hierarchy, type, per-location feature flags, exactly one `UNALLOCATED` bootstrap sentinel), zones and
bins, and the inventory-status registry whose behaviour flags are the single source of
availability/commitment/sellability semantics. It also closes the deferred location/bin/status FKs
opened by FS-01 and publishes the synchronous resolution/validation contract that FS-04 (posting),
FS-05 (location costing groups), FS-10 (location network) and FS-11 (warehouse execution) consume.

## 2. Scope

**In scope (backend):**
- Location registry: code/name/type, self-referencing hierarchy, per-location flags
  (`is_bins_enabled`, `is_statuses_enabled`, `is_consignment_allowed`,
  `allow_commit_from_non_available`), timezone, opaque `subsidiary_ref`, address JSONB, soft
  inactivation; exactly one `UNALLOCATED` bootstrap sentinel per tenant.
- `zone` and `bin` registry: zone grouping, bin types, pickability, advisory capacity, coordinates,
  soft activation/inactivation; bins-enabled enforcement (location → bin → item rule hand-off).
- `inventory_status` registry: behaviour flags (`is_available_for_allocation`, `is_committable`,
  `is_sellable`, `is_consigned`, `is_default`, `is_system`, `is_active`), deterministic default-status
  resolution, seed statuses.
- Deferred-FK closure for FS-01: `item_master.item_location.location_id/bin_id/default_status_id`,
  `item_master.item_bin.location_id/bin_id`, `item_master.item_inventory.default_status_id`
  (additive migration + orphan backfill check, DM-GLOBAL-06).
- Registry contract for dependants: location/status resolution, effective bin requirement and
  default-bin resolution, descendant-location expansion for data scopes, posting-position validation,
  bootstrap state, and the **bootstrap-distribution validation hook** used by the FS-04 distribution
  command (the distribution document itself is FS-04-owned; see §5.8 boundary).
- Location/zone/bin/status lifecycle (activate/inactivate) and registry-reference integrity guards.
- Events, jobs, flags/tenant settings, seeds, OpenAPI fragment, tests and deploy gates.

**Out of scope / deferred:**
- The `inventory_distribution`/`inventory_distribution_line` document and `POST /v1/inventory/distributions`
  (FS-04 `inventory.ledger`; FS-03 only provides sentinel + validation contract).
- Inventory transactions, balances, commitments, availability quantities, lot/serial identity,
  transfer orders, adjustments, worksheets, imports (FS-04/FS-06).
- WMS topology layering: pick/putaway strategies, bin blocks, warehouse extensions, replenishment
  tasks (FS-11; `warehouse` is a location extension layered over `traceability.location`).
- Location costing groups and cost-group membership (FS-05 `costing.engine`; `item_location.cost_group_override_id`
  stays a deferred FK until FS-05).
- Subsidiary/OneWorld hierarchy and intercompany semantics (finance boundary, `subsidiary_ref` is opaque).
- UI, mobile (permanently excluded), analytics, integrations.

### 5.1 Location model and hierarchy rules

- `location_type` semantics: `WAREHOUSE`/`STORE` hold stock; `RECEIVING` is a receiving dock/target
  (may hold stock pending putaway); `TRANSIT` is a logical in-transit location for TO/in-transit
  reporting; `CONSUMPTION` is a production-consumption location (WIP issue targets, FS-09);
  `UNALLOCATED` is reserved for the bootstrap sentinel. Posting eligibility of a location type is
  decided by FS-04 from this flag + item type; FS-03 exposes the type as data (`ASSUMPTION`: the
  type list comes from DATA-MODEL §6; docs support locations/WMS/in-transit).
- Hierarchy: parent must be in the same tenant, must be a location, must not be the node itself or a
  descendant (recursive check in a `DEFERRABLE` trigger `trg_location_hierarchy_cycle` and again in
  service code). Depth limit default 10 (`inventory.storage.location_max_depth`) to bound recursive
  CTE cost. Reports roll up quantities by hierarchy (FS-15); roll-ups are read-only and never post.
- A location may change parent without changing identity; descendants move with it. Code is immutable
  after create (`ASSUMPTION`: code is the stable external reference; changing it would break imports).
- `UNALLOCATED` cannot have children, cannot be a parent, cannot be inactivated or re-parented, and
  cannot have bins/statuses disabled (status resolution must stay deterministic for legacy stock).
- `subsidiary_ref` is an opaque finance-boundary reference; FS-03 stores/validates format only and
  never enforces intercompany rules (out of scope).
- Location access restriction hooks: FS-00 `user_data_scope` rows with `scope_type=LOCATION` restrict
  reads/writes by role/user; `include_descendants=true` is resolved by
  `LocationResolver.expand_location_scope`. Posting into an out-of-scope location fails with
  `403 FORBIDDEN_SCOPE` at FS-04 step 1 (FS-04 owns the check; FS-03 supplies the hierarchy).
  WMS/role-specific location restrictions (e.g. warehouse operator limited to one warehouse) are
  expressed through the same hook; no separate ACL table in Phase 1.

### 5.2 Inventory-status semantics (flags are the single source of availability)

| Flag | Meaning (contract) | Enforced by | Rule |
|---|---|---|---|
| `is_available_for_allocation` | Quantities in this status count toward “available for allocation” in ATP/allocation/commitment eligibility (non-available stock is excluded) [iri-205, iri-211] | FS-04 commitments/fulfilment; FS-10 ATP/allocation reads | `RULE-03-05`, `DM-TRACE-03` |
| `is_committable` | Commitments may be placed against stock in this status; `false` ⇒ `409 STATUS_NOT_COMMITTABLE` [iri-211] | FS-04 C-01 | `RULE-03-06`, `DM-TRACE-03` |
| `is_sellable` | Stock in this status is eligible for sale/fulfilment; non-sellable statuses are excluded from sell-side availability and WMS pick recommendations [mpw-808] | FS-04 T-12 guard; FS-11 pick eligibility; FS-10 ATP | `RULE-03-07` |
| `is_consigned` | Status denotes vendor-consigned ownership; may only be used with `ownership=CONSIGNED` positions [iri-323] | FS-04 posting validation; FS-13 | `RULE-03-08`, `DM-LED-04` |
| `is_default` | Applied when a posting omits the status; exactly one non-consigned default per tenant | FS-04 default resolution | `RULE-03-09`, `DM-TRACE-03` |
| `is_system` | Seeded/structural status; cannot be deleted/inactivated; flags immutable except `is_sellable` | FS-03 service + DB trigger | `RULE-03-10` |
| `is_active` | Active statuses only for new postings; inactive statuses remain valid historically | FS-03 + FS-04 step 4 | `RULE-03-11` |

Flag-combination rules: `is_consigned=false` is required for the default status; `is_consigned=true`
implies `is_committable` may be true but never `is_default`; `is_committable=true` with
`is_available_for_allocation=false` is a valid *non-available but committable* configuration only when
tenant setting `inventory.storage.commit_non_available=true` (documented non-available inventory
settings, iri-205; `ASSUMPTION` — the precise NetSuite matrix is not fully documented, A-02). When
`is_committable=true` and `is_available_for_allocation=false`, commitments consume the location’s
`allow_commit_from_non_available` budget; FS-04 rejects when the location flag is false
(`409 POLICY_VIOLATION`). `allow_commit_from_non_available` is resolved per location and defaults
false.

### 5.3 Bins, zones and preferred/required-bin resolution

- Bins exist only under `location.is_bins_enabled=true` (DM-TRACE-02). A bin belongs to exactly one
  location and optionally one zone; zone must belong to the same location (trigger). Moving a bin
  between locations or changing its code is prohibited (physical identity; `ASSUMPTION`).
- The item-level requirement is: a bin is required for an item at a location when
  `item_master.item_inventory.use_bins=true` **and** `location.is_bins_enabled=true` **and**
  `item_inventory.bin_required_on_txn=true` (DM-ITEM-09); FS-03 returns this through
  `resolve_position_defaults` and FS-04 enforces it (step 4/8). If bins are enabled but not required,
  a bin may be omitted (position tracked per location/status).
- Preferred/default bins (consumed by WMS FS-11 putaway/pick strategies and by receipt defaults, not by
  the ledger key): `item_master.item_bin.is_preferred` (one per item+location),
  `is_default_receiving`, `is_default_picking`, and `item_master.item_location.default_bin_id` as the
  fallback. Resolution precedence: request-supplied bin → `is_default_receiving`/`is_default_picking`
  by movement direction → `item_location.default_bin_id` → none. Inactive bins never resolve as a
  default (`422 INACTIVE_REFERENCE`).
- Bin capacity (`capacity_qty`, `capacity_uom_id`) is **advisory** in Phase 1: FS-03 validates type and
  positive values, exposes it for WMS putaway strategies, but the posting engine does not hard-block
  on capacity (`ASSUMPTION`, not documented as a posting rule). Capacity enforcement, if enabled, is
  an FS-11 strategy concern.
- Disabling bins at a location (`is_bins_enabled: true → false`) requires no active bins
  (`422 BINS_IN_USE`) and no non-zero `inventory_balance_bin` rows for that location (FS-04 trigger
  guard, §5.4); historical detail rows stay valid [iri-258].

### 5.4 Lifecycle state machines

Master data has no drafts; it is created active or created and immediately inactivated (audited).

| Aggregate | States | Transitions and guards |
|---|---|---|
| `location` | ACTIVE, INACTIVE | ACTIVE→INACTIVE [`not is_unallocated`, no active children, no active bins, no non-zero balances (§5.4.1), reason required]; INACTIVE→ACTIVE [parent (if any) ACTIVE; no conflicting code] ; no DELETE ever. |
| `zone` | ACTIVE, INACTIVE | ACTIVE→INACTIVE [no guard; bins may keep the historical zone reference]; INACTIVE→ACTIVE [location ACTIVE]; no DELETE. |
| `bin` | ACTIVE, INACTIVE | ACTIVE→INACTIVE [no non-zero `inventory_balance_bin` for the bin (§5.4.1); no open WMS task references it — FS-11 enforces at its layer via bin-status read before task creation]; INACTIVE→ACTIVE [location ACTIVE and bins enabled]; no DELETE. |
| `inventory_status` | ACTIVE, INACTIVE | ACTIVE→INACTIVE [`not is_default`, `not is_system`, no non-zero balances in status (§5.4.1), no active document reference]; INACTIVE→ACTIVE [no flag conflicts]; no DELETE. |

#### 5.4.1 Stock-coupled inactivation guard (cross-FS migration contract)

`traceability` is a lower layer than `inventory_ledger` (ARCHITECTURE §1.4), so FS-03 cannot read
`inventory_ledger.inventory_balance*` and must not own a trigger that depends on FS-04 tables. The
balance-coupled half of the guard is therefore a **contract obligation on FS-04**, installed by its
migration `alembic:0008_ledger_core`:

- `trg_location_inactive_guard` on `traceability.location` (AFTER UPDATE OF is_inactive): if
  `is_inactive` flips to true and `EXISTS (SELECT 1 FROM inventory_ledger.inventory_balance b WHERE
  b.tenant_id=NEW.tenant_id AND b.location_id=NEW.id AND (b.qty_on_hand<>0 OR b.qty_committed<>0))`
  then raise `LOCATION_HAS_STOCK`.
- `trg_bin_inactive_guard` on `traceability.bin`: same shape against `inventory_balance_bin`.
- `trg_status_inactive_guard` on `traceability.inventory_status`: same shape against
  `inventory_balance`/`inventory_balance_lot`.

FS-03 exit-gate tests cover the static guards and assert (via a contract test double) that FS-04’s
migrations install these triggers; the FS-04 exit gate proves the trigger behaviour end-to-end. Until
FS-04 is deployed (FS-03 can be deployed and verified on its own in wave 0C order), the API-level
guard returns `200` with a `warnings[]` entry `BALANCE_GUARD_DEFERRED` when balances cannot be
checked — this keeps FS-03 independently deployable without lying about a check it cannot perform;
flag `inventory.storage.strict_inactivation=true` turns it into `409 LOCATION_HAS_STOCK_GUARD_UNAVAILABLE`
for tenants that require the guard from day one (`ASSUMPTION`).

### 5.5 UNALLOCATED sentinel, bootstrap and inventory distribution

- Exactly one row per tenant with `is_unallocated=true` and `location_type='UNALLOCATED'`
  (`DM-TRACE-01`, partial unique). The sentinel exists so the bootstrap import can park legacy stock
  before locations/distribution exist [iri-200..iri-202] (DMX-06). Identity columns (`code`,
  `location_type`, `is_unallocated`, `parent_id`, `is_bins_enabled`) are immutable via trigger.
- Bootstrap sequence (FS-04 implements the distribution document; FS-03 validates the target):
  1. tenant enables locations and creates its real locations (`location_type` from docs);
  2. opening balances are imported with `bootstrap_mode=true` into the sentinel position
     (FS-04 `import_batch` type `OPENING_BALANCE`, T-31);
  3. negative inventory is resolved **before** distribution (documented requirement, ARCHITECTURE §2.8);
  4. an `inventory_distribution` (FS-04) moves each item/qty from the sentinel to one target (SIMPLE)
     or split across targets (MANUAL) [iri-201, iri-202];
  5. `INV-08`: after the distribution completes, no balance may reference the sentinel and no posting
     may use it except bootstrap-mode commands.
- `LocationResolver.validate_distribution_target` is called by FS-04 inside the distribution posting
  transaction (step 4/8) and returns aggregated errors. Distribution command shape (contract reference;
  **endpoint and tables are owned by FS-04**, see manifest `inventory_distribution*` and
  `POST /v1/inventory/distributions`):

```jsonc
// POST /v1/inventory/distributions  (Idempotency-Key required; FS-04 implementation)
{
  "distribution_mode": "SIMPLE",            // SIMPLE | MANUAL
  "bootstrap_mode": true,
  "transaction_date": "2026-10-21",
  "lines": [                                 // source always UNALLOCATED
    {"item_id":"…","to_location_id":"…","inventory_status_id":"…","bin_id":null,
     "lot_id":null,"serial_id":null,"qty":"12.000000000000","unit_cost":"8.500000000000"}
  ]
}
```
  FS-03 side of the contract: sentinel present and not already consumed
  (`bootstrap_state.distribution_completed=false`), target locations active/non-sentinel,
  bins/statuses valid under target flags, SIMPLE has exactly one positive line per item, MANUAL line
  sums per item ≤ sentinel balance (FS-04 re-checks under lock). FS-04 emits
  `inventory.distributed` and the post-conditions are validated by `INV-08` in both exit gates.

### 5.6 Registry contract consumed by the posting engine

`validate_posting_position` is invoked from FS-04’s 17-step algorithm at step 4 (pre-lock static
validation) and re-run at step 8 for mutable registry facts (active flags, bin flags, status flags)
after locks are taken. Contract:

- Input: `{tenant_id, item_id, location_id, bin_id?, inventory_status_id?, ownership, lot_id?,
  serial_id?, qty_class, transaction_type, transaction_date}`.
- Output: `{ok, normalized: {location_id, inventory_status_id, bin_id, status_flags},
  errors: [{path, code, message}], warnings: []}`.
- Must not perform writes or take row locks (callers hold rank 3+ when re-validating); must be
  idempotent and side-effect free; errors are stable codes (see §5.7) and are surfaced by FS-04 as
  `422 VALIDATION_FAILED` (or specific 409 codes where the ledger maps them).
- Cached only per request; flag changes are visible to the next transaction (read committed).

### 5.7 Business rules (testable)

- `RULE-03-01` Exactly one `is_unallocated` location per tenant; it validates
  `location_type='UNALLOCATED'` (`DM-TRACE-01`).
- `RULE-03-02` Bins are creatable/activatable only for locations with `is_bins_enabled=true`; a bin’s
  zone belongs to the same location (`DM-TRACE-02`).
- `RULE-03-03` Location hierarchy is acyclic, tenant-local, depth ≤ configured maximum; the sentinel
  has no parent and no children.
- `RULE-03-04` Codes are unique and immutable: `(tenant, location.code)`, `(tenant, location, bin.code)`,
  `(tenant, location, zone.code)`, `(tenant, status.code)`.
- `RULE-03-05` A commitment to stock whose status has `is_available_for_allocation=false` is rejected
  unless location `allow_commit_from_non_available=true` and status `is_committable=true`; default
  outcome `409 STATUS_NOT_COMMITTABLE`/`POLICY_VIOLATION` (FS-04 enforcement, DM-TRACE-03).
- `RULE-03-06` A commitment against a status with `is_committable=false` always fails
  `409 STATUS_NOT_COMMITTABLE` (DM-TRACE-03).
- `RULE-03-07` Fulfilment/issue of stock in a status with `is_sellable=false` is rejected for
  sell-side transaction types (`FULFILLMENT`, `KIT_FULFILLMENT`, `TO_FULFILLMENT` out of a sellable
  location) unless the transaction is a transfer/adjustment/status move (`422 STATUS_NOT_SELLABLE`).
- `RULE-03-08` `ownership=CONSIGNED` positions require a status with `is_consigned=true`, the location
  flag `is_consignment_allowed=true`, and the item’s consignment eligibility (FS-13); consigned↔owned
  mixing in one position is impossible (DM-LED-04, INV-27 support).
- `RULE-03-09` Default-status resolution is deterministic: supplied → item-location → item →
  tenant default → `409 NO_DEFAULT_STATUS`; a consigned posting never falls back to the owned default.
- `RULE-03-10` System statuses cannot be inactivated; non-system status flag changes are rejected when
  non-zero balances exist in the status (`409 STATUS_IN_USE`).
- `RULE-03-11` Inactive registry rows cannot be used by new postings (`422 INACTIVE_REFERENCE`);
  historical detail/audit references remain valid.
- `RULE-03-12` Status flag combinations obey §5.2: default is non-consigned; `is_system` implies
  active; `is_committable=true` + `is_available_for_allocation=false` requires the tenant setting
  `inventory.storage.commit_non_available=true`; otherwise `422 VALIDATION_FAILED`.
- `RULE-03-13` Location/zone/bin/status inactivation is idempotent and audited; posted historical
  rows are never modified (`DM-GLOBAL-04`, append-only ledger unaffected).
- `RULE-03-14` All registry reads/writes are tenant-scoped by RLS + composite FKs; cross-tenant ids
  return `404` (`INV-25`, `DM-GLOBAL-01`, `DM-GLOBAL-10`).
- `RULE-03-15` Deferred FK closure: after `0007_traceability_registry`, every non-null
  `item_location.location_id/bin_id/default_status_id`, `item_bin.location_id/bin_id` and
  `item_inventory.default_status_id` validates against this tenant’s registry; orphan count = 0
  (`DM-GLOBAL-06`).
- `RULE-03-16` No posting or balance may use the sentinel after distribution (`INV-08`); the registry
  contract returns `422 UNALLOCATED_LOCATION_NOT_POSTABLE` when `allow_unallocated=false`.

Invariants owned or materially contributed by this set (cited again in §10): `DM-TRACE-01`,
`DM-TRACE-02`, `DM-TRACE-03`, `DM-TRACE-08` (status changes only via ledger T-30 — registry exposes
flags, FS-04 enforces), `DM-ITEM-09` (consumer hand-off), `DM-LED-04` (consignment configuration),
`INV-08` (joint with FS-04), `INV-25`, `INV-26`, `DM-GLOBAL-01..10`.

## 12. Rollback

- Flag off `inventory.storage_registry.enabled` (immediate): write routes return `409 DOMAIN_DISABLED`;
  reads and existing references stay valid; dependants’ postings that only read the registry continue
  (flag gates writes, not the contract).
- Redeploy the prior image; migrations are additive and N-1 compatible (old app tolerates new nullable
  columns/tables; new app tolerates the old schema for read paths only during rollout).
- No prod down-migration. Data compensation: master data is inactivated, never deleted; an incorrectly
  inactivated location/status is reactivated (audited) — the ledger remains untouched.
- Balance-guard triggers from FS-04 stay installed if FS-03 is rolled back (they only fire on registry
  UPDATEs and are harmless); they are removed by a later forward migration only.
- Dependants automatically blocked by `check-env` while status ≠ verified.
