## 1. Objective and source coverage

Deliver the physical/cycle-count backend: count plans and filters, calculated/manual/cycle count
creation, an immutable on-hand snapshot at count start (with a documented snapshot-recalculation path
on reject), batch line capture with blind-count semantics and tolerance/auto-approval policy, recount,
review/approve/reject with declarative approvals, and generation of the T-20 count-variance posting
through the FS-04 ledger contract plus costing valuation through FS-05. The backend exposes no mobile
or device workflow: line capture is an authenticated batch API usable by any client (D8).

## 2. Scope

**In scope (backend):**
- Count plan creation/scheduling: plan master (frequency, next run date, status), include/exclude scope
  filters (location/zone/bin/item/item-category/ABC/status), blind flag, approval-required flag,
  zero-qty inclusion; generate one count at a time from a plan.
- Calculated vs manual counts: manual counts created with explicit item/bin scope; calculated counts
  selected from item/ABC/interval calculation inputs; cycle counts generated from plans; zero-quantity
  positions included only when configured.
- Snapshot semantics at count start: immutable `inventory_count_snapshot` rows (qty, value, ledger
  sequence) captured at DRAFT→OPEN; later postings never change the snapshot; optional snapshot
  recalculation on reject creates a **new snapshot revision** linked by `recalculated_from_id`.
- Count line entry batch API: batch upsert of counted quantities per line/position (blind counts never
  expose snapshot/variance), no mobile-specific payloads; recounts append attempts.
- Review/approve/reject workflow with FS-00 declarative approvals (thresholds, SoD) and optional
  auto-approval within tenant tolerances (Smart Count backend semantics; `EXT`).
- Variance generation: exactly one T-20 `COUNT_VARIANCE` transaction per count (via FS-04
  `inventory.ledger` contract) whose per-line delta equals counted − snapshot and is valued per item
  method (FS-05); numbered lines routed through the documented incremental-adjustment form; consigned
  lines rejected with `409 PROHIBITED_COUNT_TYPE` (routed to the consigned path once FS-13 is deployed).
- Recount: append-only recount attempts and count rounds; rejected counts may be recounted and re-submitted.
- Next count date/interval per item: derived schedule query (plan frequency/tenant interval + last
  posted count), used by plan generation and exposed read-only.
- Jobs (cycle generation, snapshot refresh/derived-cache maintenance, stale cleanup), events, flags,
  RBAC scopes, tenant isolation, audit.

**Out of scope / deferred:**
- Any UI/workbench/dashboard/mobile/scanner workflow (Smart Count mobile `iri-403`, SCM Mobile excluded
  permanently, D8); device sessions are FS-11 `EXT` records, not used here.
- Smart Count SuiteApp packaging/roles/admin/saved searches (`iri-392..394, 396..402, 404..406` remain
  DEFERRED-SUITEAPP/MOBILE; only listed backend semantics above are `EXT`).
- Posting engine (FS-04), costing math (FS-05), lot/serial identity (FS-06), WMS task containers (FS-11),
  consigned ownership posting (FS-13), reporting presentation (FS-15).
- Count import tooling/UI (`import_batch` owned by FS-04; count import goes through FS-04's import contract
  with `import_type=COUNT`, not a new endpoint).

Business rules and invariants (cite DATA-MODEL/ARCHITECTURE ids):

- `DM-CNT-01`: snapshot rows are created at count start and never updated; "snapshot recalculation on reject"
  creates a new snapshot row linked by `recalculated_from_id`; the original revision is retained for audit.
- `DM-CNT-02`: approval leads to exactly **one** variance posting (T-20) per count, linked via
  `posted_transaction_id`; rejection generates none and releases the count. No double-post: a second post
  attempt returns the stored result via idempotency or `409 INVALID_STATE_TRANSITION`/`DOCUMENT_ALREADY_POSTED`.
- `DM-CNT-03`: a count line's variance equals counted − snapshot at approval time (`variance_qty` generated);
  subsequent stock movements do not alter an approved/posted count (immutability trigger).
- `DM-CNT-04`: blind counts never expose snapshot quantities or variances through the API until the count
  reaches PENDING_REVIEW/approved; batch capture responses return only line ids/status.
- `DM-CNT-05`: counts cannot include items/locations outside the caller's data scope; the same scope check
  applies at generation, capture, approval and posting (service principal calls carry an explicit scope token
  in the job payload).
- `DM-CNT-06`: variance postings respect prohibitions: numbered positions post one T-20 with full
  bin/lot/serial detail; where the documented "incremental adjustment form" is required for numbered lines
  the service creates a linked `inventory_adjustment` via FS-04 and sets `document_link`
  (`INVENTORY_ADJUSTMENT_FOR_COUNT`); group-average worksheets remain prohibited (FS-04 `DM-COST-09`);
  consigned positions never post through T-20 — `post` returns `409 PROHIBITED_COUNT_TYPE` with routing hint
  (consigned adjustment path is FS-13, deployed later; see §14 conflict).
- `DM-CNT-07`: recounts append rows; the accepted attempt is recorded on the line
  (`count_status=APPROVED`, `count_round`).
- `DM-LED-09` / `DM-GLOBAL-07`: count posting is at-most-once per document revision; `posted_transaction_id`
  is unique and set in the posting transaction; failures write no ledger rows (FS-04 atomic posting).
- `DM-GLOBAL-08` / `INV-26`: only declared state transitions succeed (`409 INVALID_STATE_TRANSITION`);
  posted counts are immutable except audit/status projection columns.
- `DM-PLAT-03` / FS-00 approvals: one active `approval_request` per count; requester≠approver (SoD);
  auto-approval uses a SYSTEM actor with an `approval_action` row and audit comment (`EXT`).
- Tolerance/auto-approval (`EXT`, Smart Count backend semantics): tolerances are tenant settings
  `counts.tolerance_qty` and `counts.tolerance_percent` (qty and value percent of snapshot value); a count is
  auto-approval-eligible only when the tenant enables `counts.auto_approve_within_tolerance`, every line's
  variance is within tolerance, and no line is a numbered/consigned routed line with a posting exception.
  Tolerance never suppresses the variance posting; it only skips human approval.
- Valuation: T-20 lines are valued by FS-05 inside the posting transaction like T-07/T-08 (`value_adjust`,
  standard/avg/group-aware); variance account resolution order: line reason account → count
  `variance_account_ref` → tenant default `counts.default_variance_account`.
- Numbered constraints: count line identity must exist and be a legal position (FS-06 `validate_count_position`);
  serial count line `counted_qty ∈ {0,1}`; a missing serial cannot be "counted in" without an explicit identity
  (line creation requires an existing serial or an `EXT` manual serial registration through FS-06); expired lots
  are still countable (counting is physical) but any resulting adjustment for an expired/FEFO lot follows
  FS-06 policy.
- Zero/negative: negative snapshot positions may be counted (counted qty ≥ 0); `include_zero_qty=false`
  omits zero-on-hand positions at generation.
- Snapshot consistency: line `snapshot_qty` must equal the latest snapshot revision row for that position at
  capture; a recalc replaces line snapshot values from the new revision only before posting.

State machines:

`inventory_count` (DATA-MODEL §19; this set owns the transitions):

| From | To | Guard | Side effects |
|---|---|---|---|
| DRAFT | OPEN | `start`; scope non-empty; feature flags; prerequisite flags (numbered/bin per item) | immutable snapshot revision captured; lines created |
| DRAFT | CANCELLED | cancel before start | no snapshot retention obligation beyond audit |
| OPEN | COUNTING | first `capture_lines` | line status update; `counted_at` audit |
| COUNTING | PENDING_REVIEW | `submit`; all lines counted or recount accepted | approval request created when required; tolerance evaluation |
| PENDING_REVIEW | APPROVED | `approve`; `approval_ok` (or SYSTEM auto-approval within tolerance) | approved_at/by; optional auto-post |
| PENDING_REVIEW | REJECTED | `reject` (reason) | optional snapshot recalculation revision |
| APPROVED | POSTED | `post_variance` (or auto-post) | T-20 txn + `posted_transaction_id`; events `count.approved`/`count.variance_posted` |
| REJECTED | OPEN | recount/restart action | recount round increments; rejected lines reopened as RECOUNT_REQUIRED |
| any unposted | CANCELLED | admin cancel | audit; no ledger rows |
| POSTED | REVERSED? | not allowed for counts — corrections are new counts/adjustments (`R-03`) | — (terminal) |

`count_plan`: `ACTIVE ⇄ PAUSED`, any → `ARCHIVED` only when no count is open; ARCHIVED plans generate nothing.

## 6. API surface

`inventory.adjusted` is emitted by FS-04 inside the T-20 posting transaction (never re-emitted by FS-07) and is
consumed by FS-05/FS-15; it is part of FS-04's contract, not of `counts.engine@1.0.0`.

| Job | Schedule | Purpose | Idempotent? | Failure handling |
|---|---|---|---|---|
| `counts.generate_cycle_counts` | daily (tenant timezone) | generates due counts from ACTIVE plans (`next_run_date <= today`), advances `next_run_date`, emits `count.generated` | yes (`run_key = cycle:<tenant>:<date>`; one count per plan per run, mpw-877) | retry/backoff, DLQ, alert; no partial plan state (transaction per plan) |

| `counts.stale.cleanup` | daily | cancels DRAFT counts older than `counts.draft_ttl_days`; raises alerts for stale OPEN/COUNTING counts; purges nothing posted | yes (dry-run mode supported) | retry/backoff; alert; never deletes posted rows |

## 9. Implementation steps (ordered)

1. Migration `0014_counts`: tables/constraints/indexes/generated variance column; immutability trigger; RBAC
   scopes; idempotent setting defaults.
2. Snapshot service: capture from FS-04 balances read contract with `snapshot_ledger_sequence`, revision chain
   (`recalculated_from_id`), immutability tests.
3. Count creation/generation: plan filter evaluation (includes/excludes, zero-qty), calculated scope resolution,
   derived next-count-date, one-count-per-generation rule.
4. Line capture/recount service: batch validation, blind-response shaping, serial/lot validation via FS-06
   `validate_count_position`, idempotent batch keys.
5. Review/approval workflow: state machine + FS-00 approvals (SoD, thresholds), tolerance auto-approval,
   reject + snapshot recalculation.
6. Variance posting: build T-20 posting plan → FS-04 in-process `PostingPort.post_count_variance` facade with
   idempotency key (numbered routed adjustments via `PostingPort.post_adjustment`); consigned prohibition; link
   transactions via `document_link`; valuation is FS-05-owned inside the posting (the FS-04 HTTP endpoints remain
   available to external clients but are not used for cross-module calls).
7. APIs + OpenAPI fragment + auth scopes + pagination; events/outbox; three jobs registered in `job_definition`.
8. Contract tests (provider + consumer fixtures FS-01/03/04/05/06), integration suite, gate wiring
   (`scripts/deploy_set.sh FS-07 $ENV`), evidence under `verification/evidence/FS-07/`.

## 12. Rollback

- Redeploy the previous image; migrations are additive and N-1 compatible; no down-migration in prod.
- Flag off `inventory.counts.enabled`: blocks count creation/capture/posting; snapshots, decisions and posted
  variance references stay readable for audit.
- Migrations additive/N-1 compatible; no down-migration in prod (down tested for dev/staging only).
- Data compensation: posted variances are corrected by compensating adjustments/new counts, never by deleting
  ledger rows or snapshots; rejected counts retain original snapshot revision.
- Dependants automatically blocked by `check-env` while status ≠ verified.
