## 1. Objective and source coverage

FS-02 delivers the complete backend pricing surface: price levels and multi-currency item prices with
quantity breaks, quantity-pricing schedules with the four documented calculation modes (LINE /
OVERALL_ITEM / PARENT / SCHEDULE) and marginal rates, pricing groups, advanced price rules with criteria,
actions, conflict resolution and dynamic item collections, coupons, mass price updates/level swaps,
purchase-price updates, effective-dated price updates with overlap handling (D4 `EXT`) and a deterministic
price-resolution API that returns an **authoritative priced quote** for sell-side consumers. The quote
(policy version + level + quantity break + currency + effective date + applied rules) is snapshotted by the
**external order-management system** on its side (D3/Δ-2); Phase 1 adds no ledger sell-side price columns
and no pricing snapshot table. It is independently valuable
because every sell-side document (quote, order, fulfilment, invoice — owned by the external order boundary)
needs a reproducible sell price without re-resolving history, and every other value-bearing set needs a
stable price contract at wave 0B.

## 2. Scope

**In scope (backend):**
- `price_level` CRUD (multi-currency; exactly one default per tenant), `item_group` / `customer_group`
  (+ members; customers are **opaque external refs** — D3), `pricing_group` mapping
  item_group × customer_group → price_level (+ optional default discount %).
- `item_price`: price per item/level/currency/quantity band with effective range; multi-currency rows;
  deterministic selection at a document date.
- `price_schedule` + breaks (DISCOUNT_PERCENT / DISCOUNT_AMOUNT / FIXED_PRICE), calculation modes
  LINE / OVERALL_ITEM / PARENT / SCHEDULE, marginal-rate semantics, assignment via
  `item_master.item_sales.quantity_pricing_schedule_id`.
- `price_rule` + criteria (CUSTOMER/CUSTOMER_GROUP/ITEM/ITEM_COLLECTION/ITEM_CATEGORY/QTY/DATE/CURRENCY,
  AND/OR groups) + actions (SET_PRICE_LEVEL/PERCENT_DISCOUNT/AMOUNT_DISCOUNT/PERCENT_MARKUP/AMOUNT_MARKUP/
  FIXED_PRICE/COST_PLUS with `cost_basis` and `apply_to`), priority + conflict policy
  (HIGHER_PRIORITY/FIRST_MATCH/STOP), effective dates, enable/disable.
- Dynamic `item_collection` (criteria JSONB) with materialised members and a recompute job; static collections.
- `coupon` (PERCENT/AMOUNT, item/item-category scope, date window, max uses) with **idempotent per-document
  redemption** and a validation endpoint.
- Advanced price-rule cost-plus: `COST_PLUS` actions and `item_price.cost_plus_basis` resolved through a
  `CostLookupPort` (item-master fallback in 0B; replaceable by `costing.engine` after FS-05).
- Effective-date pricing (`price_update` + `price_update_detail`; update types ITEM/ITEM_CATEGORY/CUSTOMER/
  CUSTOMER_GROUP): schedule → apply → revert lifecycle, overlap exclusion + SUPERSEDED handling (D4 `EXT`,
  documented semantics `iri-141..166`).
- Mass price updates, price-level swaps and purchase-price batch updates implemented as idempotent jobs.
- **Backend** price-list data generation (rows per level/currency/quantity band) — rendering/printing is
  DEFERRED-UI (`iri-034`); endpoint marked EXT per task requirement.
- Deterministic price-resolution service/API returning an authoritative `PricedQuote` payload + resolution
  trace (`policy_version`, `price_level_id`, `quantity_break`, `currency_code`, `effective_at`,
  `rules_applied[]`, optional `quote_hash`), including quantity-pricing math for all four modes; consumed
  through the `pricing.engine` contract by external order-management consumers (D3/Δ-2) and by any
  boundary-driven inventory command that needs a priced context. **FS-04 (ledger) stores inventory
  valuation/unit cost only — it does not persist sell-side price fields** (no price columns in
  DATA-MODEL; FS-04 spec states this). No pricing snapshot table is added in Phase 1.
- Currency handling: document-currency prices; base-currency fallback only when tenant setting
  `pricing.allow_base_currency_fallback=true` (DM-PRICE-05).

**Out of scope / deferred:**
- Customer master/customer records/PII — external boundary (D3); only `external_customer_ref` is stored.
- Documents, order lines and price-snapshot persistence — the external order-management system owns
  sell-side documents and snapshots the priced quote on its side (D3/Δ-2); the inventory ledger (FS-04)
  owns valuation/unit cost only and stores **no sell-side price fields**. FS-02 returns quotes; it never
  writes document or ledger tables and adds no pricing snapshot table (DM-PRICE-01/04 apply to sell-side
  documents at the boundary, not to `inventory_transaction_line`).
- Costing computation, average/FIFO/last-purchase cost, standard cost — FS-05. FS-02 reads a cost basis
  through `CostLookupPort` (item-master `initial_cost`/`purchase_price` fallback until FS-05 ships).
- Item/vendor purchase-price record (`item.purchasing.purchase_price` is FS-01-owned; `item_vendor_price`
  is FS-08-owned): FS-02 batch-updates call the FS-01 contract, never write foreign tables directly.
- Price list **printing/rendering**, pricing workbooks/datasets, Narrative Insights — DEFERRED-UI/ANALYTICS.
- CSV import of price updates (`iri-164`), Effective-Date-Pricing SuiteApp install/roles/browser, Advanced
  Pricing SuiteApp UI — DEFERRED-SUITEAPP/INTEGRATION.
- Tax, revenue recognition, discount/markup/subtotal *item* behaviour — FS-01 taxonomy + finance boundary.
- Promotions beyond coupons (e.g. buy-X-get-Y) — not in the cataloged pricing topics; not implemented.

### 4.2 Migration, seeds and deferred FK close

- **Migration** (must match `feature-sets.json`): `alembic:0006_pricing`. Additive only; down-migration
  tested; N-1 compatible. Creates all 17 `pricing.*` tables, indexes, constraints, range-exclusion
  constraint on `price_update`, overlap/band triggers, plus **closes FS-01 deferred FKs**:
  `item_master.item_sales.price_level_id → pricing.price_level`,
  `.quantity_pricing_schedule_id → pricing.price_schedule`, `.pricing_group_id → pricing.pricing_group`
  (all nullable columns created by FS-01 `0004`; FK + validation added here; orphan check in exit gate).
- **Seeds / reference data** (idempotent per tenant): `DATA-MODEL.md` §21.2 defines **no pricing seed**.
  This spec seeds exactly one row: a default `price_level` `DEFAULT` (`name='Default'`,
  `currency_code=<tenant base currency>`, `is_default=true`) so that item-based resolution and
  `item_sales.price_level_id` have a target on a fresh tenant — **ASSUMPTION** (§14.1 Q2; flagged as a
  DATA-MODEL seed gap). Job definitions for the six `pricing.*` jobs are seeded by this migration.
- **Deferred FKs / cross-context references:** `coupon.item_id`/`item_category_id`/`item_id` on detail →
  `item_master.item`/`item_category` (created here; FS-02 depends on FS-01); `item_price.item_id → item`;
  `price_update.*` → `price_level`/`item`/`item_category`/`customer_group`; `pricing_group → item_group/
  customer_group/price_level`; `currency_code` FKs → `platform.currency`; `customer_group_member.
  external_customer_ref` has **no FK** (external boundary); `price_rule_criteria.value_*` are scalar
  criteria, not references; coupon redemption links are `platform.document_link` rows (no local table).

## 5. Services, rules and invariants

Use cases (service method → behavior):

| Use case | Inputs | Behavior / validation | Emits |
|---|---|---|---|
| `price_levels.upsert` | code/name/currency/default/inactive | Currency must exist/active; one default (partial unique; setting a new default clears the old in the same tx); inactivate rejected while referenced by prices (409 `PRICE_LEVEL_IN_USE`); `pricing.price.updated` audit | `pricing.price.updated`, audit |
| `item_groups` / `customer_groups` / `pricing_groups` upsert + members | group payloads / external refs | Codes unique; external refs opaque (no PII validation); `customer_group_member` requires group exists; pricing group unique per item×customer group; resolution requires exactly one best match (default flag) | `pricing.price.updated`, audit |
| `item_prices.upsert` | item/level/currency/qty band/price/effective dates | Item must exist/active; level/currency exist; active + `qty_min` band checks; no overlapping qty bands for same item/level/currency (trigger+advisory lock); effective range must not overlap another **active** row for same band (trigger; latest `effective_from` wins only for historical rows) | `pricing.price.updated`, audit |
| `item_prices.bulk_upsert` | ≤5,000 rows or a `price_update` id | All-or-nothing validation per chunk; per-row results; creates/applies `price_update(update_type=ITEM)` with APPLIED status when prices are effective now | `pricing.price.updated` / `pricing.price_update.applied`, audit |
| `item_prices.swap_levels` (job) | level_a, level_b, filters (items/categories) | Atomic swap of `item_price` rows between two levels inside job transaction with `pg_advisory_xact_lock` per item set; dry-run returns diff; audit before/after; no effective-date changes | `pricing.price.updated`, audit |
| `purchase_prices.batch_update` (job) | item ids/categories, price, currency, effective_date | Calls FS-01 `item_master.apply_purchase_price_update` (contract); never writes `item_master` tables directly; per-item results; `item_purchasing.purchase_price` updated; audit | `pricing.price.updated`, audit |
| `price_schedules.upsert` | schedule + breaks | `calculation_mode` enum; `is_marginal` boolean; breaks non-overlapping, ordered by `qty_from`; value constraints per pricing method (percent 0–100; amount/fixed ≥0); schedule currency must exist | `pricing.price.updated`, audit |
| `price_rules.upsert` + criteria/actions | rule header, criteria rows, action row | Priority ≥0; dates valid; criteria operator/value type checked per criterion; collection/category/level refs exist; one action row; `COST_PLUS` needs `cost_basis`; advanced pricing flag on | `pricing.rule.changed`, audit |

### 5.1 Price resolution algorithm (normative, deterministic)

Inputs: tenant, `lines[]` (each `{line_ref, item_id, quantity, uom, parent_item_id?}`), optional
`external_customer_ref`, `customer_group_id`, `price_level_id`, `currency_code`, `document_date`,
`coupon_code`, `cost_context{unit_cost, cost_basis}`. All quantity and money values are decimal strings.

1. **Eligibility**: item exists and is active (422 `INACTIVE_REFERENCE`); currency exists (422
   `UNKNOWN_CURRENCY`); document date valid (`YYYY-MM-DD`).
2. **Quantity-pricing schedule selection** (per line, used later): item-level
   `item_sales.quantity_pricing_schedule_id`; mode from `price_schedule.calculation_mode`; matrix child
   may inherit the parent's schedule when `item_sales.matrix_parent_qty_behavior` says so.
3. **Base candidate** for each line (in order, first match wins):
   a. **Price rule** — active rules ordered by `(priority ASC, code ASC)`; a rule matches when its date
      window contains `document_date`, currency matches (or rule currency NULL = any), and its criteria
      groups evaluate true (same `group_no` AND; groups OR). Conflict policy: `FIRST_MATCH` = first
      matching rule wins and evaluation stops; `HIGHER_PRIORITY` = evaluate all matching rules and take
      the lowest priority number; `STOP` = first matching rule wins **and** no lower precedence level is
      consulted. Action applies: `SET_PRICE_LEVEL` switches the level for steps 3b–3d;
      `FIXED_PRICE` yields the unit price; `PERCENT_DISCOUNT`/`AMOUNT_DISCOUNT`/`PERCENT_MARKUP`/
      `AMOUNT_MARKUP` apply to the price resolved by steps 3b–3d; `COST_PLUS` = cost basis × (1 +
      value/100) (`apply_to=UNIT` only in Phase 1; LINE/TOTAL supported for discounts/markups).
   b. **Pricing group** — match item's pricing item group × customer's customer group → `price_level_id`
      (explicit request level wins over pricing group); `discount_percent` (if set) is applied to the
      level/base price.
   c. **Price level** — explicit `price_level_id` (request or rule action) else tenant default level.
   d. **Item base price** — `item_price` row for (item, level, currency) whose active quantity band
      contains the line quantity (or aggregated quantity for the mode) and `effective_from <= date <
      effective_to` (latest `effective_from` wins among matches).
   e. **None** — `unit_price=0`, `price_source=NONE`, `warning=NO_PRICE`.
4. **Currency fallback (DM-PRICE-05)**: if no row for the document currency and tenant setting
   `pricing.allow_base_currency_fallback=true`, use the base-currency row × `FinancePort.receive_rate`
   (direction base→document) with `fallback_used=true`; otherwise `409 PRICE_CURRENCY_MISSING`.
5. **Coupon** (when `coupon_code` supplied): validate; compute discount on the step-3 price:
   `PERCENT` → `discount = price × value/100`; `AMOUNT` → `discount = min(value, price × qty)`; result
   `unit_price = price − discount/qty` (12 dp, currency-minor-unit rounding for totals); set
   `price_source=COUPON`, `pre_coupon_source=<step 3 source>`, `coupon_code`. A coupon never overrides a
   `NONE` price with a negative amount (clamped at 0).
6. **Quantity pricing** (schedule present): apply the mode/marginal math of §5.2 on the step-5 prices for
   this resolution request; produce final per-line `unit_price`, `extended_price`, break id, mode,
   `quantity_basis`, discount amount.
7. **Priced quote**: build the canonical quote (`quote_hash`, `policy_version`, currency, effective date,
   `price_level_id`, `quantity_break`, `rules_applied[]`, sources, ids, trace). The quote is immutable and
   self-contained — the external order-management consumer snapshots it on its side; **no later
   re-resolution is allowed for a stored hash** (DM-PRICE-04 applies to the boundary document, not to
   `inventory_transaction_line`). Resolution is pure/read-only (no writes); FS-04 may call it only to obtain
   an optional priced context for boundary-driven inventory commands — it persists no sell-side price fields.

`PriceResolution` response (per line): `{line_ref,item_id,uom,quantity,unit_price,extended_price,
currency_code,price_source,pre_price_source?,price_level_id?,price_rule_id?,coupon_code?,schedule_id?,
quantity_break?,calculation_mode?,quantity_basis,marginal_applied,fallback_used,policy_version,quote_hash,trace[]}`.
All money/quantity as decimal strings; `trace[]` = ordered `{step, level|rule|group|base|coupon|schedule,
source_id, applied, reason}` for testability.

### 5.2 Quantity-pricing computation modes (DM-PRICE-02)

Definitions: a schedule has ordered breaks `[qty_from, qty_to)` with `pricing_method`/`value`.
`q` = quantity basis for the mode. `unit_base` = pre-schedule unit price for the line. Money rounds with
largest-remainder allocation to currency minor units (D-28/INV-13/14); unit prices are quantized to 12 dp.

| Mode | Quantity basis | Application |
|---|---|---|
| `LINE` | per-line quantity | Determine the break by that line's `q`; apply discount/markup/fixed price to that line only. |
| `OVERALL_ITEM` | Σ quantity of the same item across all lines in the request | Determine one break from the aggregate; compute the total discount/price effect; allocate it back to lines pro-rata by quantity with deterministic largest-remainder on money; each line's `quantity_basis` reports the aggregate. |
| `PARENT` | Σ quantity of all **sibling matrix children sharing `parent_item_id`** in the request | Identify the parent via `item_matrix_member`; use `item_sales.matrix_parent_qty_behavior` (`PARENT` = parent-quantity behaviour; `LINE`/`OVERALL`/`SCHEDULE` override the mode) to select the quantity basis; allocate to child lines pro-rata. |
| `SCHEDULE` | Σ quantity of all lines in the request that share the same `price_schedule_id` (cross-item) | Determine one break from the request-wide schedule quantity; apply to all lines referencing the schedule pro-rata by extended base amount; `quantity_basis` reports the schedule total. |

`is_marginal=true` (**marginal/tiered rate**): each break applies only to the quantity inside its band;
`amount = Σ_breaks min(max(q − qty_from, 0), band_size) × per_unit_value(pricing_method, unit_base)`, then
allocate/discount as above. `is_marginal=false` (**quantity discount**): the single matching break applies
its value to the entire basis quantity. The response always reports `marginal_applied` and the matched
break; golden fixtures pin both interpretations (§10).

### 5.3 Effective-date update materialisation (D4 `EXT`)

| update_type | Effective on apply | Revert |
|---|---|---|
| `ITEM` | New `item_price` rows (one per detail × qty band) with `effective_from/effective_to`; previous future rows for the same key/band become inactive (`is_active=false`, retained) | Deactivate generated rows; reactivate superseded future rows |
| `ITEM_CATEGORY` | Generated `price_rule` (`rule_type=FIXED_PRICE`/`SET_PRICE_LEVEL`, effective window) + `price_rule_criteria(ITEM_CATEGORY, IN, category ids)` + one action row per detail | Deactivate generated rule/actions |
| `CUSTOMER` / `CUSTOMER_GROUP` | Generated effective-dated `price_rule` with `CUSTOMER`/`CUSTOMER_GROUP` criteria and FIXED_PRICE/PERCENT_DISCOUNT action (item_price has no customer dimension — §14.1 Q4) | Deactivate generated rule |
| `PENDING → APPLIED` | Job `pricing.apply_effective_updates` at `effective_start`; manual `POST /api/v1/price-updates/{id}/apply` allowed only inside the window | `pricing.apply_effective_updates` also reverts at `effective_end` |
| `SUPERSEDED` | New overlapping PENDING/APPLIED update saved with `pricing.price_update.overlap_policy=SUPERSEDE` marks the earlier one SUPERSEDED in the same tx; it then never applies. Default policy `REJECT` → `409 PRICE_UPDATE_OVERLAP`. | — |

Business rules and invariants (DATA-MODEL ids + local ids):

- `DM-PRICE-01`: deterministic resolution order coupon → price rule (priority, conflict policy) →
  pricing group → price level → item base price → 0/NONE traceable; every document line stores
  `unit_price` + `price_source` + `price_rule_id` snapshot on the **sell-side document** at the external boundary (immutable); the inventory ledger stores valuation only.
- `DM-PRICE-02`: modes LINE/OVERALL_ITEM/PARENT/SCHEDULE and marginal rates implemented as documented
  [iri-027]; matrix parent quantity behaviour reads `item_sales.matrix_parent_qty_behavior`.
- `DM-PRICE-03`: effective-date updates cannot overlap for the same target+level+currency
  (`EXCLUDE USING gist`); applying writes new `item_price` rows with `effective_from` and supersedes
  previous future rows.
- `DM-PRICE-04`: historical document prices are never re-resolved; price changes affect only future
  resolution.
- `DM-PRICE-05`: multi-currency prices are stored per currency; resolution falls back to base × exchange
  rate only when `pricing.allow_base_currency_fallback=true`.
- `DM-PRICE-06`: coupons unique per tenant, cannot exceed `max_uses`/date range; usage increments are
  idempotent per document.
- `DM-PRICE-07`: customer entities are external; only `external_customer_ref` is stored (no customer PII).
- `RULE-PRICE-08`: an item belongs to at most one pricing item group in Phase 1 (422
  `ITEM_IN_MULTIPLE_PRICING_GROUPS`); pricing group resolution is deterministic.
- `RULE-PRICE-09`: price levels and item/customer groups are inactivated, never deleted; inactive
  references reject new resolution (`422 INACTIVE_REFERENCE`) but historical quotes/documents remain valid.
- `RULE-PRICE-10`: for the same `(item, price_level, currency, qty_min)` only one active effective range
  may contain a given date; all overlapping-active writes are rejected (`409 PRICE_OVERLAP`).
- `RULE-PRICE-11`: quantity bands for the same `(item, level, currency, effective range)` must not
  overlap and must not leave overlapping gaps; band `qty_min=0` is the default band; `qty_max=null` is
  open-ended and may coexist with no other band for the same key.
- `RULE-PRICE-12`: price selection ties (same effective_from) are broken by `created_at DESC, id DESC`
  (UUIDv7) and the chosen row id is recorded in the quote.
- `RULE-PRICE-13`: rule conflicts are deterministic: order `(priority ASC, code ASC)`; `HIGHER_PRIORITY`
  evaluates all matches; `FIRST_MATCH`/`STOP` stop at the first; `STOP` additionally suppresses lower
  precedence levels (pricing group/level/base) for that line.
- `RULE-PRICE-14`: rule criterion operators: `EQ`, `NE`, `IN`, `BETWEEN`, `GTE`, `LTE`; value column used
  must match the criterion type (text/number/date); malformed criteria are rejected at save
  (`422 INVALID_CRITERIA`).
- `RULE-PRICE-15`: cost-plus pricing requires a cost basis; resolution uses request `cost_context` when
  supplied, else `CostLookupPort` (default: `item_inventory.initial_cost`, then
  `item_purchasing.purchase_price`; absent → `409 COST_BASIS_UNAVAILABLE`; never estimates silently).
- `RULE-PRICE-16`: coupon redemption is idempotent per `(coupon, document)` via the unique
  `platform.document_link` row; `uses_count` is incremented in the same transaction and never exceeds
  `max_uses`; replayed posting returns the stored result.
- `RULE-PRICE-17`: coupon `uses_count` is a denormalisation of redemption links; the
  `pricing.reconcile` calculation in `pricing.coupon.expire` restores drift and reports it (audit + alert).
- `RULE-PRICE-18`: conversion/rounding: unit prices quantized to 12 dp; extended/line/total money rounded
  to currency minor units with largest-remainder allocation; no float arithmetic anywhere (D-10/D-28).
- `RULE-PRICE-19`: price resolution is read-only and has no side effects; only `redeem_coupon` and the
  `price_update` apply/revert flows write.
- `RULE-PRICE-20`: dynamic item collections are eventually consistent (recomputed by job); resolution
  uses materialised members and records whether the collection was stale beyond the max staleness.
- `RULE-PRICE-21`: `price_update` details must be complete before APPLY (all target items exist and
  active); partial application is never committed (single transaction per update).
- `RULE-PRICE-22`: mass updates and level swaps are jobs: each run is recorded in `job_run`, audited with
  before/after price summaries, and safe to retry (`run_key` + advisory lock).

State machines (FS-02 owns these; `DATA-MODEL.md` §19):

- `price_update`: `PENDING → APPLIED [effective_start reached, no overlap, details complete]`;
  `PENDING → CANCELLED [admin cancel]`; `PENDING|APPLIED → SUPERSEDED [overlap policy SUPERSEDE and a
  newer overlapping update saved]`; `APPLIED → REVERTED [effective_end reached / manual revert]`;
  terminal `CANCELLED/SUPERSEDED/REVERTED` immutable. Side effects: generated `item_price`/`price_rule`
  rows, events, audit, job cursor.
- `price_rule` / `price_level` / `item_group` / `customer_group` / `price_schedule` / `item_collection` /
  `coupon`: `ACTIVE ↔ INACTIVE` (master data inactivate only, never delete); coupon additionally expires
  naturally when `end_date` passes or `max_uses` is reached (computed on validate; no state stored).
- `coupon redemption` is not a state machine; it is an append-only set of `document_link` rows with a
  counter (RULE-PRICE-16).

  rows are deactivated and superseded rows restored.
- Redeploy prior image; migrations additive + N-1 compatible (no prod down-migration).
- Coupon counters are reconciled (not decremented) after rollback; redemption links remain append-only.
- Dependants blocked automatically by `check-env` while status ≠ verified.

### 14.2 Assumptions recorded

- Customers are external (D3): `external_customer_ref` is an opaque string; no customer PII, no FK.
- Resolution is a pure read; the external order system persists snapshots on its side; FS-02 never writes document/ledger tables and adds no pricing snapshot table.
- An item belongs to at most one pricing item group in Phase 1 (RULE-PRICE-08); multi-group pricing is
  not in the cataloged docs.
- `price_rule.rule_type` is a coarse classification; the action row drives behaviour. Exactly one action
  row per rule (Phase 1).
- Rule `currency_code` NULL means "applies to any currency"; a non-null rule only matches that currency.
- `PRICE_LEVEL`/`FIXED_PRICE` rule actions override the level/price for the line; discounts/markups cascade
  onto the level-resolved price, not on top of each other (one rule per line under FIRST_MATCH/STOP).
- Dynamic collections are eventually consistent (job); `subscription`/webhook refresh is not in scope.
- Customer groups are resolver inputs (D3 `CustomerGroupResolver`); the external order system resolves
  customer→group and passes `customer_group_id`/ref in the resolution request.
- Effective-date pricing remains flagged `EXT` (D4) with `pricing.price_update.enabled` default off.
