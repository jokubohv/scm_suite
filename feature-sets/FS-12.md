## 1. Objective and source coverage

Deliver the backend semantics of NetSuite Quality Management: versioned quality specifications with characteristic
lines, inspection plans with sampling, event/on-demand triggers and queues, inspection instances with result capture,
disposition/waiver, inventory holds/releases driven through the ledger status-change contract, and immutable
Certificates of Analysis. No inspection data is invented: receipts/fulfilments/work-order facts arrive from FS-08/09/04
events or API references; quality tables never post inventory directly (DM-QA-02).

## 2. Scope

**In scope (backend):**
- Quality specifications (versioned) + characteristic lines (numeric/text/pass-fail/choice, min/max, required,
  internal-only flag) and the documented 35-inspection-per-spec limit.
- Inspection plans (item or item-category scoped, inspection type, sampling method/size, trigger condition JSONB),
  plan lines and sample-size overrides, derived-field/statistical summary evaluation over result rows.
- Inspection triggers (receipt/work-order/fulfilment/adjustment/manual), frequency counters with scheduled reset,
  on-demand queues with assignment strategies (round-robin/least-open/manual).
- Inspections: creation from triggers or on-demand, lifecycle, result capture, disposition derivation
  (PASS/FAIL/WAIVED), waivers with approval action, cancellation, inspector assignment, queue membership.
- Quality hold/release: apply hold to stock positions by posting inventory status changes through `inventory.ledger`
  (T-30) and linking via `platform.document_link`; release reverses/compensates and is audited.
- COA: draft/issue/revoke, immutable after issue, lines from inspection results, lot-specific references, attachment
  reference, internal-only results excluded from supplier-facing COA data.
- Quality images via FS-00 `attachment_metadata` references on results/COA.
- Tenant preferences/parameters (hold status, auto-COA, default queue, derived-field config, notification recipients).
- Backend read surfaces other sets/dependants can rely on (`quality.management` contract) incl. inspection status.

**Out of scope / deferred:**
- Quality Management Connect / REST API for external vendors, vendor quality integrations (D4 `DEFERRED-INTEGRATION`).
- Quality mobile data collection/tablet UI (D8 `DEFERRED-MOBILE`); no offline/sample-collection endpoints.
- Reports/dashboards/analytics workbooks (FS-15 status view only), COA report rendering/printing.
- SuiteFlow-style custom workflows, SuiteApp install/roles/browsers help surfaces; the declarative approval hook
  from FS-00 is used for waivers/hold approvals.
- Non-Conformance Register (NCR) aggregate: the Quality Tab topic groups NCR screens, but DATA-MODEL §14 has no NCR
  tables; Phase 1 represents non-conformance by FAILED inspections + holds (§14 C-2). NCR/document workflows deferred.

Business rules and invariants:

- `DM-QA-01`: disposition derives from required results; WAIVED only with a recorded approval action; a FAILED
  inspection closes only through WAIVE or an inventory hold posting (acceptance §7.13).
- `DM-QA-02`: quality tables never post ledger rows; holds are applied by calling `inventory.ledger` T-30 status
  changes (no direct ledger access); the hold linkage is stored via `platform.document_link` (source_doc_type
  INSPECTION), which is the release/reconcile key.
- `DM-QA-03`: COA only for PASSED inspections; immutable after issue; revocation is a new status with audit.
- `DM-QA-04`: specs/plans versioned; ACTIVE specs immutable — changes create a new version; inspections store the
  spec version used (`inspection_plan_id` → plan → spec version at creation; snapshot copied into result_summary for
  reproducibility).
- `DM-QA-05`: trigger firing is idempotent per `(trigger, source_entity)` — enforced by the partial unique index and
  by consumer dedupe on `event_id`; replays never duplicate inspections.
- `DM-QA-06`: supplier-facing COA data excludes internal-only results (`quality_spec_line.is_internal`, EXT column);
  quality records respect item/location data scopes.
- `QA-RULE-01` (sampling): inspection sample size = plan `sample_size`, overridden per plan line if set; derived
  aggregates compute over recorded result rows; `SAMPLE_PERCENT` requires a positive percentage in
  `trigger_condition`/`sample_size` (validated).
- `QA-RULE-02` (COA eligibility): COA requires inspection PASSED and plan `sampling_method IN (FULL, SAMPLE_RANDOM)`
  — the model's mapping of the documented "Simple Sampling" requirement (iri-382); lot-controlled items require
  `inspection.lot_id` set and COA `lot_id = inspection.lot_id` (documented COA is lot/batch-specific).
- `QA-RULE-03` (frequency triggers): when `trigger_condition.frequency` is set (e.g. every Nth transaction or period),
  the trigger fires when `evaluation_counter` reaches the frequency; scheduled reset (`trigger.reset_counter` /
  job `quality.trigger.counter_reset`) resets counters per configured transaction type/item/location (iri-381).
- `QA-RULE-04` (hold scope): a hold position must exist in the current on-hand projection (FS-04 read) and have qty>0;
  held positions must use a status with `is_committable=false`; release restores the prior status (stored on the
  document_link metadata) or the tenant default.
- `QA-RULE-05` (queue assignment): ROUND_ROBIN cycles active inspectors; LEAST_OPEN assigns the inspector with fewest
  open inspections in the queue; MANUAL requires explicit `inspector_id`; unassignable queues keep items PENDING.
- `QA-RULE-06` (spec/plan scope): plan item OR item-category (XOR); trigger conditions may narrow by item/category/
  location/supplier ref; a trigger must target a plan or queue, not both-empty.
- Cross-set invariants: `INV-09` (append-only audit/ledger), `INV-25` (tenant isolation), `INV-26`/DM-GLOBAL-08
  (state machines only through declared transitions), `DM-GLOBAL-01..10`, `DM-QA-01..06`.

State machines:

- `quality_spec`: `DRAFT → ACTIVE → RETIRED`; new version = new row (`DRAFT → ACTIVE`, previous `ACTIVE →
  RETIRED` with effective_to); no edit of ACTIVE lines.
- `inspection`: `PENDING → IN_PROGRESS → PASSED|FAILED`; `FAILED → WAIVED [approved]`; `PENDING|IN_PROGRESS →
  CANCELLED`. Completion requires all required results; PASSED cannot be reopened (new inspection if needed).
- `coa`: `DRAFT → ISSUED → REVOKED`; `DRAFT → CANCELLED` (never issued); ISSUED rows immutable.
- `inspection_trigger`: active/inactive flag (not a document lifecycle); counter reset audited.
- Side effects: every lifecycle transition writes `audit_event` + outbox event (per aggregate ordering); hold/release
  transitions additionally link the FS-04 posting (T-30) in the same transaction and emit `inventory.status_changed`.

## 12. Rollback

- Redeploy the previous image; migrations are additive and N-1 compatible; no down-migration in prod.
- Flag off `quality.management.enabled`: blocks new inspections/triggers/COA writes and consumers; existing records
  stay readable; **holds already applied remain** (they are ledger status postings) and are not auto-released.
- Quality tables are append-style with immutable issued COAs; corrections are new versions/inspections/COA revocations,
  never edits/deletes.
- Migrations additive/N-1 compatible; no prod down-migration (down tested in CI).
- Holds must be released deliberately (inspection release or compensating T-30) before disabling quality for a tenant;
  document the operator runbook step.
- Dependants (FS-15) blocked by `check-env` until FS-12 verified.
