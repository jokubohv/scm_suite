## 1. Objective and source coverage

FS-01 delivers item identity and the NetSuite item-type taxonomy, type-specific extensions, the
units-of-measure conversion engine, item categories, kit/group composition, matrix parent/child items,
barcodes/aliases/related items, and per-item/per-location stock and planning attributes. It is
independently valuable because it is the master-data foundation every inventory document, price,
BOM and planning calculation references: without it no other 0B+ set can validate an item id, a UoM
conversion or a posting eligibility rule.

## 2. Scope

**In scope (backend):**
- Item CRUD by header fields + type-specific extension subtables; no hard delete (`inactive_at` only).
- Item-type taxonomy: 24 system types with `can_stock`, `requires_bom`, `requires_numbering`,
  `is_charge_only` flags and a code-level posting/document eligibility map (§4.3, §5 rules).
- Immutability-after-save: `item_type`, `base_uom_id`/`units_type_id`, `item_inventory.costing_method`,
  `stock_uom_id`, `initial_cost` (D-22 trigger) — survives raw SQL and import.
- UoM engine: `uom_type` + base unit, `uom` conversion factors, `uom_conversion` (units-type-level
  explicit overrides), `item_uom` roles STOCK/PURCHASE/SALE/CONSUMPTION/DEFAULT with per-item
  `conversion_override`; base-UoM normalisation to `NUMERIC(38,12)` with documented rounding; whole-base-unit guard.
- Item categories (tree) + many-to-many membership with one primary category.
- Kit/group composition (`kit_group_member`) with cycle/nesting rejection; assembly **BOM** membership
  is owned by FS-09 (build transactions owned by FS-09 — see out-of-scope).
- Matrix parent/child: option definitions/values, member mapping, child generation/link, combination cap.
- Barcodes (UPC/EAN/Code128/GS1), primary barcode, scanner resolution by barcode; WMS item aliases and
  alias resolution (`mpw-811`).
- Related items (RELATED/UPSELL/CROSS_SELL/SUBSTITUTE).
- Per-item stock/planning settings (`item_inventory`, `item_purchasing`, `item_sales`, `item_accounting`)
  and per-location settings (`item_location`, `item_bin`), including reorder point, preferred stock,
  safety stock, lead time, seasonal demand, preferred location, cost-group override columns.
- Item activation/inactivation lifecycle with referent guards; custom-field values validated through
  FS-00 EAV; deferred-FK readiness reporting (`item.reference.validate` job).
- Contract facade `item.master@1.0.0` for dependants: eligibility check, UoM conversion, item-location
  planning settings read, purchase-price update, reference validation, and item read DTOs.

**Out of scope / deferred:**
- Locations, zones, bins, inventory statuses (`traceability.location/zone/bin/inventory_status`) — FS-03
  owns them; FS-01 keeps `item_location`/`item_bin` with **nullable, unconstrained** location/bin columns
  (deferred FKs, DMX-19; closed by FS-03).
- Assembly/BOM definitions, routings, work-order/build transactions — FS-09. FS-01 owns that `ASSEMBLY`/
  `WIP`/`PHANTOM`/`OUTSOURCED` **types exist** and that assemblies can be kit-parent-like only for BOM
  hook-up; it does **not** create `bom_component` or build documents.
- Item prices, price levels, quantity schedules, price rules, coupons — FS-02. `item_sales` carries
  **nullable** pricing pointer columns (deferred FKs closed by FS-02 `0006_pricing`).
- Vendor master, item-vendor prices/contracts — FS-08. `item_purchasing.preferred_vendor_id` deferred FK.
- Costing methods/engine, location costing groups, standard cost — FS-05. FS-01 stores the chosen
  `costing_method` and `initial_cost` but computes no cost.
- Balances/availability quantities — FS-04. FS-01 exposes **settings**, not on-hand/available quantities.
- Customer part numbers, UPC auto-assign registry, warranty — FS-14 (customer master is external, D3).
- Lot/serial identities and numbering — FS-06; FS-01 only marks item types `requires_numbering`.
- WMS warehouse/process-family assignment and item stock locations — FS-11 (item alias data is here).
- Import tooling/Item Creation Assistant/CSV import, price lists, label printing, item lists/360 UI —
  DEFERRED-INTEGRATION/UI (feature-coverage deferrals).
- Item feature/display UI (web-store screens, featured-item pages) — UI deferred; the **backend data**
  for those topics is handled as described in §14.2 (custom fields + `is_sellable`).

### 4.3 Item type taxonomy seeds (24 documented types)

Flags per `DATA-MODEL.md` §4.3 seed row; values below are the Phase-1 seed proposal (`ASSUMPTION` where the

Business rules and invariants (DATA-MODEL ids + local ids):

- `DM-ITEM-01`: `item.item_type_id` immutable after save (trigger rejects raw SQL/import changes).
- `DM-ITEM-02`: `item_inventory.costing_method` immutable after save [iri-037]; `initial_cost` immutable after save (manifest acceptance; stricter than "first costed movement" wording — see §14.1 Q2).
- `DM-ITEM-03`: stockable item (`can_stock=true`) has exactly one `item_inventory` and exactly one
  `item_uom(role=STOCK)`; non-stockable items have neither; charge-only types have no `item_uom` rows.
- `DM-ITEM-04`: `item.base_uom_id` must be the base unit of `item.units_type_id`; every `item_uom` unit
  belongs to the same units type (`422 UOM_TYPE_MISMATCH`).
- `DM-ITEM-05`: a matrix child has exactly one `item_matrix_member` row and exactly one parent; matrix
  parent never stocks; parent/child types are consistent (`MATRIX_PARENT`/`MATRIX_CHILD` unless the
  parent is converted per §5 type-migration).
- `DM-ITEM-06`: kit/group parents have ≥1 `kit_group_member`; members are stockable and non-nested;
  cycles rejected by recursive check at save.
- `DM-ITEM-07`: `item_barcode.barcode` globally unique per tenant (scanner resolution deterministic).
- `DM-ITEM-08`: at least one `item_location` row for every active stockable item when multi-location is
  enabled; preferred location unique per item.
- `DM-ITEM-09`: bins must be enabled on the item and the location before `item_bin`/bin-required
  postings are allowed (`422 BINS_NOT_ENABLED`); until FS-03 deploys, bin columns stay nullable/no-FK.
- `DM-ITEM-10`: `allow_vendor_consignment=true` only for non-assembly types and when manufacturing is
  disabled per documented mutual exclusion [iri-323] (`ASSUMPTION`/O-10) — flag guard via FS-00 settings.
- `DM-ITEM-11`: planning quantities (`reorder_point`, `preferred_stock_level`, `safety_stock`,
  `lead_time_days`, `seasonal_demand`) are non-negative and in **stock units** [iri-073];
  auto-calculated values are written only by the replenishment job and only when
  `auto_calculate_planning=true` (FS-01 exposes/validates the columns; FS-10 writes them).
- `DM-ITEM-12`: inactivation only when no open commitments/open documents; historical references remain
  valid; new transactions on inactive items → `422 INACTIVE_REFERENCE` (enforced by dependants through
  `require_active_item`).
- `DM-ITEM-13`: custom-field values validate against `custom_field_def`; required fields block activation.
- `RULE-ITEM-14`: matrix combination cap 2000 [iri-120]; generation is atomic (all or none).
- `RULE-ITEM-15`: matrix option values in use by an existing child cannot be deactivated/removed.
- `RULE-ITEM-21` (FIX-1): planning values are written **only** through the published `item.master`
  contract (`apply_planning_values`) — no cross-module SQL writes (ARCHITECTURE §1.4 rules 2–3,
  DM-GLOBAL-02). `source=AIM` requires `auto_calculate_planning=true`; `source=MANUAL/OVERRIDE` is the
  explicit manual path; values are non-negative, in stock units and 12-dp decimal strings; write path is
  idempotent per key, optimistic-locked (`If-Match`), audited, and emits `item.planning_values.updated`.
- `RULE-ITEM-22`: `source`/`policy_version`/`effective_at` are **provenance metadata** echoed in the
  audit event and `item.planning_values.updated` payload; they are not stored as new FS-01 columns
  (the caller FS-10 persists `formula_version` on `replenishment_calculation_line`). This avoids a
  DATA-MODEL schema change while keeping DM-PLAN-07 traceable.
- `RULE-ITEM-16`: `item.upc_code` must equal the item's primary `UPC_A` barcode when one exists (or be
  NULL); both are unique per tenant and every update keeps them consistent. `item.upc_code` may also be
  set by the FS-14 UPC registry through `item.master.mirror_upc_code` (no barcode row required); when both
  exist they must match (`409 UPC_MISMATCH`).
- `RULE-ITEM-17`: drop-ship/special-order flags (`item_purchasing.is_drop_ship/is_special_order`) must match
  the item type (`DROP_SHIP`/`SPECIAL_ORDER`); other types cannot set both true (`422 TYPE_FLAG_MISMATCH`).
- `RULE-ITEM-18`: non-stockable types may carry sale/purchase/default `item_uom` rows but never STOCK;
  non-inventory types support limited unit sets (ARCHITECTURE §4.1) — DEFAULT required.
- `RULE-ITEM-19`: `item_number` is user-supplied, unique per tenant, mutable until first posted
  transaction (dependent sets reject renumbering of posted references; audit records before/after).
- `RULE-ITEM-20`: `kit_group_member.uom_id` must be a UoM of the member item; quantity stored in member
  stock units at posting time (conversion by FS-04).
- `UOM-01`: `qty_base = qty_uom × factor`; factor = base units per unit; factor > 0; base factor = 1
  (ARCHITECTURE §4.1).
- `UOM-02`: conversion goes through the units-type base only; no cross-type identity conversion
  (`422 UOM_TYPE_MISMATCH`).
- `UOM-03`: converted quantities quantize to 12 dp with ROUND_HALF_UP; never round before multiplying value.
- `UOM-04`: `must_be_whole_base_unit=true` rejects non-integral base quantities (`422 UOM_FRACTIONAL_BASE`).
- `UOM-05`: `uom_type.base_uom_id` must reference a `uom` of the same type with `is_base=true`.
- `UOM-06`: a `uom` cannot be deactivated while referenced by an active item; `uom_conversion`
  `from_uom_id`/`to_uom_id` must belong to `uom_type_id`.

State machines (FS-01 owns master-data lifecycles, not documents):

- `item` lifecycle: `ACTIVE → INACTIVE [inactivate guard passes]`; `INACTIVE → ACTIVE [reactivation checks:
  type unchanged, stockable subrecords present, required custom fields present]`; no `DELETED` state
  (DM-ITEM-12; DM-GLOBAL-08). Side effects: events + audit; dependants reject new references.
- `item_matrix_member`: created via `generate`/`link`; identity immutable after save; unlink only when the
  child has no documents/commitments (checked via referent validators); parent option-set changes that
  affect existing children are rejected.
- `uom_type`/`uom`/`item_category`: `ACTIVE ↔ INACTIVE` with reference guards; `is_system` rows cannot be
  deactivated.
- Type migration (`convert_to_inventory`) is a multi-step **workflow**, not a state change on the source
  item: new item created → references rewired by caller → source inactivated. Each step audited; partial
  failure leaves both items valid (idempotent retry by item numbers).

## 12. Rollback

- Flip `inventory.item_master.enabled` off: item writes stop; all item data remains readable to dependants
  (they continue resolving existing items); outbox events already published are not retracted.
- Redeploy prior image; migrations are additive + N-1 compatible (no prod down-migration).
- Forward-fix only: no hard deletes; bad items are inactivated; type mistakes use the type-migration
  workflow; audit rows record each repair.
- Dependants blocked automatically by `check-env` while status ≠ verified.

### 14.2 Assumptions recorded

- Item types are seeded per tenant and read-only via API; custom item-type creation is deferred (no
  posting-eligibility drift) — `ASSUMPTION`.
- `item.upc_code` and `item_barcode` coexist: the primary `UPC_A` barcode is the canonical source; the
  header field is a denormalised copy for legacy/import compatibility (RULE-ITEM-16).
- Categories are used by FS-02 price updates, FS-07 counts and FS-10 planning scopes; no category-level
  posting behaviour.
- Aliases are for WMS/warehouse alternate identifiers; they are not customer part numbers (FS-14 owns those)
  and carry no customer PII (D3 boundary).
- Kit/group members must be stockable (DM-ITEM-06); nested groups and phantom members are rejected in
  Phase 1 (`ASSUMPTION`; phantom explosion belongs to FS-09 BOMs).
- `item.related` association rows are the only item-master rows that may be hard-deleted (they are not
  master data and carry no history requirement); every delete is audited.
