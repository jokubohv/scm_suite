## 1. Objective and source coverage

Deliver the value side of every inventory posting: cost objects and methods (moving average, FIFO,
LIFO, group average, standard, specific, lot-numbered), append-only cost layers/consumption and cost
ledger, the asynchronous recalculation engine with the per-tenant block-vs-provisional policy (D5),
standard costing (categories/templates/versions/planned standards/rollup/revaluation and the six
documented variance families), System COGS adjustments and underwater handling, landed and estimated
landed cost allocation, location costing groups, and exact value reconciliation. It is invoked
**synchronously inside FS-04’s posting transaction** under the cost-object advisory lock, so no
posting is ever partially costed (INV-10/INV-17).

## 2. Scope

**In scope (backend):**
- Cost objects, current cost state (`item_cost`), cost methods (AVERAGE/FIFO/LIFO/GROUP_AVERAGE/STANDARD/
  SPECIFIC/LOT), cost-object key derivation and method dispatch; method immutability is enforced by
  FS-01 (`item_inventory.costing_method` trigger) and consumed here.
- Synchronous per-movement valuation API called by FS-04 step 9/13: `value_movement`, typed
  `value_inbound/outbound/move/adjust/build/unbuild/wip_issue/wip_completion/wip_close/return/
  ownership_transfer/reverse/value_revalue/value_cogs_adjust/value_landed_cost/value_dropship`, and
  `assert_postable` (D5 pre-post check).
- Append-only `cost_ledger_entry`, `cost_layer`/`cost_layer_consumption` layer engine with negative-
  position representation (no negative layers), layer consumption/replay for reversals.
- Recalculation engine: triggers, scope, async job with durable cursors, cost checkpoints, diffing,
  correction postings (T-25), rerun/idempotency, `cost_recalc` status (`PENDING_RECALC`), D5
  block-vs-provisional tenant policy.
- Standard costing: cost categories, inventory cost templates, cost versions, planned standards,
  multi-level rollup (including costed-BOM data), standard activation, revaluation (T-24) including
  caller-supplied per-WO WIP revaluation API (WIP scope owned by FS-09), and the six variance families.
- COGS adjustments/System COGS (T-25), underwater true-up, return-cost handling, rounding residuals.
- Landed cost (T-26) and estimated landed cost (T-27) documents, allocation bases and algorithms,
  standard-cost treatment, closed-period/period-shift intents, recalc enqueue.
- Location costing groups (group-average) and group balances.
- Cost read models/APIs (item costs, layers, valuation), cost reconciliation job, events, flags,
  seeds, OpenAPI/event schemas, tests and deploy gates.

**Out of scope / deferred:**
- Ledger transactions, balances, commitments, posting algorithm/locks/idempotency, documents other
  than cost documents (FS-04 owns them; FS-05 plugs in as the value engine and its T-24..T-27 postings
  run through FS-04’s `PostingPort`).
- Lot/serial identity tables and FEFO (FS-06; specific/lot cost identity columns are nullable deferred
  FKs until then).
- BOM/routing/work-centre/WO documents (owned by FS-09, a later-wave **consumer** of `costing.engine`;
  FS-05 never reads FS-09 tables — WIP-scope selection belongs to FS-09, which calls the FS-05
  revaluation API with its computed scope). FS-05 owns only valuation inputs/outputs.
- Procurement documents/bills/receipts (FS-08; landed-cost allocation links are deferred FKs).
- FX revaluation, GL/trial balance/period close, tax (finance boundary; intents only).
- Inventory Cost Accounting Workbook / reports presentation (analytics deferred; read models only).
- UI, mobile (permanently excluded), integrations, SuiteApp packaging.

### 5.1 Cost objects and key derivation

- **Cost object key** = `(tenant, item, cost_scope)` where `cost_scope`:
  - `location` for `AVERAGE`, `FIFO`, `LIFO`, `STANDARD` (per-location on-hand value);
  - `location_costing_group` for `GROUP_AVERAGE` (item cost state is per group; member locations share it);
  - plus `lot`/`serial` identity for `SPECIFIC` and `LOT` (one `item_cost` row per identity; a serial layer
    has `qty_original=1`, DM-COST-11).
  - `STANDARD` uses the effective `standard_cost` row for the item/category (no location column); the
    `item_cost` row per location exists to hold on-hand value = `qty × standard` and variances.
- Cost-object derivation is deterministic and shared by the ledger (`cost_object_id` denormalisation,
  DMX-20): `CostObjectResolver.resolve(item, location, lot, serial)` used by both FS-04 and FS-05; the
  pointer is written on the ledger line in FS-04 step 9 and validated by FK-less equality on read.
- `item_cost` is the authoritative running state; `cost_layer` is authoritative for FIFO/LIFO/specific
  remaining quantities; `cost_ledger_entry` is the append-only truth both are checked against
  (INV-10). `group_average_balance` mirrors the group cost object state for cross-location reads.
- Method changes are impossible: `item_inventory.costing_method` is immutable after save
  (DM-ITEM-02 / D-22); a different method requires a new item. Costing fails closed when the item has
  no method/cost configuration (`409 COSTING_INCOMPLETE`).

### 5.3 Value flow per movement and cost entries

Posting flow (inside FS-04 transaction): FS-04 passes each movement to `value_movement` →
cost strategy computes `{unit_cost, value_delta, layer_actions, estimated}` → FS-05 returns cost entries
(one per ledger line per movement type) and GL intents → FS-04 persists cost artefacts in step 13.

- **One cost entry per ledger line per movement/run** (`INV-17`): `cost_ledger_entry` with
  `movement_type` mapping: inbound → `IN`; outbound → `OUT`; adjustment → `ADJUST`; build/consumption →
  `IN/OUT` per line; transfer → `TRANSFER` (value moved, net 0 across pair); revaluation → `REVALUE`;
  landed cost → `LANDED`; variance → `VARIANCE`; COGS adjustment → `COGS_ADJUST`.
- **Value equation (`INV-10`)**: per cost object, `item_cost.value_base = Σ cost_ledger_entry.value_delta
  = Σ inventory_transaction_line.value_base` (per position); `qty_on_hand = Σ qty_delta`; reconcile
  proves it nightly. `cost_estimated=true` propagates from entries to ledger headers/API warnings.
- **Accounts/intents**: each movement supplies a posting-rule id (FS-04 §5.18 table) and account refs
  from FS-01 item accounting (asset/COGS/adjustment/variance/unbuild variance) or cost categories
  (labour/overhead/etc.); account refs are opaque finance-boundary strings.
- **Estimated values**: when no usable cost exists and the negative policy allows estimation, the
  entry is `estimated=true`, `unit_cost` = last purchase price or 0; the flag clears only when a
  true-up posts (§5.10).
- **Return policy (O-12):** traceable return (serial/lot or original line reference) restores original
  cost; otherwise current method cost; multi-location return costing rule applied per [iri-229]
  (location’s cost object). Tenant setting `costing.returns.costing_policy`
  (`ORIGINAL_WHEN_TRACEABLE` default, `CURRENT` alternative).

### 5.4 Cost layers and layer consumption (FIFO/LIFO/specific)

- Layer creation: receipts, positive adjustments, builds, returns-in; transfers do not create new
  valuation layers with new cost — for FIFO/LIFO the implementation closes the source layer and opens
  the destination layer with the same unit cost and `derived_from_layer_id` (ARCHITECTURE §3.3
  implementation choice); average/standard transfer value is carried as value, no layers.
- Consumption algorithm (normative, ARCHITECTURE §3.3): (1) order candidate layers by method
  (`(layer_date, layer_seq)` FIFO / reverse LIFO / identity for specific); (2) consume
  `min(require, qty_remaining)` per layer with `value = quantize(qty × unit_cost, 12)`; (3) if layers are
  exhausted and quantity remains: negative policy applies → estimated cost from last purchase price and
  `estimated=true`; else `409 INSUFFICIENT_ON_HAND`; (4) final partial consumption uses
  `value_remaining × (consume_qty / qty_remaining)` quantized, and a full consumption removes the exact
  remaining value (no residual); (5) append `cost_layer_consumption` rows (never update) and update
  `qty_remaining/value_remaining/status` on the layer.
- Layer invariants: `Σ consumption.qty + qty_remaining = qty_original`, same for value (`INV-11`);
  no negative `qty_remaining`/`value_remaining` (`INV-15`); `status=EXHAUSTED` iff remaining = 0;
  average/standard objects must not have OPEN layers (DM-COST-02); specific serial layers have
  `qty_original = 1` (DM-COST-11).
- Negative positions: layers are **never negative**; a negative qty state lives in `item_cost.qty_on_hand
  < 0` plus estimated `cost_ledger_entry` rows; replenishment true-up appends T-25 entries (§5.10).
- Reversal: `value_reverse` replays the original consumption trail; restore layer quantities by
  inserting compensating `cost_layer_consumption` rows (negative not allowed by schema → reversal
  creates new layer/adjustment representation documented in §14) and posts residual as cost
  adjustment if layers were consumed by later transactions.

|---|---|
| Triggers | (a) backdated cost-affecting posting; (b) reversal of a cost-affecting posting; (c) landed-cost application/adjustment; (d) standard cost change (revaluation per item/location/open WO); (e) correction of receipt cost; (f) import batch with `recalculate=true`; (g) manual admin request (audited). |
| Scope | `(tenant, item_id, cost_scope, from_date)`; only affected items; multi-item documents enqueue several item-scoped jobs (dedupe by scope). |
| Algorithm | (1) load last cost checkpoint at/before `from_date` (period-end snapshot; rebuilt from cost ledger if missing — `costing.checkpoint.build`); (2) stream `cost_ledger_entry`/ledger movements for the item ordered by `(transaction_date, ledger_sequence)`; (3) recompute expected unit cost/value movement per movement including layer consumption; (4) diff expected vs recorded; (5) append `cost_ledger_entry` correction rows (`cost_run_id`, `rounding_residual` where applicable) and T-25 `cogs_adjustment` postings grouped by cost object/period (period open guard; adjustments use `adjusts_period_id`); (6) update `item_cost`/layers to the recomputed state; (7) set `item_cost.status = CURRENT` or `REQUIRES_ATTENTION` (mapped to PENDING_RECALC/UNDERWATER) and emit completed event. |
| Concurrency | one run per `(tenant,item)` via advisory lock; chunked commits every N movements with durable cursor in `job_run.cursor`; postings for the same item during recalculation serialise on the cost-object lock; a posting that starts while a recalc is pending is **blocked** by default (D5) or marked `cost_provisional=true` when the tenant opted in. |
| Idempotency | `run_key = (tenant, item, from_date, ledger_high_watermark)`; re-run with same key is a no-op; newer watermark extends scope; the job is re-runnable after failure from cursor. |
| Bounds | max movements per run (`costing.recalc.max_movements_per_run`, default 200k); max from-date distance; dry-run mode returns planned adjustments without posting (used by verifier/exit gates). |
| Outputs | `job_run` evidence, `cost_ledger_entry` corrections, `cogs_adjustment`/T-25 postings, `item_cost.status`, events `cost.recalculation.completed`, metrics (lag, adjustment amount, items affected). |
| Tests | golden corpus G-01..G-12 replayed through normal and recalculation paths must end at identical valuation (§10). |

### 5.6 Backdating interaction and D5 block/provisional policy

- **Detection:** FS-04 step 6 marks a posting `is_backdated=true` when
  `transaction_date < latest_effective_date(item, cost_object)`; FS-05 is told to `enqueue_recalculation`
  after commit (step 17) or synchronously for standard-cost changes.
- **D5 policy** (Lead decision D5; `O-07` resolved as per-tenant flag):
  `costing.block_when_recalc_pending=true` (default) → a posting that requires a provisional cost for an
  item whose `item_cost.status=PENDING_RECALC` returns `409 COSTING_RECALC_REQUIRED` from
  `assert_postable`; **nothing is posted** (no partial ledger). With the flag `false`, the posting
  proceeds with `cost_provisional=true`, the ledger header/cost entries are flagged
  (`cost_estimated=true`), the item stays `PENDING_RECALC`, and the later recalculation issues T-25
  adjustments that clear the provisional flags. The chosen mode is recorded on each cost entry so
  replay is deterministic.
- **Reversal/backdated correction:** recalculation from `min(original_date, reversal_date)`; if the
  target period is closed, T-25 postings use the earliest open period with `period_shifted=true` and
  `adjusts_period_id` = the original period (finance intent carries both dates).
- **Standard-cost changes** are never backdated: they take effect from the version’s `effective_from`;
  on-hand is revalued via T-24 (no history rewrite) and open WOs revalue per §5.8.
- **Recalculation proof:** after any recalc, `costing.reconcile_costs` must show zero drift (INV-10),
  and the golden corpus asserts normal-path vs recalculated-path equality (§10).

### 5.7 Standard costing: categories, templates, versions, planned standards and rollup

- **Cost categories** are the building blocks (material/labour/machine/overhead/freight/duty) used for
  standards, rollups and variance analysis [iri-042, mpw-157]. **Inventory cost templates** assign
  categories/weights to item types or item categories [iri-043]; resolution precedence: item category
  template → item type template → tenant default (no template = all categories at manual standard,
  `ASSUMPTION`).
- **Cost versions** are effective-dated standard sets [iri-045]: `PLANNED` (editable), `ACTIVE`
  (effective; creates `standard_cost` rows), `SUPERSEDED` (read-only after a newer version becomes
  effective). Multiple versions may coexist; a *single* active version per tenant is **not** required
  (clarification of DATA-MODEL §8 note; effective standards are per item/category).
- **Planned standards** are per item/category within a version, entered manually or produced by a
  rollup; activation requires all planned standards approved and no effective-date overlaps
  (DM-COST-05). Activation creates `standard_cost` rows from `effective_from` and, if on-hand or open
  WIP exists, opens a revaluation scope (T-24) — the activation itself never writes inventory value.
- **Rollup** (multi-level, [iri-047, mpw-031, mpw-038..047]): for a cost version, compute assembly
  standards from component standards already in the version plus conversion-cost inputs supplied by
  the **caller** in the rollup request (manual planned standards / cost-category amounts). FS-05 does
  not pull BOM/routing data: FS-09 (later wave) is a consumer that builds its own costed-BOM request
  from its data and calls `POST /v1/cost-rollups`; purchased/assembly items without conversion
  inputs roll up material costs only (`ASSUMPTION`). Material cost types are selectable
  per documentation: per costing method, per purchase price, per item default [mpw-043..045]; conversion
  cost calculations produce top-level and fully-exploded costs [mpw-041/046]. Output: `cost_rollup_run`
  + `cost_rollup_line` per item/category/BOM level with `breakdown JSONB` (component contributions);
  deterministic for identical inputs; rerun creates a new immutable run; approval writes
  `planned_standard_cost` rows for the version.
- **Standard cost on-hand value invariant (`INV-16`)**: on-hand value = `qty × active standard`
  (± open variances); enforced by reconcile. Standard-cost outbound is always at standard; actual-vs-
  standard differences become variances (§5.9), never retroactive re-costs of inventory.

### 5.8 Revaluation (T-24), including WIP and per-WO lines

- **Standard change revaluation** [iri-048]: when standards become effective (or a cost correction is
  approved), the engine computes per line `value_delta = (new_cost − old_cost) × qty` at the
  item/location (on-hand qty) and posts one value-only transaction per revaluation line via
  `PostingPort.post_revaluation` (T-24). On-hand value and open layer values are updated
  (`cost_layer.status=REVALUED` when the layer carries revalued value); average/standard `item_cost`
  rows updated; `cost_revaluation.posted_transaction_id` set in the same transaction.
- **WIP revaluation** [mpw-152] — **provider direction (no upward dependency):** FS-05 exposes the
  revaluation API + document + event; the **caller owns WIP-scope selection**. When FS-09 is deployed,
  FS-09 computes the open-WO scope (partially built WOs in Released/Built; WOs not in Released/Built
  are out of scope per documentation) and WIP quantities, then calls
  `POST /v1/cost-revaluations` with one `work_order_id` line per WO and `POST /v1/cost-revaluations/{id}/post`;
  FS-05 validates/revalues exactly the supplied lines (`cost_revaluation_line` per WO) and never reads
  FS-09 tables. Before FS-09 is verified, WO lines are rejected (`409 DEPENDENCY_NOT_DEPLOYED`) while
  on-hand revaluation works; the `work_order_id` FK remains deferred/closed additively by FS-09.
- **Revaluation document lifecycle:** `DRAFT → PENDING_APPROVAL → APPROVED → POSTED → REVERSED`
  (and `VOID` pre-post); approval required; reversal posts the negated value-only transaction; no
  double post (`posted_transaction_id UNIQUE`). **Finance intents (D2):** every T-24 post emits the
  `STDREVAL` posting-rule intent(s) inside the FS-04 posting transaction; `FinancePort.record_journal_intent`
  persists `platform.finance_journal_intent` rows (one append-only row per GL-instruction line,
  INV-29/DM-PLAT-11). FS-05 never writes the finance table itself; the intent is part of the
  revaluation post flow and is asserted by `tests/invariants/test_finance_intents.py` (FS-00) plus the
  FS-05 provider-contract revaluation fixture.
- **Variance interaction:** revaluation does not create cost variances; it corrects asset value and
  emits `standard_cost.revalued` / `cost.revaluation.posted`.

### 5.9 Variance families (six documented families)

All variances post through configured accounts (FS-01 item variance accounts / cost categories) via
`cost_variance` + the GL posting rule of the triggering posting; `variance_type` enum is owned here.
`cost_variance.amount_base` must be non-zero; variances are period-attributed (`fiscal_period_id`) and
closeable (`OPEN→CLOSED`); closed variances are retained.

| Family | `variance_type` values | Trigger / source | Calculation | Posting path |
|---|---|---|---|---|
| 1. Purchase price variance | `PURCHASE_PRICE` | T-01 receipt for a standard-cost item [iri-037] | `(actual receipt cost − standard) × qty_received` | part of T-01 `RCPT` intent (Dr/Cr PPV) + `cost_variance` row |
| 2. Vendor bill variance (qty/price/FX) | `BILL_QUANTITY`, `BILL_PRICE`, `EXCHANGE_RATE` | T-04/T-06 bill match [mpw-478, mpw-479] | bill vs receipt/PO at matched quantities/rates; FX variance from receipt vs bill rate (never re-costs inventory) | T-06 `BILLVAR`; `vendor_bill_variance` (FS-08) links to `cost_variance` |
| 3. Production quantity variance | `PRODUCTION_QUANTITY` | T-15 build / T-18 completion; component usage vs BOM standard | `(standard component qty − actual consumed qty) × standard cost` | T-15/T-18 `BLD/WIPCMP` intents (+`cost_variance`) |
| 4. Production cost variance | `PRODUCTION_COST` | T-18 completion / T-19 close; conversion cost actual vs standard per cost category [mpw-055..057] | `(actual conversion cost − standard conversion cost)` by category (labour/machine/overhead) | T-18/T-19 `WIPCMP/WIPCLS` intents |
| 5. Unbuilt variance | `UNBUILT` | T-16 unbuild [mpw-020] | restored component cost vs assembly cost removed (difference) | T-16 `UNBLD` intent to unbuild variance account |
| 6. WIP standard revaluation variance | `WIP_REVALUATION` | T-24 per-WO revaluation when component standards change mid-order [mpw-152] | `(new standard − old standard) × WIP qty` for open WOs | T-24 `STDREVAL` intent (+ per-WO `cost_revaluation_line`) |
| (supporting) | `ROUNDING`, `LANDED_COST_ABSORPTION`, `COGS_ADJUSTMENT` | rounding residual / landed cost on standard items [mpw-731] / System COGS true-up | residual/largest-remainder; standard items post landed cost as variance | T-25 `COGSADJ` / T-26 `LANDED` intents |

### 5.10 System COGS adjustments, underwater costing and return costing

- **Underwater cost fallback** [iri-037, iri-263]: when a position is underwater, outbound
  `unit_cost = last_purchase_price`; if no purchase history, `0` with `estimated=true` (FS-04 policy
  §5.10). Group-average items use the group average instead of last purchase price [iri-064].
- **True-up** [iri-056]: when replenishment brings the position to `qty ≥ 0`, the engine applies the
  true receipt cost to the previously estimated quantity and posts the difference as **System COGS
  adjustment (T-25)** with `adjustment_type=UNDERWATER_TRUE_UP`, `source_cost_run_id` = the true-up run;
  period attribution: the adjustment posts with the **receipt’s `transaction_date`** (documented
  behaviour: correction posts with the item receipt, which may shift cost between periods) while
  `cost_ledger_entry.adjusts_period_id`/`cogs_adjustment_line.adjusts_period_id` records the period
  whose original cost was estimated [iri-263]. Estimated flags clear only when the true-up posts.
- **COGS adjustment document types** (`cogs_adjustment.adjustment_type`): `UNDERWATER_TRUE_UP`
  (system), `RECALC` (recalculation diff), `ROUNDING` (residual true-up), `RETURN_COST` (return
  cost correction). System-generated adjustments require no human approval; manual adjustments require
  approval and a reason. Reversal of a T-25 posts the negated value; no qty change.
- **Return costing** [iri-063, iri-229]: original cost when traceable, else current method cost; a
  return into a different location uses the documented multi-location return rules (location cost
  object); difference vs original can post as `RETURN_COST` correction; serial/lot identities restore
  their identity cost (FS-06).
- **Rounding residuals**: unavoidable residual `< 1e-9` posts as a `cost_adjustment` line flagged
  `rounding_residual=true`; nightly reconcile asserts zero residual drift (`INV-13/14`).

### 5.11 Landed cost (T-26) and estimated landed cost (T-27)

- **Landed cost document** [mpw-716..733]: header (`vendor`, optional bill link, `allocation_basis`,
  currency, `estimated`) + lines (cost category/landed-cost item, amount, optional basis override) +
  allocations to receipt lines. Allocation bases: `WEIGHT` (item weight), `QUANTITY` (received qty in
  base UoM), `AMOUNT` (receipt line extended value), `PER_LINE` (equal split); basis override per line;
  allocation must use the receipt line quantities/values **as posted** (no re-cost of the bill).
- **Allocation algorithm:** compute exact shares with `Decimal`; distribute by largest-remainder to 12dp
  so `Σ allocated_amount = landed_cost_line.amount` exactly per currency (`INV-12`, DM-COST-07);
  allocations reference only posted receipt lines; standard-cost items post the allocated amount as
  `LANDED_COST_ABSORPTION` variance instead of inventory value [mpw-731]; average items update
  `item_cost.value_base`/`avg_cost`; FIFO/LIFO items update existing layers' `value_remaining` (or
  create a value-only layer adjustment via `cost_layer.status=REVALUED`/`derived_from_layer_id`); qty is
  unchanged (T-26 value-only).
- **Posting:** T-26 value-only transaction through FS-04; enqueues recalculation from the receipt date
  (§5.5); closed-period guard with `period_shifted` intent; allocations/`cost_ledger_entry` link the
  transaction; document lifecycle `DRAFT→PENDING_APPROVAL→APPROVED→POSTED→REVERSED`, `posted_transaction_id`
  unique; reversal restores layers/avg and enqueues recalculation.
- **Estimated landed cost (T-27)** [mpw-734..751]: templates define cost lines (category, basis,
  default amount/percent); assignment to items/purchase lines is data owned by FS-01/FS-08 (documented
  assignment fields); at receipt (invoked by FS-08 receipt posting via `costing.estimated_landed_cost`
  hook) the engine computes estimates and posts T-27 value-only, once per receipt line
  (`uq` by receipt line + template line), flagged `estimated`. When the actual landed cost (T-26)
  posts, the estimate is reversed (paired T-27 reversal) and the true amount applied; T-27 without a
  matching T-26 remains accrued (read model exposes `estimated=true`). Cancellation/reversal rules:
  estimate reversal only while unreplaced; period-shift intent carries original receipt date.
- **Interfaces:** `costing.landed_cost.apply(receipt_line_refs, allocations[])` called by
  procurement/vendor-bill posting **inside the same transaction** (ARCHITECTURE §3.6).

### 5.12 Group-average costing and location costing groups

- **Group object:** `location_costing_group` (currency = tenant base currency; all members must share
  the base currency) + members; a location belongs to at most one group. Group-average items use the
  group cost object; items whose location has no group **fall back to AVERAGE** [iri-064].
- **Balance:** `group_average_balance` keeps `(item, group)` `qty_on_hand/value_base/avg_cost`; every
  costing transaction in any member location recomputes the group average (`avg = Σvalue/Σqty` across
  members) and updates member `item_cost` rows to the group average on read (member rows hold
  location qty/value for reporting while cost is group-level; implementation detail: `item_cost`
  with `location_costing_group_id` set is the group object; member locations do not carry separate
  average state).
- **Behaviours:** cross-location average impact [iri-064] (receipt in location A changes group cost used
  in B); underwater fulfilment borrows group average; `include_in_transit_value` includes in-transit
  value in the group total when enabled (per-group flag); `BALANCING` status while a group correction is
  pending, exposed by the balance-location-costing-group accounts status read [iri-067/068]
  (`ASSUMPTION` DMX-18).
- **D6 guard:** inventory worksheets are prohibited for group-average items [iri-064]: FS-04 checks the
  item’s method/cost-object type and rejects T-08 with `422 POLICY_VIOLATION`; the registry-level
  configuration (group assignment) is validated here (location in a group, currency equality, no
  duplicate membership).
- **Group changes:** adding/removing a location requires zero group balance for all group items at that
  location (or an explicit balancing transfer/revaluation documented by finance); removal enqueues
  recalculation for affected items; group inactivation only when all balances are zero.

### 5.13 Precision, currency and rounding rules

| Concern | Rule (ARCHITECTURE §3.7, DATA-MODEL §1.4) |
|---|---|
| Numeric types | quantities/money `NUMERIC(38,12)`; Python `Decimal` with 28-digit context; floats prohibited (lint); API decimal strings. |
| Valuation currency | tenant base currency; every cost entry stores base value; source transaction currency/rate stored on the ledger; no FX revaluation (deferred). |
| FX source | receipt rate on receipt date, bill rate on bill date; difference = vendor bill FX variance (T-06), never inventory re-cost. |
| Value rounding | extended value per movement `quantize(qty × unit_cost, 12)`; posting residual (Σ rounded − exact) assigned by largest-remainder to movements with largest fractional part (`INV-13`); rounding mode recorded on each cost entry. |
| Layer arithmetic | partial consumption value = `value_remaining × (consume_qty / qty_remaining)` quantized; final consumption removes exact remaining value; `Σ consumption + remaining = original` (`INV-11`). |
| Residuals | unavoidable residual `< 1e-9` posts as `cost_adjustment` line flagged `residual=true`; nightly reconcile asserts zero residual drift (`INV-14`). |
| Rounding mode | tenant setting `costing.rounding_mode ∈ {PER_MOVEMENT (default), PER_TRANSACTION, PER_DOCUMENT}`; recorded per entry for deterministic replay (D-28). |
| Presentation | API can return 2-dp money views (`?money_dp=2`) — presentation only, never used for arithmetic. |
| Quantity/UoM | valuation unit cost is always per base UoM; conversion exact to 12dp (FS-01), `422 UOM_PRECISION_EXCEEDED` otherwise. |

### 5.14 Finance intents for value movements

- FS-05 does not call the finance port directly for postings driven by FS-04: `value_movement` returns
  `gl_intents` (posting-rule ids and account refs) to FS-04, which calls
  `FinancePort.record_journal_intent` inside the same transaction (D2; FS-04 §5.18). For value-only
  documents that FS-05 creates (T-24/T-25/T-26/T-27), the intent is emitted by FS-04’s posting of the
  T-24..T-27 transaction using the rule ids below. Cross-process service callers may submit these
  T-24..T-27 postings through FS-04’s generic internal posting command
  (`POST /v1/inventory-transactions`, FS-04 §5.17.1); in-process callers keep using `PostingPort`. **Confirmed for revaluation (D2):** T-24 emits
  `STDREVAL` intents; FS-00 persists one append-only `platform.finance_journal_intent` row per
  instruction line keyed by `(inventory_transaction_id, posting_rule_id, intent_line_no)`
  (INV-29/DM-PLAT-11); FS-05 contributes no direct finance writes and the ledger transaction id is the
  provenance link.
- Posting rules owned/parameterised here: `STDREVAL` (T-24), `COGSADJ` (T-25), `LANDED` (T-26),
  `LANDEDEST`/reversal (T-27), `BLD/UNBLD/WIPISS/WIPCMP/WIPCLS` (variance components), `RCPT` PPV
  portion, `BILLVAR` (T-06 value lines). Account refs resolve from `item_accounting`/`item_inventory`
  (`asset_account_ref`, `cogs_account_ref`, `adjustment_account_ref`, `variance_account_ref`,
  `unbuild_variance_account_ref`) and `cost_category` defaults; opaque finance-boundary strings.
- Intents are balanced (`Σ debit = Σ credit`) in base currency and carry the cost-category dimension
  where applicable; `period_shifted`/`backdated_original_date` propagate for closed-period corrections;
  instruction counts equal persisted `finance_journal_intent` rows per posting revision (INV-29).
- Availability check: FS-05 emits intents only when `costing.engine.enabled=true`; disabled costing
  makes cost-bearing postings fail closed at FS-04 (`409 DOMAIN_DISABLED`).

### 5.15 Reconciliation, read models and pending-status jobs

- `costing.reconcile_costs` (nightly + exit gate): rebuilds `item_cost` and open layers from
  `cost_ledger_entry`, compares (INV-10, INV-11, INV-15, INV-16), checks pending-recalc backlog and
  estimated-value aging. Drift is a P1 incident; `repair=true` may rewrite costing read/state models
  from the append-only cost ledger (never ledger/cost entries) in short batches under an advisory lock.
- `costing.cogs_adjust` (nightly/on-demand): finds underwater positions whose true-up is pending after
  replenishment and creates T-25 `UNDERWATER_TRUE_UP` adjustments; idempotent by `(item,cost object,
  receipt line)`; approval not required for system-generated.
- `costing.layers.expire` (monthly): marks fully exhausted layers for archival reporting, closes stale
  `OPEN` layers with zero remaining (data repair only if reconcile proves it), maintains partitions.
- `costing.checkpoint.build` (monthly/on-demand): creates cost checkpoints used by recalculation;
  rebuildable from cost ledger.
- Read models exposed to dependants/FS-15: `item_cost` (current valuation), open `cost_layer` detail,
  `group_average_balance`, `cost_variance` by period, `cost_ledger_entry` (stock-ledger value side);
  all tenant-scoped and permission-gated (`costing.cost.read`, `reporting.cost.view`).
- Freshness: `item_cost`/layers are synchronous with postings; accruals/estimates are flagged; no
  stale-cost reads silently used for posting (D5).

### 5.16 Business rules and invariants

Scoped DATA-MODEL rules implemented here:

- `DM-COST-01` exactly one `item_cost` per cost-object key; key derivation per §5.1.
- `DM-COST-02` FIFO/LIFO cost objects’ layers match `item_cost.qty/value` (`INV-11`); average/standard
  objects have no OPEN layers.
- `DM-COST-03` `cost_ledger_entry` append-only; every entry references one ledger line except
  recalculation/rounding entries; one entry per line per movement/run (`INV-17`).
- `DM-COST-04` recalculation writes only new entries with `cost_run_id`; never updates history; deltas
  post as T-25.
- `DM-COST-05` `standard_cost` effective dates do not overlap per item/category; version activation
  requires approved planned standards and triggers revaluation scope.
- `DM-COST-06` standard on-hand value = `qty × active standard` ± open variances (`INV-16`); open-WO
  revaluation lines per WO.
- `DM-COST-07` landed-cost allocations sum exactly to each line amount (`INV-12`) and reference only
  posted receipt lines.
- `DM-COST-08` group members share base currency and cannot belong to another group; group-average items
  use only locations in a group (else fall back to Average).
- `DM-COST-09` group-average items are rejected on inventory worksheets (`422 POLICY_VIOLATION`).
- `DM-COST-10` `item_cost.status` must be `CURRENT` for posting unless provisional costing is enabled;
  recalculation sets `PENDING_RECALC` and blocks per D5.
- `DM-COST-11` specific-cost layers have `qty_original=1` and require numbered identity columns.
- `DM-COST-12` no float storage/derivation; all numerics `NUMERIC(38,12)`.

Additional testable rules owned by this spec:

- `RULE-05-01` A cost-bearing posting never commits without a matching cost entry for every ledger line
  (`INV-17`); valuation failure rolls back the whole posting (`409 COSTING_INCOMPLETE`).
- `RULE-05-02` `unit_cost`/`value_delta` are method-deterministic for identical history; replaying the
  cost ledger yields identical `item_cost` and layers (INV-10/11; golden corpus).
- `RULE-05-03` `Σ delegated cost entries = Σ ledger value` per cost object; no orphaned cost entry or
  layer (reconcile exact, DM-GLOBAL-09).
- `RULE-05-04` Layer conservation: consumption + remaining = original for qty and value; no negative
  layer values; exhausted layers close exactly (`INV-11`, `INV-15`).
- `RULE-05-05` Rounding identity: Σ rounded movement values equals the exact posting value within
  `1e-9`; residuals are explicit entries (`INV-13`, `INV-14`).
- `RULE-05-06` Landed-cost allocation per line equals the line amount exactly; allocations reference only
  posted receipts (`INV-12`).
- `RULE-05-07` Standard on-hand value equals `qty × effective standard` at effective dates; revaluation
  expresses the change as a value-only posting, never a history rewrite (`INV-16`).
- `RULE-05-08` Pending recalculation with default D5 blocks postings (`409 COSTING_RECALC_REQUIRED`);
  provisional mode is opt-in, flagged and later trued-up (§5.6).
- `RULE-05-09` Underwater estimated costs are flagged `estimated=true` and trued up via T-25 with
  period attribution; flags clear only after true-up (§5.10).
- `RULE-05-10` Group-average balances recompute across member locations; group items never use
  worksheets; group locations share currency (§5.12, D6).
- `RULE-05-11` Method immutability is respected; no posting values an item under a different method than
  `item_inventory.costing_method`.
- `RULE-05-12` Every value posting emits balanced finance intents via `platform.finance` (D2); value
  corrections are compensating postings only.
- `RULE-05-13` Tenant isolation/RLS on all costing tables/APIs (`INV-25`); cost values not exposed
  without `costing.cost.read`/`reporting.cost.view`.
- `RULE-05-14` Recalculation/standard/landed/COGS jobs are idempotent and rerunnable with durable
  cursors; reruns never duplicate cost entries (`INV-17` unique key) or adjustments.

Invariants owned/contributed: `INV-02` (value conservation), `INV-10` (value equation), `INV-11` (layer

### 5.17 State machines (owned aggregates)

| Aggregate | States | Transitions and guards |
|---|---|---|
| `cost_version` | PLANNED, ACTIVE, SUPERSEDED | PLANNED→ACTIVE [all planned standards approved, no effective-date overlap, activation revaluation queued]; ACTIVE→SUPERSEDED [newer version effective]; no DELETE; PLANNED editable, ACTIVE/SUPERSEDED immutable standards. |

| `cost_rollup_run` | QUEUED, RUNNING, SUCCEEDED, FAILED | QUEUED→RUNNING→SUCCEEDED/FAILED; rerun creates a new run (immutable results); FAILED retry increments attempt within max; no CANCELLED results mutation. |

| `group_average_balance.status` | CURRENT, BALANCING, UNDERWATER | CURRENT→BALANCING [group correction pending]; BALANCING→CURRENT [correction posted and balances]; CURRENT/BALANCING→UNDERWATER [negative group position]; UNDERWATER→CURRENT [true-up]. |

## 12. Rollback

- Flag off `costing.engine.enabled` (immediate): cost-bearing postings fail closed (`409
  DOMAIN_DISABLED`); cost reads stay available; pending recalculations can be completed or paused. No
  valuation writes occur while off.
- Redeploy the prior image; migrations are additive and N-1 compatible; no prod down-migration.
- Cost ledgers/layers are append-only: corrections via compensating value postings (T-25) or reversal;
  never update/delete cost entries or consumption rows.
- Recalculations and valuations are rerunnable/idempotent; a faulty rollup/revaluation can be reversed
  by its own T-24 reversal and the version SUPERSEDED (never deleted).
- If D5 block must be relaxed temporarily, set `costing.block_when_recalc_pending=false` (audited) and
  plan the true-up; do not disable reconciliation.
- Dependants automatically blocked by `check-env` while status ≠ verified; FS-06/07/08/09/10/13/15
  consumer tests fail closed against the previous contract version.
