## 1. Objective and source coverage

Deliver the planning context: a **read-optimised, write-restricted** backend that never posts inventory, computes
demand and supply plans, DRP transfer suggestions, supply allocations with FEFO lot/serial assignment and ATP
projections, and turns suggestions into **draft** purchase orders/work orders/transfer orders through the owning
contexts. AIM reorder-point/preferred-stock automation runs behind a versioned formula policy (D7) with
deterministic fixtures; ATP runs behind a versioned method policy. Planning outputs are immutable runs keyed by
`run_key`, tenant-scoped, data-scoped and reproducible from the same inputs and policy version.

Source book: Inventory Management [book_N2249433](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/book_N2249433.html);

## 2. Scope

**In scope (backend):**
- Planning rules + scopes, planning horizons/buckets, time fences (FROZEN/SLUSHED) and demand-change thresholds.
- `demand_history` projection intake (sales/issues/fulfilment/adjustment/forecast/external), partitioned monthly, with retention/maintenance hooks.
- Demand plans: statistical methods LINEAR_REGRESSION, MOVING_AVERAGE, SEASONAL_AVERAGE, SALES_FORECAST; OPEN_DEMAND (current demand: active `inventory_commitment` rows with `required_by_date` via `inventory.balances` plus `order.demand` boundary events); MANUAL; manual line overrides; plan lifecycle and status monitoring; demand-change action messages.
- AIM auto-calculation jobs (`replenishment.aim`, `replenishment.ordering`): per item/location average demand, seasonal factor, lead time, safety stock → reorder point/preferred stock under versioned `aim_formula_policy`; `replenishment_calculation(_line)` with `formula_version`; writes to item planning fields **only** through FS-01's contract and only when `auto_calculate_planning=true`; Order Items / quantity-to-order data and reorder-reminder data.
- Supply planning/MRP engine (`planning.supply.run`): net requirements per item/location/bucket from demand plans + actual demand, minus available/on-order/scheduled receipts; multi-level BOM explosion incl. phantom; lead-time offset via FS-09 calendars; lot sizing; allowed supply types; suggestions + planning action messages; deterministic `run_key`; immutable runs; bulk draft-order creation through FS-08/FS-09/FS-04 APIs.
- DRP on the same engine (`planning_rule.engine=DRP_BOD`): distribution categories, network/members, bill of distribution/levels (acyclic), transfer supply type → `supply_plan_suggestion(action_type=CREATE_TO)`; no duplicate algorithm (§6.5 EXT note).
- Supply allocation: strategies (PRIORITY/FAIR_SHARE/PROPORTIONAL), ordered rules, location scope, assembly/kit inclusion, FEFO lot/serial assignment; runs/results/exceptions; allocation plans only (never ledger); optional reserve-now → FS-04 commitment calls.
- ATP: `atp_projection` rebuild (`atp.rebuild`, event-driven + job), versioned `atp_method` policy with per-bucket netting, clamping at zero, earliest-availability and checking-availability query API; documented staleness.
- Replenishment data endpoints (Order Items, reorder reminders), planning workbench/signal read endpoints as data feeders for FS-15/future Control Tower (`EXT`; no UI).
- Planning-readonly enforcement, tenant isolation, RBAC/data scopes, audit, events/outbox, jobs, flags/tenant settings/policy versions, migrations+seeds, deterministic fixture corpus.

**Out of scope / deferred:**
- Supply Planning Workbench UI (`iri-305`), Supply Chain Control Tower product/UI (`iri-322`), allocation/workbench UIs, Item 360/ATP availability UI (`iri-319` display surfaces; the backend check API is in scope), SuiteAnalytics workbooks/datasets (planning/ATP/DRP analytics), report rendering.
- Inventory replenishment/withdrawal **worksheets** and bulk transfer-order documents (FS-04-owned, `iri-244..247`); FS-10 contributes planning-side draft TO creation only (C-6).
- WMS warehouse-internal replenishment (FS-11 `replenishment_plan`/`replenishment_task`; architecturally disjoint, ARCHITECTURE §6.8).
- Any ledger/balance/cost write: FS-10 holds no ledger write client or grant (INV-20); no GL/journals/period close (D2 boundary); no external EDI/demand-system integration (order boundary only); no UI/mobile/offline; no SuiteApp packaging.

Business rules and invariants (testable; DATA-MODEL ids cited):

- `DM-PLAN-01`/`INV-20` — planning tables are written only by planning jobs/APIs and never reference or mutate ledger/cost tables. Enforcement: module has **no** FS-04/FS-05 write client; DB grants for `replenishment` role are `SELECT` on dependency schemas; import-linter contract; `test_planning_readonly_ledger.py`.
- `DM-PLAN-02`/`INV-21`/`RULE-PLAN-01` — a suggestion converts to at most one document (`created_doc_id` partial unique); conversion is idempotent per suggestion id; converting an already-CONVERTED suggestion returns the previously created document ref (replay) or `409 SUGGESTION_ALREADY_CONVERTED` for a different request.
- `DM-PLAN-03`/`RULE-PLAN-02` — supply plans are deterministic for a given `run_key` (input snapshot + policy versions + formula ids); re-running the same key is a no-op; rerun with changed inputs creates a new immutable run; results are never updated in place.
- `DM-PLAN-04`/`INV-24`/`RULE-PLAN-03` — time fences: demand changes inside FROZEN fence are rejected (`409 TIME_FENCE_VIOLATION`); inside SLUSHED fence changes are stored + flagged (`planning_action_message` DEMAND_CHANGE/TIME_FENCE) and never silently applied.
- `DM-PLAN-05`/`INV-22`/`RULE-PLAN-04` — ATP projected available is clamped at ≥0 per bucket; the shortage for a bucket is derivable (`shortage = max(0, projected_unclamped_negative)`); `atp_projection` column constraint enforces clamp; rebuild is idempotent and event-driven; posting decisions never depend on ATP.
- `DM-PLAN-06`/`INV-23`/`RULE-PLAN-05` — allocation never exceeds supply per (item, location) and per FEFO lot/serial: for each (run, item, location, supply_ref) Σ qty_allocated ≤ supply qty; for each lot Σ allocations ≤ lot on-hand; every uncovered demand has `allocation_exception`.
- `DM-PLAN-07`/`RULE-PLAN-06` — AIM writes planning fields on `item_master.item_location`/`item_inventory` only when `auto_calculate_planning=true`, only from `action=APPLY` lines, through the FS-01 contract, and stores/echoes the formula version; disabling auto-calc stops writes and manual values remain authoritative [iri-269..276].
- `DM-PLAN-08`/`RULE-PLAN-07` — DRP network/BOD graphs are acyclic, a location appears once per network, BOD arcs have source≠destination and positive lead time; transfer suggestions carry source/destination and are only emitted when `TRANSFER` ∈ `allowed_supply_types`.
- `DM-PLAN-09`/`RULE-PLAN-08` — planners may only see/convert suggestions inside their data scope (location/item/category), enforced on every read/write and conversion.
- `RULE-PLAN-09` — no double-counting of supply/demand: each demand source is counted exactly once per plan bucket (demand plan OR open demand per configuration, not both for the same order line; open-WO component demand from FS-09 excludes components already covered by another open supply; scheduled receipts counted once per document); proven by fixtures with expected gross/net requirement.
- `RULE-PLAN-10` — projection determinism: identical `run_key` inputs (quantity snapshots, document open quantities, BOM versions, lead times, time fences, policy versions) yield identical `supply_plan_line`/`suggestion` values (golden fixtures; double-run equality).
- `RULE-PLAN-11` — AIM determinism: identical inputs + `formula_version` → identical `reorder_point_calculated`/`preferred_stock_calculated`/`action` (fixture corpus §10.1); arithmetic in `NUMERIC(38,12)` with HALF_UP quantisation to 12 dp and documented epsilon.
- `RULE-PLAN-12` — ATP determinism + policy version recorded: identical projection inputs + `atp_method` policy → identical rows; response/event carries policy id+version; method enum values are those of `atp_projection.method`.
- `RULE-PLAN-13` — suggestion quantities: qty > 0, respects lot sizing (FIXED_QTY exact multiples; MIN_MAX between min/max; LOT_FOR_LOT exact net requirement), due date ≥ horizon start and offset by lead time; suggestions below MOQ are raised to MOQ (vendor `min_order_qty` read via FS-08) and flagged in `explanation`.
- `RULE-PLAN-14` — plan status lifecycles follow the planning-run state machine (§5 state machines); failed runs never replace the last APPROVED plan; cancellation only pre-calculation.
- `RULE-PLAN-15` — demand-history rows are append/upsert-idempotent by natural key; corrections are new buckets/versioned window inputs, never silent rewrites of approved plans.
- `RULE-PLAN-16` — all quantities/money are `NUMERIC(38,12)` and wire decimal strings; timestamps UTC; `bucket_date`/`transaction_date` are DATE in tenant timezone semantics; no floats in domain math (D-10).
- `RULE-PLAN-17` — tenant isolation (INV-25): every table/route is tenant-filtered and RLS-protected; cross-tenant ids return 404.
- `RULE-PLAN-18` — every state change/config change/policy change writes an append-only `audit_event`; plan run metadata (`job_run`) proves who/when/input hash.
- `RULE-PLAN-19` — policy changes are additive: a new policy id+version is required for any formula/method change; existing runs keep their recorded version and remain reproducible.
- `RULE-PLAN-20` — the API never returns another tenant's planning data and never accepts `tenant_id` from the client; data-scope filters are applied before pagination.

## 12. Rollback

- **Flag-first, immediate:** `replenishment.planning.enabled=off` stops jobs/routes/event handlers; plans,
  suggestions, runs, projections remain readable and immutable; drafts created earlier remain owned by FS-04/08/09
  contexts (their rollback applies independently). No data loss.
- **Deploy previous image**; migrations are additive/N-1 compatible (no dropped columns; new tables ignored by old
  code). No prod down-migration; down-migrations tested in CI/sandbox only.
- **Data compensation:** planning data is derived — rerun with a new policy version/run_key after validation rather
  than mutating prior runs; proposals that created drafts are traceable through `created_doc_type/id` and are
  cancelled/dismissed in their owning context. Never delete ledger/planning rows: runs/suggestions are immutable
  records (planning tables may be retained/archived by retention policy).
- **Policy rollback:** restore the prior tenant setting `replenishment.aim_formula_policy` / `replenishment.atp_method`
  version (additive ids, so both old and new remain resolvable) and rerun the affected jobs; prior calculation rows
  keep their recorded `formula_version` for audit.
- **Consumers:** `check-env` blocks FS-15 automatically while status ≠ verified; communicate via events/changelog.
