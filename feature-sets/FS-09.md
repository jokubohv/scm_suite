## 1. Objective and source coverage

Deliver the manufacturing execution backend: assembly-item extensions, multi-level BOMs with revisions and BOM
member control (including phantoms and matrix assemblies), routings/work centres/calendars/cost templates,
work-order lifecycle and component commitment, WIP issue/completion/close (T-17/T-18/T-19), non-WIP assembly
build/unbuild (T-15/T-16), outsourced manufacturing with PO linkage, engineering change orders, deterministic
scheduling-run/capacity computation and the available-to-build calculation. The set is independently deployable
once its declared dependencies are verified and is the source of open-WO demand/supply for FS-10 and of
component-picking requirements for FS-11. It owns manufacturing documents and read models only; every value/stock
effect is posted through FS-04/FS-05 contracts (finance effects surface as `platform.finance_journal_intent` rows).

**Δ-CFG/Δ-REUSE (EXT/ASSUMPTION, beyond the SCM help set):** the set additionally delivers a tenant-configurable
**manufacturing compatibility engine** — typed attributes/values, slot/capacity definitions and rule sets with
**dual scope** (assembly/BOM-revision baseline **and** order/configuration/customer/region/channel context rules,
both applied with AND semantics and deterministic specificity → priority → code ordering), configurable
enforcement (tenant default HARD; per-rule/per-rule-set `INHERIT|HARD|WARN`; override scope + mandatory reason,
audited), and immutable `compat_configuration` validation evidence gating **every** manufacturing/configuration
path (BOM activation, matrix generation, phantom explosion, WO create/update/release/firm, WIP issue/completion/
close/backflush, non-WIP build, outsourced manufacturing, ECO implementation, order/configuration boundary and
available-to-build; unbuild is exempt). It also delivers **unbuild reuse**: per component-line dispositions
RETURN_TO_STOCK (default), SCRAP and HOLD, optional used/condition/return-status/resale/target-bin, configurable
valuation (ORIGINAL_COST default, NRV/MANUAL via FS-05), preserved serial/lot lifecycle and full-only reversal.
Scope/objective beyond the crawled docs is marked `EXT`/`ASSUMPTION` throughout; no catalog topic is added.

## 2. Scope

**In scope (backend):**
- `assembly_item` extension for item types ASSEMBLY / WIP / PHANTOM / MATRIX_PARENT / OUTSOURCED, default BOM/routing, build cost, revision-control mode, backflush/yield defaults, unbuild-variance and WIP account refs; matrix-assembly child resolution and phantom explosion.
- Kit/group/assembly member semantics: FS-01 owns `kit_group_member` composition and item typing; kits and groups are **never stocked or built** in FS-09 (kit/group fulfilment T-14 remains an FS-04 posting, O-11); FS-09 owns only assembly/WIP/phantom/matrix-child manufacturing master data and build transactions. Assembly/WIP items are stockable and post via T-15..T-19.
- BOM master: multi-level BOMs, BOM revisions (effective-dated, overlap-proof), default BOM resolution (master/location-specific), BOM components (qty per, UoM, yield %, round-up, phantom flag, operation association), BOM member control by effective date or revision, component where-used and BOM/costed-BOM inquiry APIs.
- Routing/master data: routings, routing steps (sequence, set-up/run times, work centre, cost category, outsourced flag), step charges, work centres/groups, work-center calendars (working days/shifts/capacity), manufacturing cost templates/lines.
- Work orders: planned/firm-planned/released/in-process/built/closed lifecycle plus cancel/void/reopen; manual, mass-created, and sales-order-linked (`external_sales_ref`) WOs; multi-line WOs; component requirement snapshot from the effective BOM revision with yield/round-up; component commitments on release; component issue/backflush; operation-task generation from routing; time/quantity completion records.
- WIP manufacturing: issue/completion/close transactions (T-17/T-18/T-19), backflush, WIP value/qty reconciliation read model, WIP account flow, variance handoff to FS-05, and the D6 standard/average-only method guard.
- Non-WIP assembly build/unbuild (T-15/T-16) incl. unbuild-from-original-build and unbuild variance.
- Outsourced manufacturing: outsourced operations, vendor PO creation/linkage (FS-08), build-helper receipt, vendor charges (estimated/actual) absorbed into build cost, consolidator creating draft POs.
- Engineering change orders: ECO create/submit/approve/implement (effective-dated BOM revision application), approval metadata via FS-00 declarative approvals.
- Scheduling computation: deterministic forward/backward, infinite/finite runs producing `scheduled_operation`, `capacity_plan`, `work_center_load`; rough-cut capacity roll-up and API; optional audited `apply` of a run to WO dates (never automatic; DM-MFG-10). Manufacturing Scheduler **UI** deferred (D4).
- Available-to-build (ATB) calculation API (D4 `EXT`, ASSUMPTION on arithmetic) with top-level/all-levels modes and kit expansion.
- Production output/scrap/yield bookkeeping: FG output via completions/builds, scrap via `qty_scrapped` on WOs/lines/operations plus T-07 adjustments (reason `SCRAP`, FS-04) and WIP close variance; component yield % and round-up drive requirement/consumption math (DM-MFG-03, RULE-MFG-11).
- Work-order component-picking interface for FS-11 (exported contract: `GET /v1/work-orders/{id}/components/pick-requirements` + `work_order.released` events; FS-09 never calls WMS).
- **Compatibility engine (Δ-CFG, EXT/ASSUMPTION):** `compat_attribute_def`/`compat_attribute_value` typed attribute catalogue and item/assembly values; `compat_slot_def` configurable slots/capacity per assembly/BOM revision; `compat_rule_set`/`compat_rule` with **dual scope** (`ASSEMBLY`/`BOM_REVISION` **and** `CONFIGURATION`/`ORDER`/`CUSTOMER`/`REGION`/`CHANNEL`, both applied, AND semantics); nine rule types (`REQUIRES/EXCLUDES/ONE_OF/MIN_QTY/MAX_QTY/CAPACITY/ATTR_EQ/ATTR_RANGE/SUBSET_OF`); configurable enforcement (tenant default HARD; per-rule/per-rule-set `INHERIT|HARD|WARN`; HARD blocks with `409 COMPATIBILITY_VIOLATION`, WARN records a violation); overrides require `manufacturing.compat.override` + mandatory reason and are audited; every validation persists an immutable `compat_configuration` evidence record (hash, ordered matched rule sets/rules, result `VALID/WARN/HARD_FAIL/OVERRIDDEN`, override refs).
- **Generic compatibility gates (Δ-CFG):** the same engine gates **every** manufacturing/configuration path — BOM/BOM-revision create+activate, matrix-assembly option generation, phantom explosion (phantom-flattened components; phantom members still subject to parent rules), WO create/update/release/firm, WIP issue/completion/close/backflush (revalidated at completion), non-WIP assembly build, outsourced manufacturing (subcontract BOM/output), ECO implementation/BOM-revision activation, order/configuration boundary (`order.demand` configure-to-order requests validated before demand commit, including customer/region/order scopes) and available-to-build (only valid configurations contribute). **Unbuild is exempt** (restores a previously valid build snapshot); kits/groups are not manufacturing paths (out of scope; optional future hook).
- **Unbuild disposition/reuse (Δ-REUSE, EXT/ASSUMPTION):** per `assembly_unbuild_component` line `disposition = RETURN_TO_STOCK` (default) | `SCRAP` (no stock; value to scrap/variance via FS-05; serial/lot scrapped) | `HOLD` (non-committable pending inspection); optional `is_used`, `condition_code_id`, `return_status_id` (USED/REFURB default when used), `target_location_id`/`target_bin_id`, `allow_resale` (default false for used); `value_policy = ORIGINAL_COST` (default, original build cost) | `NRV` | `MANUAL` (with `unit_value`), difference posted through FS-05 revaluation/adjustment inside the unbuild transaction; policy configurable at tenant/assembly/per-line (line override requires `manufacturing.unbuild.dispose`); serial/lot identity preserved with lifecycle `IN_STOCK_USED`/`SCRAPPED`/`HOLD`; quantity/value conservation; **full reversal only** (returned components must still be in the recorded status/qty; partial reversals not allowed); `REWORK` deferred to the FS-14 repair flow (no new dependency).
- Manufacturing preferences/tenant settings, feature flags, RBAC scopes (incl. `manufacturing.compat.manage|validate|override`, `manufacturing.unbuild.dispose`), audit, events/outbox, jobs, migration+seeds.

**Out of scope / deferred:**
- Manufacturing Scheduler SuiteApp UI/admin/install topics (computation and data API kept); Work Instructions/Traveler; Advanced Manufacturing SuiteApp (work benches, travelers, shop-floor data collection, advanced capacity); Costed BOM and Cost Variance Analysis SuiteApps (rollup/costed-BOM computation kept in FS-05; FS-09 exposes inquiry data only); Supply 360; Production Control Board; printing/labels/BOM/work-order/traveler rendering; Manufacturing Mobile and all scanner workflows (permanently excluded per D8 — no device protocol, no offline sync); Manufacturing analytics workbooks; UI for ATB/Item 360; external EDI/carrier integrations; GL/journals/period close (finance boundary, D2 — FS-09 posts through FS-04/FS-05 and only emits intents indirectly); consigned inventory (FS-13; assembly↔consignment tenant guard is enforced jointly per D6/A-10); wage/payroll/time-clock systems.
- **Δ-CFG/Δ-REUSE out of scope:** external CTO/configurator product or UI; hard-coded per-product constraint logic; separate compatibility service (D-32 alternatives rejected); kits/groups compatibility hook (documented future hook, not a manufacturing path); **REWORK/remanufacture dispositions** (deferred to the FS-14 repair flow — FS-09 emits no rework posting); compatibility rule authoring UI/saved-search surfaces (backend APIs only); used-goods resale/marketing workflows; condition/grade inspection capture (FS-12) and buyer-facing catalog constraints; repair orders and warranty exchange (FS-14).
- No foreign-key writes into FS-10/FS-11 tables; no UI tokens, screenshots or scheduled dashboards are deliverables.

tables only; no changed request/response or removed surface), so the consumer impact list from
`python tools/feature_sets.py who-depends-on --contract manufacturing.execution` (currently FS-10, FS-11, FS-12,
FS-15) keeps its `>=1.0.0 <2.0.0` ranges unchanged — **no consumer spec changes and no DAG/edge changes**. A
future breaking change would require a new major version + coordinated rollout. FS-09 consumes lower contracts
only through their contract facades; it never imports another module's ORM models (ARCHITECTURE §1.4, D-14).

Business rules and invariants (testable; DATA-MODEL ids cited):

- `DM-MFG-01` — work orders are non-posting until a build/completion posts; status transitions follow §19 and component commitments are raised on release.
- `DM-MFG-02`/`INV-28` — WIP is valid only for assemblies whose `item_inventory.costing_method` is STANDARD or AVERAGE; LIFO/FIFO/SPECIFIC assemblies are rejected at configuration (`422 POLICY_VIOLATION`) and at every WIP posting (`409 POLICY_VIOLATION`); components may use any method.
- `DM-MFG-03`/`RULE-MFG-01` — `work_order_component` snapshots the resolved BOM revision + yield/round-up at creation; after release the snapshot is immutable; a re-resolution requires an audited revision (ECO) or a new WO.
- `DM-MFG-04`/`RULE-MFG-02` — build/unbuild qty reconciles to component consumption: Σ consumed (yield-adjusted, round-up applied) = Σ required ± documented scrap/tolerance; phantom assemblies are exploded and never stocked (no balance row may exist for a phantom item).
- `DM-MFG-05` — unbuild requires the original-build link or a new unbuild transaction; cost differences post to the configured unbuild variance account; per-line dispositions/valuation follow `DM-MFG-14` (RETURN_TO_STOCK default, SCRAP/HOLD, ORIGINAL_COST default / NRV / MANUAL through FS-05); worksheet-based unbuild adjustments are prohibited (documented interaction [mpw-021]; guard: `409 PROHIBITED_ADJUSTMENT_TYPE` when an inventory worksheet targets an assembly with unbuild cost history — §14 A-7).
- `DM-MFG-06`/`RULE-MFG-03` — WIP completion with backflush consumes the remaining required components; for AVERAGE assemblies the completion value uses the last-purchase-price estimate where the actual average cannot be established and the difference is surfaced as variance (FS-05 contract).
- `DM-MFG-07`/`RULE-MFG-04` — `work_order_wip_balance.wip_value = value_issued − value_completed ± posted WIP close variance` after every WIP posting; WO close reconciles to zero (± posted variance); closed WOs cannot build (WIP) and only non-WIP WOs can be reopened.
- `DM-MFG-08`/`RULE-MFG-05` — outsourced operations link a vendor PO; components transfer/consume at the configured outsourced (`component_location_id`) location; vendor charges ESTIMATED at PO and ACTUAL at receipt are absorbed into build cost; received ≤ ordered.
- `DM-MFG-09`/`RULE-MFG-06` — ECO changes apply to BOM revisions only after approval, are effective-dated, and every implementation writes an audit event and an ECO log status row; no ECO may alter posted documents.
- `DM-MFG-10`/`RULE-MFG-07` — scheduling runs are immutable snapshots; they never mutate WO dates unless `apply` is called (audited); rerun from identical inputs (same scope + policy version + input hash) produces byte-identical `scheduled_operation`/`work_center_load` fixture output.
- `DM-MFG-11`/`RULE-MFG-08` — serialized/lot assembly outputs require new identities equal to built qty; component consumption identities must exist and match qty (delegated to FS-06; mismatch → `409 SERIAL_QTY_MISMATCH`/`LOT_MISMATCH`).
- `RULE-MFG-09` — BOM graph is acyclic at every level: creating/activating a BOM revision that reaches itself through any component (including phantom paths) fails `422 BOM_CYCLE`; BOM explosion depth is limited by tenant setting (`manufacturing.bom.max_depth`, default 20) to bound recursion.
- `RULE-MFG-10` — BOM explosion correctness: for any assembly/qty/date, the preview/explode result's leaf quantities equal the qty-per product along each path after component yield and round-up, with phantom levels multiplied through and sub-assembly stock not consumed by the explosion itself (golden fixtures §10).
- `RULE-MFG-11` — component qty math: `qty_required = round_up_or_exact(qty_per × qty_ordered × phantom_product / (component_yield_percent/100))`; round-up uses `CEIL` in the component's stock UoM precision; zero/negative yield rejected (golden fixtures).
- `RULE-MFG-12` — `qty_built ≤ qty_ordered` per header and line; completion qty cannot exceed remaining; a WO with `qty_scrapped` never inflates built qty.
- `RULE-MFG-13` — operation task sequence: completion out of order rejected when `manufacturing.completion.validate_sequence=true` (default true) unless an explicit override with role `manufacturing.sequence_override` is used (audited).
- `RULE-MFG-14` — operation actual times: `run_minutes_actual ≥ 0`, `setup_minutes_actual ≥ 0`; labor/machine hours = Σ operation completions of the task; actual production start/end are derived from first/last posted completion (AUTO mode) and exposed read-only (no schema column; §14 C-7).
- `RULE-MFG-15` — release guards: WIP flag enabled; assembly/item/location/status active; costing method compatible; BOM revision exists for the WO date; routing (if any) belongs to the item; otherwise `409`.
- `RULE-MFG-16` — void guards: no posted WIP/build/completion transaction linked to the WO; posted ones must be reversed first; void releases commitments; closing a WO does not delete anything.
- `RULE-MFG-17` — matrix parent assemblies are never postable (`422 MATRIX_PARENT_NOT_POSTABLE`); WOs/builds select matrix children only [mpw-010]; matrix children may have their own BOM/routing (FS-01 matrix membership).
- `RULE-MFG-18` — capacity math: `capacity_plan.load_hours` = Σ `work_center_load.load_hours` per bucket; `utilization_percent = load_hours / available_hours × 100` (0 when available=0 → status OVERLOADED if load>0); available hours come from calendar days × capacity (`capacity_hours` per shift) × efficiency.
- `RULE-MFG-19` — finite scheduling never double-books a work centre: Σ load_hours per (work centre, day) ≤ available_hours unless `finite_overflow=ALLOW` (not supported in v1; violations recorded as `violation_reason` instead of overload).
- `RULE-MFG-20` — available-to-build output is deterministic: identical item/location/date/on-hand inputs and policy version produce identical integer `buildable_qty`; floor is applied to whole assembly units; negative inputs clamped to 0.
- `RULE-MFG-21` — tenant isolation: every query/write filters `tenant_id`; no endpoint returns or accepts another tenant's WO/BOM/ECO/schedule ids (INV-25).
- `RULE-MFG-22` — immutability: posted `wip_transaction`, `assembly_build`, `assembly_unbuild` and their lines reject updates/deletes (trigger `trg_*_immutable_posted`); `compat_configuration` rejects UPDATE/DELETE (append-only); corrections only via reversal/compensating document (DM-GLOBAL-04, INV-09).
- `RULE-MFG-23` — audit: every state transition, ECO implementation, scheduling `apply`, cost-template rate change and manual sequence override writes an append-only `audit_event` with actor/reason.
- `RULE-MFG-24` — no cross-context writes: FS-09 writes only `manufacturing.*` (+`platform.finance_journal_intent` indirectly via FS-04/FS-05 posting); no `CAST`/SQL against FS-04/05/08 tables; compatibility reads item attributes/statuses through FS-01/FS-03 contracts and keeps order/customer/region/channel references opaque; enforced by import-linter + schema grants (DM-GLOBAL-02).
- `RULE-MFG-25` — kit/group items are never accepted as assembly build/WO targets (`422 INVALID_ITEM_TYPE_FOR_ASSEMBLY`); kit/group member explosion and T-14 fulfilment are FS-04/FS-01 concerns and must not be duplicated in manufacturing services (O-11).
- `DM-MFG-12` — compatibility evaluation is deterministic against **all** matching rule sets (assembly/BOM **and** order/configuration/customer/region/channel scopes), ordered by scope specificity (order/configuration > customer > region/channel > assembly/BOM), then priority, then rule code; enforcement is configurable (rule > rule-set `enforcement_mode` > tenant `manufacturing.compat.enforcement_default`, default HARD); HARD blocks the guarded action (`409 COMPATIBILITY_VIOLATION`), WARN records an immutable violation, overrides require `manufacturing.compat.override` + reason and are audited.
- `DM-MFG-13` — compatibility gates apply to **every manufacturing/configuration path** (BOM/BOM-revision create+activate, matrix generation, phantom explosion, WO create/update/release/firm, WIP issue/completion/close/backflush, non-WIP build, outsourced manufacturing, ECO implementation, order/configuration boundary, available-to-build); unbuild restores a prior snapshot and is **exempt** from new-configuration validation; each validation persists an immutable `compat_configuration` record.
- `DM-MFG-14` — unbuild disposition is per `assembly_unbuild_component` line and optional: default RETURN_TO_STOCK; SCRAP returns no stock (value to scrap/variance via FS-05); HOLD returns non-committable; `is_used` optional and defaults a USED/REFURB non-sellable/non-committable status; valuation ORIGINAL_COST default, configurable (tenant/assembly/line) to NRV/manual; serial/lot identity and quantity/value conservation preserved; line overrides require `manufacturing.unbuild.dispose` and are audited.
- `INV-33` — **compatibility/reuse integrity:** no HARD-violating configuration reaches a build/posted quantity; rule-set/scope evaluation is deterministic and evidence-recorded; every unbuild line conserves quantity and value, preserves serial/lot identity, and used/scrap/hold dispositions match the posted stock status.
- `RULE-MFG-26` — dual-scope AND semantics: every ACTIVE, effective rule set whose scope matches the configuration contributes (assembly/BOM baseline rules **and** context rules); no scope replaces another; results are independent of rule-set input order; ordering is scope specificity → priority → code; evaluation is deterministic for the same configuration hash + rule-set versions (INV-33).
- `RULE-MFG-27` — rule-type semantics are fixed and unit-tested: `REQUIRES` (component/attribute present), `EXCLUDES` (pairwise incompatibility), `ONE_OF` (exactly one of a set), `MIN_QTY`/`MAX_QTY` (per component/slot/attribute), `CAPACITY` (slot capacity math, RULE-MFG-28), `ATTR_EQ`/`ATTR_RANGE` (typed attribute equality/range with units), `SUBSET_OF` (component set contained in allowed set); invalid/unknown JSON expressions are rejected at save (`422 COMPAT_RULE_INVALID`).
- `RULE-MFG-28` — capacity math: for each slot `s`, Σ(`units_per_component` × selected component qty) ≤ `slot.capacity`; attribute constraints filter eligible components (e.g. socket match, GPU length ≤ max, PSU watts ≥ required, DIMM population min/max, rack-U); comparisons use `NUMERIC(38,12)` (no floats), unit conversion via FS-01 compatible values; `is_required` slots must be populated; violations cite slot/rule ids and offending components.
- `RULE-MFG-29` — enforcement precedence: per-rule `severity` > rule-set `enforcement_mode` > tenant setting `manufacturing.compat.enforcement_default` (default HARD); `INHERIT` defers to the next level; HARD blocks the guarded action before any document/ledger effect; WARN allows it but records the violation on the immutable validation record and emits `manufacturing.config.violation`.
- `RULE-MFG-30` — override: only `manufacturing.compat.override` holders may override a HARD result; a mandatory non-empty `override_reason` is required; tenant `manufacturing.compat.allow_override` must be true; the validation record becomes `OVERRIDDEN` with `override_by/override_reason/overridden_at` and the action is audited; overriding is impossible when the same caller also lacks the guarded action's own scope.
- `RULE-MFG-31` — validation evidence: every validation persists one append-only `compat_configuration` row with `configuration_hash`, ordered matched rule sets/rules + versions, snapshots, result and override refs; identical hash + rule-set versions yields an identical outcome (idempotent/replayable) and a new record per validation request (never updated); records are the L3-gate evidence for INV-33.
- `RULE-MFG-32` — generic path matrix is mandatory: the gate is invoked exactly as listed in DM-MFG-13, with the correct `context` (`BOM/WO/BUILD/OUTSOURCED/ORDER/ECO/ATB`); unbuild is exempt (no new-config validation); matrix assembly generation only creates option combinations that pass (invalid children rejected/flagged); phantom-flattened components are validated and phantom members remain subject to parent rules; ATB excludes invalid configurations from buildable quantities.
- `RULE-MFG-33` — order/configuration boundary: configure-to-order validation accepts opaque order/customer/region/channel refs, evaluates all applicable context rule sets and must be called **before** `order.demand` demand commit; FS-09 exposes `POST /v1/manufacturing/configurations/validate` for that boundary and stores the evidence; no order/customer table is read or written (D3 boundary, no new dependency).
- `RULE-MFG-34` — only ACTIVE rule sets effective on the validation date (and effective/active rules within them) are enforced; DRAFT/RETIRED content is never enforced; an ACTIVE rule set's content is immutable (edit by retiring and creating a new version) and each validation record stores the rule-set versions used.
- `RULE-MFG-35` — attribute typing: `compat_attribute_value` sets exactly the typed column matching the definition (`TEXT`→`value_text`, `NUMERIC`→`value_number`, `BOOL`→`value_bool`, `SELECT`/multi-valued→`value_json`); SELECT values must be members of `choices`; units are validated against the definition's unit; mismatch → `422 COMPAT_ATTRIBUTE_TYPE_MISMATCH`.
- `RULE-MFG-36` — scope-reference validation: `ASSEMBLY`→existing assembly item, `BOM_REVISION`→existing revision, `CONFIGURATION/ORDER/CUSTOMER/REGION/CHANNEL`→opaque non-empty external refs (no FK); invalid/missing refs → `422 COMPAT_SCOPE_INVALID`; tenant isolation applies to every scope row (INV-25).
- `RULE-MFG-37` — unbuild disposition matrix: `RETURN_TO_STOCK` requires resolvable `return_status_id` (USED/REFURB default when `is_used=true`, else the recorded/available status or configured default) and target defaults (or explicit target location/bin); `SCRAP` must have no target/return-status columns and consumes serial/lot as scrapped; `HOLD` requires a hold/non-committable status; `is_used=true` requires `condition_code_id` + `return_status_id`; `allow_resale` defaults false and only used/refurb conditions may set it; invalid combinations → `422 UNBUILD_DISPOSITION_INVALID`.
- `RULE-MFG-38` — unbuild valuation: ORIGINAL_COST (default) uses the original build cost snapshot (`assembly_build_component.unit_cost`/linked build); NRV uses the configured source (current cost / last-purchase-price proxy — ASSUMPTION A-14); MANUAL requires `unit_value`; policy resolution tenant → assembly-level map → per-line override, with per-line override requiring `manufacturing.unbuild.dispose`; differences post through FS-05 inside the unbuild transaction; per line `qty_restored × unit_cost_used ± value_delta = posted value` (INV-02/INV-33).
- `RULE-MFG-39` — serial/lot lifecycle: returned identities keep their identity and gain lifecycle history `IN_STOCK_USED` (used/refurb return), `SCRAPPED` (scrap) or `HOLD` (hold, non-committable); quantity conservation per line and per identity (DM-MFG-11/INV-19); no duplicate active position per serial; used statuses default non-sellable/non-committable.
- `RULE-MFG-40` — unbuild reversal: full reversal only in Phase 1; requires every returned component still in the recorded disposition status, quantity, condition and location/bin (HOLD components must not have moved); posts compensating movements and disposition-value compensation; partial reversals / moved-used components are rejected (`409 UNBUILD_NOT_REVERSIBLE`); disposition evidence retained.
- `RULE-MFG-41` — REWORK/remanufacture is deferred to the FS-14 repair flow; FS-09 has no REWORK disposition, posting type or event and never routes unbuilt components to a repair order (no new dependency).
- `RULE-MFG-42` — Δ tables tenant isolation/audit: `compat_*` and `condition_code` rows are tenant-scoped + RLS (INV-25), rule-set/attribute/slot/condition changes and every override are audited (`audit_event`); evidence records are append-only (INV-09).
- `RULE-MFG-43` — condition registry: codes are unique per tenant and seeded (`NEW/USED_A/USED_B/USED_C/REFURB/SCRAP`); `is_used` conditions default non-sellable/non-committable; inactive conditions are rejected for new dispositions/returns; scrap maps to a scrapped serial/lot lifecycle (RULE-MFG-39).
- `RULE-MFG-44` — compatibility evaluation budget/determinism: evaluating a configuration with up to 100 ACTIVE rules over 10 components has p95 ≤ 50 ms on the reference compose stack (ASSUMPTION A-20); caches keyed by tenant + rule-set versions are invalidated on rule-set activate/retire and never change results.

## 6. API surface

Base path `/api/v1`; JSON; UTC timestamps; quantities as decimal strings (`NUMERIC(38,12)`); money decimal strings.
Auth scope per endpoint; posting commands require `Idempotency-Key`; document mutations support `If-Match: version`
(412 on stale). Errors use RFC 9457 envelope (`code`, `message`, `details`, `correlation_id`, `trace_id`);
FS-09 domain codes: `INVALID_STATE_TRANSITION`, `VALIDATION_FAILED`, `POLICY_VIOLATION`, `INSUFFICIENT_AVAILABLE`,
`INSUFFICIENT_ON_HAND`, `SERIAL_QTY_MISMATCH`, `LOT_CONFLICT`, `DEPENDENT_DOCUMENTS`,
`BOM_CYCLE`, `BOM_REVISION_OVERLAP`, `PHANTOM_NOT_STOCKABLE`, `MATRIX_PARENT_NOT_POSTABLE`, `WIP_DISABLED`,
`WIP_METHOD_INCOMPATIBLE` (mapped to `POLICY_VIOLATION`), `WO_OVER_BUILD`, `DOMAIN_DISABLED`, and the
Δ-CFG/Δ-REUSE codes `COMPATIBILITY_VIOLATION`, `COMPAT_RULE_INVALID`, `COMPAT_ATTRIBUTE_TYPE_MISMATCH`,
`COMPAT_SCOPE_INVALID`, `COMPAT_ATTRIBUTE_IN_USE`, `COMPAT_RULE_LIMIT`, `UNBUILD_DISPOSITION_INVALID`, `UNBUILD_NOT_REVERSIBLE`.

**Compatibility-guarded routes (Δ-CFG):** every route that creates/activates a configuration or posts a build/issue/
completion (BOM + revision activation, matrix generation, WO create/update/release/firm, WIP issue/completion/close/
backflush, assembly build post, outsourced receive, ECO implement, ATB calculate; **not** unbuild) accepts an
optional `compat` request block `{context, context_refs{order_ref,customer_ref,region_ref,channel_ref}, as_of,
override{reason}}`. Missing block → the server validates with the assembly/BOM rules and the request's context refs
when supplied. HARD result without a valid override → `409 COMPATIBILITY_VIOLATION` with
`details.violations[{rule_set_code, rule_code, severity, component_refs, slot_code, message_code}]` and the
`configuration_id`; WARN returns success plus `compat{result:"WARN", configuration_id, violations[]}`. An
`override{reason}` requires the `manufacturing.compat.override` scope and stamps the evidence record as
`OVERRIDDEN`. Validation records are immutable and replayable by `configuration_hash` (RULE-MFG-31).

## 12. Rollback

- **Flag-first, immediate:** `manufacturing.wip.enabled=off` then `manufacturing.enabled=off`. With flags off,
  writes return `409 DOMAIN_DISABLED`, jobs/event handlers stop, reads/plans remain available; no data loss.
- **Deploy previous image**; migrations are additive and N-1 compatible (old code ignores new tables; no dropped
  columns). No prod down-migration; down-migrations tested only in CI/sandbox.
- **Open work orders:** before disabling, close/short-close or void all open WOs; the guard rejects disabling
  while any WO is RELEASED/IN_PROCESS/BUILT per runbook (rollback statement in manifest). Posted WIP/build docs
  stay immutable/readable; corrections only via reversals/compensating documents (never delete ledger rows).
- **Data compensation:** reversed WIP/build transactions, compensating inventory adjustments via FS-04, cost
  corrections via FS-05; WIP balances rebuilt from ledger by `mfg.wip.reconcile`.
- **Δ-CFG/Δ-REUSE rollback:** enforcement is configurable, so operational rollback = set tenant
  `manufacturing.compat.enforcement_default=WARN` (and/or rule-set/rule `enforcement_mode=WARN`) without deleting
  evidence; rules/slots/attributes are versioned and retired, never deleted; `compat_configuration` records remain
  append-only evidence. Unbuild dispositions/valuation posted rows are immutable: correct by full unbuild reversal
  (where components are unmoved) or by compensating inventory/cost documents via FS-04/FS-05 — never by editing
  posted lines; condition codes are deactivated, not deleted; tenant settings restore defaults.
- **Consumers:** `check-env` blocks FS-10/11/12/15 automatically while status ≠ verified; communicate via
  `platform.events`/release notes and re-enable only after exit gate passes.
