## 2. Scope

**In scope (backend):**
- 21 reporting views (`reporting` schema, `SELECT`-only) exactly as specified in DATA-MODEL §17, joining the
  core read models owned by earlier sets with item/location/status/vendor/customer-ref dimensions.
- Refresh strategy per view: transactional projections read directly (plain views over materialised balance/
  cost read models) vs reporting-owned materialised views with an owning refresh job and documented max
  staleness (DM-RPT-02/04).
- Minimal Reporting API: report endpoints for stock ledger, valuation summary/detail, snapshot,
  negative inventory, back-status/pending fulfilment, activity detail, turnover, profitability, lot expiry,
  serial history, consigned balance, quality inspections, purchase history, manufacturing workbench,
  planning workbench, ATP workbench, balance search and detail search; plus an additive report catalogue,
  the two views without a baseline endpoint, and a paged export endpoint (no UI rendering).
- Query contract: explicit filter allow-lists, tenant + data-scope enforcement, required date/dimension
  bounds for ledger-scale views, stable cursor pagination (no offset paging on ledger), decimal-string
  quantities/money, UTC timestamps, `fields=` projection, freshness header/metadata.
- Permission gating: `reporting.read` for all endpoints; `reporting.cost.view` for cost/margin/value views;
  `reporting.export` for export; data scopes (`LOCATION/CLASS/DEPARTMENT/SUBSIDIARY`) applied to all queries.
- Freshness/reconciliation: per-view SLOs, `reporting.view.refreshed`/`reporting.refresh.failed` events,
  previous snapshot served on refresh failure, reconcile-exact invariant against source read models.
- Migration `alembic:0029_reporting_views` (views/materialised views/grants) and `alembic:0030_rls_grants_verify`
  (final RLS/grant verification + deferred-FK orphan check); **no base-table migrations**.
- Contract surface `reporting.readmodels@1.0.0`: view column allow-list, endpoints, events, jobs, freshness
  metadata.

**Out of scope / deferred:**
- SuiteAnalytics workbooks/datasets/report rendering, dashboards, Control Tower, printing/presentation
  (`DEFERRED-ANALYTICS`, `DEFERRED-UI`) — Phase 2; the views/API here are the data layer they will consume.
- Any write path: no INSERT/UPDATE/DELETE, no materialised-view writes from request handlers, no schema
  changes to base tables; reporting never posts, comments, or changes stock.
- Source-context business logic: authoritative quantities/valuation stay in FS-04/FS-05; authoritative ATP and
  available-to-build calculations stay in FS-10/FS-09. FS-15 views are read models that must reconcile.
- `v_available_to_build` (V-21) is a **pass-through reporting projection** of the FS-09
  `manufacturing.execution@1.0.0` ATB contract (policy `atb-v1`, `GET /v1/available-to-build` / batch calculate,
  event `available_to_build.calculated`): reporting consumes FS-09 results and never re-implements or simplifies
  the ATB formula; a cached/simplified value is never labelled canonical (see §4 V-21, §5 rule below).
- Mobile/UI/SCM Mobile (permanently excluded, D8); external BI export integrations (Phase 2).

Read-model rules (DATA-MODEL §17 and ARCHITECTURE §5.7/§7.1):

- `DM-RPT-01`: views are `SELECT`-only; ownership of view definitions is `reporting`, while the underlying
  tables stay owned by their source contexts (see §14 conflict note for DM-RPT-01 wording).
- `DM-RPT-02`: every materialised view is refreshable and documents max staleness (table above + OpenAPI).
- `DM-RPT-03`: reporting queries always carry tenant + data-scope filters; cost/margin views require
  `reporting.cost.view`.
- `DM-RPT-04`: no view recomputes authoritative quantities by scanning the whole ledger at request time;
  heavy aggregation is materialised (V-04, V-11, V-12, V-16, V-21). Plain views read already-materialised
  read models (`inventory_balance*`, `item_cost`, `atp_projection`, …).
- `RULE-RPT-ATB`: V-21 carries `policy_version` (`atb-v1`) and `input_hash` from FS-09 on every row; if the
  FS-09 ATB contract is unavailable or the cache is stale, the view serves the last refreshed projection with
  `degraded=true` freshness metadata and **never** falls back to a simplified local formula. A simplified
  single-level value (e.g. top-level immediate components only) may only be exposed as
  `approximation=true` with an explicit limitation description and a link to the authoritative
  `GET /v1/available-to-build` API — it is never represented as `v_available_to_build` canonical data.
- Views are created with `security_invoker=true` (`ASSUMPTION`/`EXT` PG16 mechanism) so base-table RLS and
  tenant policies apply to every query; `reporting` schema grants only `SELECT` to the app role
  (`INV-09`/`DM-GLOBAL-03` analogue for views).
- View column changes are additive only; `reporting.readmodels@1.0.0` column allow-list is the contract.

## 5. Services, rules and invariants

Use cases (service method → behavior):

| Use case | Inputs | Behavior / validation | Emits |
|---|---|---|---|
| `query_view` | report id, filters, cursor, limit, `fields`, data scope | resolves the view from a static registry; validates filter/sort allow-list (unknown filter → 400); enforces tenant/data scope + cost permission; applies deterministic ordering; returns rows as decimal strings + `next_cursor` + freshness metadata | — (read) |
| `search_inventory_balances` | item/location/status/ownership dimensions, date/as-of, cursor | reads `v_inventory_balance`; requires tenant + ≥1 dimension filter; cursor pagination; no offset on ledger-scale views | — |
| `search_inventory_details` | item/location/transaction/bin/lot/serial/date filters | reads `v_inventory_activity_detail`; requires date bound (ARCHITECTURE §5.9); pagination | — |
| `export_view` | report id, filters, format (`CSV`/`NDJSON`), page token | applies same scope/filters as query; streams a bounded page of rows (max `reporting.export_max_rows`); returns `Content-Type` per format + continuation token; no report rendering/formatting beyond serialisation | — |
| `get_freshness` | report id | returns `{view, materialised, last_refreshed_at, max_staleness_seconds, age_ms}` from `job_run`/refresh metadata | — |
| `refresh_views` (job) | tenant, view set | refreshes materialised views concurrently with unique indexes; writes refresh metadata; on failure keeps the previous snapshot/materialisation and raises `reporting.refresh.failed` | `reporting.view.refreshed` / `reporting.refresh.failed` |
| `refresh_atb_projection` | tenant, assembly/location scopes | calls the FS-09 `manufacturing.execution` ATB batch contract (`POST /v1/available-to-build/calculate`, policy `atb-v1`) and/or consumes `available_to_build.calculated`; stores `buildable_qty`, `limiting_component`, per-level breakdown, `policy_version`, `input_hash`, `as_of` in the V-21 cache; never computes ATB locally; records staleness/degraded flag | `reporting.view.refreshed` (with `view_name=v_available_to_build`) |
| `reconcile_readmodels` (job) | tenant, sample/full mode | recomputes each view's reconciliation aggregate against the source read models (ledger Σ, balance Σ, cost ledger Σ); drift > 0 → P1 alert + audit; never repairs by writes | audit/alert |
| `reporting_refresh_failure` handling | failed refresh | serves previous materialisation, returns `refresh_failed=true` freshness metadata, alerts; retries with backoff | `reporting.refresh.failed` |

Business rules and invariants:

- `DM-RPT-01`: read-only contract — reporting functions/endpoints only issue `SELECT`; the DB role has no
  `INSERT/UPDATE/DELETE` on `reporting` views; any write verb on a reporting path returns `405 METHOD_NOT_ALLOWED`
  (or `403 FORBIDDEN_SCOPE` when RBAC denies first) — acceptance criterion of the manifest.
- `DM-RPT-02`: materialised views are refreshed by `reporting.refresh_views`; max staleness per view is
  documented (SLO table below) and returned by `GET /v1/reports`/`get_freshness`.
- `DM-RPT-03`: every query is tenant + data-scope filtered; cost/margin views (`v_inventory_valuation*`,
  `v_inventory_turnover_inputs`, `v_inventory_profitability_inputs`, cost columns of `v_stock_ledger`/
  `v_inventory_activity_detail`) require `reporting.cost.view`; export requires `reporting.export`.
- `DM-RPT-04`: request-time queries never scan the full ledger for aggregation; only plain views over
  materialised read models are allowed; expensive aggregation is materialised.
- `INV-03`/`INV-10`/`DM-GLOBAL-09` reconcile-exact: for every reporting view, aggregate quantities/values equal
  the underlying read models (balances == Σ ledger; value == Σ cost ledger == item_cost; valuation summary ==
  valuation detail; stock ledger == activity detail totals); exit gate `test_reconcile_exact.py` asserts zero
  drift on seeded fixtures.
- Read-only + no write path: no materialised view is written by an API request; refresh only by job; no
  base-table DDL in FS-15 migrations (acceptance: "any write verb → 405/403; grants reject writes").
- Freshness SLOs (documented in OpenAPI; alarm on breach):
  - Transactional projections (`v_stock_ledger`, `v_inventory_balance`, `v_inventory_snapshot`,
    `v_negative_inventory`, `v_open_commitments`, `v_backorders`, `v_pending_fulfillment`,
    `v_inventory_activity_detail`, `v_lot_expiry`, `v_serial_history`, `v_consigned_balance`,
    `v_quality_inspection_status`, `v_purchase_history`): p95 data age ≤ **5 s** after commit (direct views).
  - Cost/valuation (`v_inventory_valuation*`, `v_inventory_turnover_inputs`, `v_inventory_profitability_inputs`):
    p95 age ≤ **5 min** after posting commit, and ≤ **26 h** for daily-bucketed turnover/profitability rows.
  - Planning/ATP/WO (`v_atp_current`, `v_planning_workbench`, `v_manufacturing_workbench`,
    `v_available_to_build`): p95 age ≤ **15 min** after source event/run. For V-21 the source event is FS-09
    `available_to_build.calculated` (or the FS-09 batch calculate call); the SLO is measured from the FS-09
    `as_of`/event time, and the response always carries the FS-09 `policy_version`.
  - On refresh failure the previous snapshot remains served; freshness metadata marks `degraded`.
- Query contract: cursor pagination only (no offset on ledger/activity), `limit` max 500 (ARCHITECTURE §5.9);
  explicit filter/sort allow-lists; unknown filter → 400; `fields=` allow-list; UTC timestamps; quantity/money
  strings; stable ordering by `(business_date, id)` or domain key.
- Performance budgets (framework §9/ARCHITECTURE §7.1): balance search p95 ≤ 150 ms; snapshot/valuation p95
  ≤ 500 ms; heavier materialised views p95 ≤ 1 s; export streams paged rows without loading the full result.
- Reconciliation failure is a P1 (valuation integrity zero-tolerance); refresh failure is an alert only, with
  last-good data served.

State machines (this set owns no documents):
- Document state machines: **none** (read-only set; no posting, no document aggregates).
- Operational read-model lifecycle per view: `FRESH → REFRESHING → FRESH` and `FRESH → STALE/FAILED → FRESH`
  (retry); the served data always remains the last successfully refreshed snapshot; failures emit
  `reporting.refresh.failed` and raise the freshness age.

## 12. Rollback

- Flag off `reporting.readmodels.enabled`: API stops serving, refresh jobs stop, views remain in place
  (droppable/recreatable) with no effect on base tables.
- Migrations are additive and view-only: down-migration drops materialised views/views then the schema;
  never touches base tables. No prod down-migration needed for rollback (flag + redeploy prior image).
- No data compensation is ever needed: reporting has no writes; last-good data continues to be served if a
  refresh fails.
- Dependants: FS-15 is the last Phase-1 set (no in-graph dependants); external BI consumers are Phase 2 and
  use the versioned contract.
