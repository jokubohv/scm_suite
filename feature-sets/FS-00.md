## 1. Objective and source coverage

FS-00 delivers every backend capability that all domain contexts need but none owns: multi-tenant
isolation with PostgreSQL RLS, identity/RBAC/data scopes, an immutable audit trail, doc/item number
allocation, per-tenant feature flags and settings, the transactional outbox + relay, jobs/scheduler,
request idempotency, attachments metadata, declarative approvals, document links, custom fields, the
finance boundary (journal intents + period status, D2) and the order boundary v0 stub contracts (D3).
Under **Δ-MT** FS-00 also owns the SaaS identity layer (`EXT`): one global identity per real person,
per-tenant membership principals with independent lifecycle/revocation, invitations, refresh-token
sessions and tenant selection/switch — without weakening tenant isolation (the active tenant comes only
from the verified token; identity/session paths are auth-only and return no tenant business data).
Under **Δ-RBAC** FS-00 also owns the complete authorization model: the authoritative 255-scope
capability catalogue (`design/permissions.json`), 7 non-editable/cloneable system role templates, custom
role lifecycle (create/clone/inactivate, permission and data-scope mapping), effective-dated role
assignment to memberships, last-admin/privilege-escalation guards, SoD enforcement (assignment + approval
time) and effective-permission resolution. Under **Δ-SSO** (`EXT`) FS-00 also owns **Dex as the OIDC
identity broker and per-company (per-tenant) SSO**: authorization-code + PKCE flows against per-connection
Dex issuers federating SAML 2.0/OIDC/LDAP-AD company IdPs, identity linking/JIT provisioning, verified-email
+ domain policy, group→role mapping bounded by RBAC, enforced-SSO/local-password fallback and break-glass —
while the platform remains the **only** authorization/token issuer (Dex tokens are never accepted as
platform bearer tokens). It is independently valuable because it is the only root set:
deploying it yields a hardened, auditable, tenant-safe, multi-tenant-user platform whose contracts every
other set consumes, and whose L3 exit gate proves RLS, tenant/user isolation (`INV-30`), authorization
completeness (`INV-31`) and SSO/authn integrity (`INV-32`), append-only privileges and the outbox/job
runtime on a greenfield environment.

## 2. Scope

**In scope (backend):**
- Tenant registry + **platform-admin** provisioning/suspend/reactivate/offboarding lifecycle; `tenant_setting`
  namespaced preferences; provisioning seeds settings/catalogue/roles/sequences/flags/fiscal-currency
  projections and a **bootstrap admin invitation** (`tenant.provisioned`).
- PostgreSQL RLS on every platform table + `SET LOCAL app.tenant_id` connection contract + raw-SQL
  isolation tests; global reference rows under the reserved `SYSTEM_TENANT_ID` are read-only.
- **Δ-MT identity model (`EXT`):** global `user_identity` (one row per real human/login identity:
  email, password/SSO subject, MFA flag, global status, `is_platform_admin`) + per-tenant `app_user`
  membership (`identity_id`, `membership_status (INVITED/ACTIVE/SUSPENDED)`, `joined_at`, `invited_by`,
  `token_version`); roles/data-scopes stay per membership, never global (DM-PLAT-12/13).
- **Δ-MT authentication/session flows:** `POST /api/v1/auth/login` (single membership → token pair;
  multiple → `TENANT_SELECTION_REQUIRED` + 5-min selection token + `tenant_choices[]`; none →
  `403 NO_ACTIVE_MEMBERSHIP`), `POST /auth/select-tenant`, `POST /auth/switch-tenant`,
  `POST /auth/refresh` (rotating refresh token, replay detection), `POST /auth/logout` (revoke session),
  `GET /api/v1/me`, `GET /api/v1/me/tenants`; JWT claims `sub`=identity, `uid`=app_user, `tid`=tenant,
  `tv`=token_version, `jti`; active tenant comes **only** from the verified token claim.
- **Δ-MT invitations:** tenant-scoped `tenant_invitation` with single-use expiring hashed token,
  intended roles; accept creates identity (if new) + exactly one membership + roles atomically
  (DM-PLAT-14).
- **Δ-MT sessions/revocation:** hashed rotating refresh tokens per `(session, tenant)`; session revoke
  (self/admin), membership suspend/disable → `token_version++` + all sessions revoked; revalidation on
  refresh and every write.
- **Δ-MT administration:** platform-admin tenant APIs under `/api/v1/platform/*` (global
  `is_platform_admin` + `platform.tenant.manage`, audited with `SYSTEM_TENANT_ID`); tenant-admin user
  and invitation APIs under `/api/v1/admin/users*` + `/api/v1/admin/invitations*` with
  `platform.users.manage` / `platform.invitations.manage` / `platform.sessions.revoke`; tenant roles can
  never grant platform-admin.
- **Δ-RBAC authorization model:** authoritative 255-scope capability catalogue provisioned per tenant from
  `design/permissions.json` (`permission_scope` + `is_platform_only`/`is_assignable`/`owner_feature_set`);
  7 system role templates (`role.is_template=true`, non-editable, cloneable) + custom roles
  (`role.is_editable=true`); `role_permission` scope sets; `user_role` effective-dated assignments per
  membership; `user_data_scope` row-level restrictions (LOCATION/CLASS/DEPARTMENT/SUBSIDIARY + descendants).
  Role lifecycle (create/clone/update/inactivate, permission + data-scope mapping), effective-permission
  resolution (union of role/app-key scopes; immediate effect), deny-by-default route guards (exactly one
  catalogue scope per non-public route; explicit public/self-service allowlists), grant-safety guards
  (scope-not-assignable, privilege escalation, last active tenant admin), SoD policy (14 hard pairs +
  requester≠approver; tenant setting `rbac.sod_enforcement=HARD` default) and audit on every change.
- **Δ-SSO authentication federation (`EXT`/`ASSUMPTION`):** **Dex OIDC broker** (authorization-code + PKCE)
  with **one isolated issuer per `tenant_sso_connection`** in the reference deployment (shared Dex allowed for
  dev/test/small fleets); Dex federates the company's **SAML 2.0 / OIDC / LDAP-AD** IdP via per-connection
  connectors generated from `connector_config` + secret-store refs. Public flows: `GET /api/v1/auth/providers`,
  `POST /api/v1/auth/sso/start` (state/nonce/PKCE S256, 5-min TTL in Redis), `GET /api/v1/auth/sso/callback`
  (single-use state/nonce validation, code exchange via Dex, ID-token validation issuer/audience/JWKS/exp/nonce/
  `email_verified`, domain policy, identity link/JIT, group→role mapping, then **platform** access JWT + rotating
  refresh session or `TENANT_SELECTION_REQUIRED`); typed, audited SSO errors; **local password (Argon2id)
  fallback retained** for non-SSO tenants/bootstrap/break-glass, rejected for members of enforced-SSO tenants.
- **Δ-SSO administration:** tenant-scoped `tenant_sso_connection` lifecycle (DRAFT→TESTING→ACTIVE→DISABLED/
  ERROR; create/update/delete-if-unlinked/test/rotate-secret/provision-refresh Dex issuer + discovery/JWKS
  health), identity links (`user_identity_link`) and group→role mappings (`sso_group_role_map`) under
  `platform.sso.manage` (writes) / `platform.sso.read` (reads); connection tests/secret rotations audited;
  **no endpoint returns client secrets or private key material** (secret refs only).
- Immutable audit trail (`audit_event`, append-only, before/after JSONB diffs, request/trace/correlation ids,
  source=API/JOB/IMPORT/INTEGRATION); audit writer helper used by every module.
- `number_sequence` allocator: per `(tenant, doc_type, scope_key, period_key)`; NON_GAPLESS default,
  GAPLESS opt-in for externally regulated docs; reset policies NEVER/ANNUAL/MONTHLY; never reused.
- `feature_flag` per tenant (default off) + tenant-setting resolver with precedence
  document → item/location → tenant → system default.
- Transactional outbox (`outbox_event`) + relay contract (at-least-once, per-aggregate ordering),
  consumer checkpoints (`event_consumer_checkpoint`), replay endpoint.
- Jobs: `job_definition` / `job_run`, in-process scheduler with advisory-lock leader election,
  RQ worker dispatch, retry/backoff, singleton locks, cursor chunking, dead-letter + alert.
- Idempotency middleware and `idempotency_key` lifecycle (replay, conflict, in-flight, TTL purge).
- Declarative approval engine (`approval_definition` / `approval_request` / `approval_action`),
  SoD, sequential/parallel steps, delegate/recall; publishes `document.*` approval events.
- `document_link` typed provenance graph (append-only) and `attachment_metadata` registry
  (metadata only; blob lives in object storage under `tenant/<id>/` prefixes).
- Custom-field registry (`custom_field_def` / `custom_field_value` EAV with typed columns and
  validation) exposed as a platform service for domain modules.
- Currency/FX/fiscal-period reference projections (read-only to app role) + finance sync endpoints.
- **D2 `platform.finance`**: `FinancePort` contract, `NullFinanceAdapter` (default) persisting **one
  append-only `platform.finance_journal_intent` row per GL-instruction line** inside the posting
  transaction (DM-PLAT-11), read-only `GET /api/v1/finance/journal-intents`, period-status reads.
- **D3 `order.demand@0.1.0` / `order.supply@0.1.0`**: Pydantic command/event models, JSON Schemas,
  in-memory test doubles and provider contract test. FS-00 publishes and validates the shapes and — per
  the 0A boundary fix — also serves the **read surface** the replenishment set needs:
  `GET /api/v1/order/demand/open` (paged required-by-dated OPEN demand from the external order system via
  the `OrderDemandAdapter`; `StubOrderDemandAdapter` + seeded fixtures in Phase 1) and the
  `order.demand.changed` v0 event for cache invalidation. FS-04 implements the inventory side of the
  commands (HTTP paths/events are FS-04's).
- `/healthz`, `/readyz`, `/internal/deps`, `/internal/outbox/replay` internal surfaces used by L2 gates
  and operations; error envelope + correlation ids; API conventions (auth, pagination, If-Match, ETag,
  rate limits, decimal strings, UTC).

**Out of scope / deferred:**
- Any domain table or business posting (item, pricing, ledger, costing, procurement, manufacturing,
  WMS, quality, consignment, extensions) — owned by FS-01…FS-14.
- UI/mobile/analytics/integration work; role/permission/feature-enablement screens; SuiteFlow-style
  workflow customisation (deferred; declarative approvals only, D-23/O-14); SCM Mobile (D8).
- `wms.device_session` / `wms.warehouse_cart` — not owned here; FS-11 owns them (`EXT`, D8/§5 envelope).
  FS-00 provides only `app_user` identity that a future device client could authenticate as.
- GL/chart of accounts/journals/period close/tax/payments (D2/PLAN §12); customer master/sales-order
  domain (D3); FX revaluation (D-13).
- Item/UoM reference seeds (`uom_type`, `uom` defaults, item taxonomy) — FS-01 owns them
  (`DATA-MODEL.md` §21.2); FS-00 seeds only global `currency` + the permission/role/flag/sequence catalogue.
- Data import tooling/Item Creation Assistant (DEFERRED-INTEGRATION); audit hash-chain/tamper-evidence
  is **not specified** by the design docs (see §14.1 Q3).
- **Δ-MT deferred envelope (addendum §9):** SCIM implementation, external IdP admin UI, tenant
  self-service signup, billing/plan tiers/quotas, custom domains, tenant-switch UI/user-role-invitation
  screens, cross-tenant analytics and audited support-impersonation tooling, enterprise tenant
  hierarchy/groups, and all mobile clients — Phase 2+; no Phase-1 backend byteams change.
- Local password *policy* hardening (reset/email verification/complexity) beyond Argon2id hashing and the
  retained fallback mode — Phase 2; Phase 1 supports Dex-SSO tenants plus local password fallback
  (`password_hash NULL` for SSO-only identities) as configured.
- **Δ-SSO deferred envelope (addendum §1):** SCIM provisioning, IdP-initiated (unsolicited) SAML, RP-initiated
  single-logout across company IdPs, multiple simultaneous IdPs per single login, just-in-time admin
  elevation, per-field ABAC (unchanged) and SSO admin UI screens — Phase 2+; no Phase-1 backend change.
- **Δ-RBAC deferred envelope (addendum §8):** role/permission admin UI, SuiteFlow-style workflow
  customisation (D-23), attribute-based access control (policy engine), per-field/row-level ACLs beyond
  documented data scopes, external IdP/SCIM group→role mapping, delegated administration hierarchies and
  an approval-workflow visual designer — Phase 2+; no Phase-1 backend byteams change.

Contract rules: additive changes only within a major version; a breaking change requires a new version
plus the consumer impact list from `python tools/feature_sets.py who-depends-on --contract <name>`.
The two `@0` order contracts are explicitly preview: breaking changes require a version bump and
coordinated updates of FS-04/08/09/10/11 consumer fixtures (`FEATURE-SETS.md` §8.1 Δ-2).

**Δ-MT contract rule:** the identity/membership/invitation/session/auth additions are **additive within
`platform.core@1.0.0` and `platform.events@1.0.0`** (new optional service facades, endpoints and event
types only; no renamed/removed members, no new contract name, **no manifest edge/gate change**).
Consumers keep resolving `tenant_id`/`app_user_id` from the request context exactly as before; only FS-00
owns the identity/session tables. `feature_sets.py who-depends-on --contract platform.core` must stay
unchanged; any future breaking auth change requires a major bump + consumer list.

**Δ-SSO contract rule:** Dex is an **external authentication boundary** (per-tenant OIDC broker); the
platform keeps issuing its own JWT/refresh tokens, so `platform.core@1.0.0` / `platform.events@1.0.0` gain
only additive SSO endpoints/events/facades — **no DAG edge, contract name or version change**; Dex tokens
or Dex groups are never accepted as platform authorization. Secret material lives only in the secret store
(DB stores `*_secret_ref` pointers).

**Δ-RBAC contract rule:** the permission catalogue, role administration and SoD additions are **additive
within `platform.core@1.0.0` / `platform.events@1.0.0`** (new endpoints/event types/service facades only;
existing scope strings are frozen and only added to). `design/permissions.json` is the single authority:
every non-public route in every spec declares exactly one catalogue scope; the plan gate
`python tools/feature_sets.py permissions` fails CI on any missing/unknown/duplicate scope. Consumers
resolve capability+data scopes from the request context per call — no set may read another set's RBAC
tables.

Business rules and invariants (cite DATA-MODEL ids):

- `DM-PLAT-01`: any insert/update whose `tenant_id` ≠ session tenant context is rejected (RLS + `before_flush` guard).
- `DM-PLAT-02`: `audit_event`, `approval_action`, `document_link`, `outbox_event`, `finance_journal_intent` rows can never be updated/deleted by the app role (trigger + grants, DM-GLOBAL-03).
- `DM-PLAT-03`: a document has at most one `approval_request`; actions are append-only; an actor cannot approve their own request (SoD).
- `DM-PLAT-04`: numbers are unique per `(tenant,doc_type)` document numbers and never reused, including after reversal/void.
- `DM-PLAT-05`: flag changes are audited with before/after; a disabled flag makes every write endpoint of that domain return `409 DOMAIN_DISABLED`.
- `DM-PLAT-06`: idempotency rows are unique per `(tenant,endpoint,key)`; same key with different `request_hash` → 409.
- `DM-PLAT-07`: `outbox_event.aggregate_version` strictly increasing per aggregate (unique constraint).
- `DM-PLAT-08`: `fiscal_period` ranges never overlap; CLOSED/LOCKED periods cannot be reopened without a new `source_version` from finance.
- `DM-PLAT-09`: `tenant.status ≠ ACTIVE` blocks all writes (reads allowed for export); offboarding never cascade-deletes ledger/audit.
- `DM-PLAT-10`: `exchange_rate` and `fiscal_period` writes only via `platform.internal` finance-sync endpoint as a service principal; app role is read-only.
- `DM-PLAT-11`: every posting that emits GL instructions persists exactly one `finance_journal_intent` row per instruction line inside the posting transaction, uniquely keyed by `(inventory_transaction_id, posting_rule_id, intent_line_no)` and linked to the posting `idempotency_key`; intents are append-only, status only transitions `RECORDED → ACKNOWLEDGED/REJECTED/SUPERSEDED`, transaction refs are logical (validated by the posting engine/reconcile, never an upward FK).
- `RULE-PLAT-09`: a replayed/retried posting inserts no duplicate intent lines (unique posting linkage is the second line of defence behind `idempotency_key`).
- `RULE-PLAT-10`: an instruction set with unequal debit/credit totals is rejected (`422 UNBALANCED_JOURNAL_INTENT`) and the posting rolls back — finance intents never commit for a failed posting.
- `RULE-PLAT-11`: only the `finance_adapter` DB role may change `finance_journal_intent.status`, and only along `RECORDED → ACKNOWLEDGED | REJECTED | SUPERSEDED`; `acknowledged_at` is set at most once; any other transition or column update is rejected by trigger (the app role keeps `SELECT, INSERT`).
- `RULE-PLAT-01`: every state-changing domain request emits exactly one `audit_event` in the same DB transaction as the change.
- `RULE-PLAT-02`: outbox is the **only** event publication mechanism; no direct publish from request handlers (§5.7).
- `RULE-PLAT-03`: event envelope always carries `tenant_id`, `correlation_id`, `causation_id`, `aggregate{type,id,version}`; payload carries ids, not PII.
- `RULE-PLAT-04`: idempotency replay must return the exact stored status/body; a replay never re-executes side effects.
- `RULE-PLAT-05`: `SYSTEM_TENANT_ID` rows are read-only for tenants; a tenant cannot be provisioned with the reserved id.
- `RULE-PLAT-06`: `api_key` secrets are stored only as Argon2id hashes; plaintext is returned once on creation.
- `RULE-PLAT-07`: approval decisions by a delegated actor record both the delegate and delegator in `approval_action`.
- `RULE-PLAT-08`: GAPLESS sequences allocate only at document post time (not draft creation); NON_GAPLESS may consume numbers on draft creation but never reassign them.
- `DM-PLAT-12` (Δ-MT): `user_identity` is global and auth-only (EXT): no tenant business table may reference it; it is not exposed through tenant routes; `app_user` is the only link and is tenant-scoped.
- `DM-PLAT-13` (Δ-MT): exactly one `app_user` per `(tenant_id, identity_id)`; tenant tokens are issued only for `membership_status=ACTIVE` on an ACTIVE tenant; suspension/revocation bumps `token_version` and revokes sessions; refresh requires an ACTIVE session bound to that tenant principal.
- `DM-PLAT-14` (Δ-MT): invitations are single-use, expiring, hashed, email-bound; role assignments are validated against the tenant role catalogue; only tenant admins (or platform admin for bootstrap) may invite/admin users; every membership, role, invitation and session change is audited.
- `INV-30` (Δ-MT): tenant/user isolation — for every API request and job, the active tenant equals the token/context tenant and every row read/written belongs to it; cross-tenant probes return 404; identity/session tables expose no tenant business data; platform-admin operations are audited.
- `RULE-PLAT-12`: the only source of the active tenant is the verified JWT `tid` claim (or the API-key's bound tenant); headers/query/body cannot override it; a token whose `tv` ≠ current `app_user.token_version` is rejected (`401 TOKEN_VERSION_STALE`).
- `RULE-PLAT-13`: refresh tokens are random opaque values stored only as hashes, rotated on every use; presenting a rotated/already-revoked refresh token revokes the session (replay detection) and emits `user.session.revoked`.
- `RULE-PLAT-14`: selection tokens are identity-scoped, single-use and ≤5-min; they grant no tenant business access and cannot be used as access tokens.
- `RULE-PLAT-15`: invitation tokens are single-use/email-bound/expiring and only resolve inside their own tenant; concurrent acceptance is serialised (exactly one membership/identity creation); invitation responses never echo tokens after creation.
- `RULE-PLAT-16`: `is_platform_admin` is a global identity attribute — no tenant role/scope may grant it; platform-admin endpoints require a global identity with the flag **and** `platform.tenant.manage`, and audit with `SYSTEM_TENANT_ID` as actor tenant.
- `RULE-PLAT-17`: identity tables are the PII erasure target; audit/ledger never contain email/password/display data (diffs redacted); `user_identity` is retained while any membership/audit obligation exists.
- `DM-RBAC-01` (Δ-RBAC): **deny-by-default route coverage** — every non-public route declares exactly one capability scope from `design/permissions.json`; unknown/duplicate/missing scopes fail CI; only the explicit public/self-service allowlists may omit a scope.
- `DM-RBAC-02` (Δ-RBAC): **grant safety** — tenant roles contain only assignable scopes; service-only (13) and platform-only (1) scopes never appear in tenant roles; system templates are non-editable (clone-only); SoD-conflicting pairs are rejected in one non-admin role; the last active tenant administrator cannot be locked out; every role/permission/assignment change is audited.
- `DM-RBAC-03` (Δ-RBAC): **effective permissions & separation of duties** — effective scopes/data scopes are resolved per request from role assignments and take effect immediately; every approval requires requester≠approver plus approval-scope authorization; posting revalidates its scope; changes emit audited events.
- `INV-31` (Δ-RBAC): **authorization completeness** — every tenant route is guarded by exactly one catalogued capability scope; scope and data-scope denials are correct; the role-template catalogue is coherent; SoD is enforced at assignment and approval time; platform-only/service-only scopes are unreachable from tenant roles.
- `RULE-RBAC-01`: privilege-escalation guard — an actor may grant/assign only roles whose scopes are a subset of the actor's own effective capability scopes unless the actor holds `platform.admin`; violation → `403 PRIVILEGE_ESCALATION`.
- `RULE-RBAC-02`: last-administrator lockout guard — a tenant must always retain ≥1 active membership holding the `admin` role; suspend/deactivate/role-removal that would leave zero active administrators → `409 LAST_TENANT_ADMIN`.
- `RULE-RBAC-03`: system templates (`is_template=true`, `is_editable=false`) cannot be edited or deleted — clone only (`409 TEMPLATE_IMMUTABLE`); the `admin` template is the only break-glass role and is exempt from SoD assignment checks but every change/use is audited.
- `RULE-RBAC-04`: `design/permissions.json` is the only catalogue authority — service-only and platform-only scopes are seeded for referential integrity but rejected by tenant role grants (`422 SCOPE_NOT_ASSIGNABLE`); the `platform.user.manage` alias is never seeded and maps to `platform.users.manage`; scope strings are frozen (additive only).
- `RULE-RBAC-05`: effective permissions are resolved from the DB on every request (role assignments ∪ API-key scopes + data scopes), so role/permission changes apply immediately; only membership suspension/revocation invalidates tokens (`token_version`, Δ-MT).
- `RULE-RBAC-06`: SoD `WARN` mode (tenant setting) downgrades only custom-role creation warnings — assignment-time conflicts and approval-time requester≠approver are always `HARD`.
- `DM-SSO-01` (Δ-SSO): `tenant_sso_connection` is tenant-scoped and RLS-protected; only tenant admins with `platform.sso.manage` (or platform admin) manage it; secrets are secret-store refs only; issuer/config changes are audited and re-tested before `ACTIVE`.
- `DM-SSO-02` (Δ-SSO): identity links are unique per `(tenant, connection, issuer, subject)` and per `(tenant, connection, identity)`; link/JIT only with verified email and allowed domain; no cross-tenant link reuse; link revocation blocks new logins and revokes sessions.
- `DM-SSO-03` (Δ-SSO): Dex authenticates, the platform authorizes: platform tokens are issued only after an ACTIVE membership; group→role mappings may grant only assignable tenant roles (never platform-only/service-only scopes) and cannot violate SoD; enforced-SSO tenants reject local-password logins.
- `INV-32` (Δ-SSO): **SSO/authn integrity** — every SSO login resolves to exactly one verified identity link and one active membership with no cross-tenant leakage; state/nonce/PKCE validated and single-use; group/role mapping bounded by RBAC; connection/link lifecycle is audited; Dex unavailability never silently downgrades to local auth.
- `RULE-SSO-01`: Dex is authentication only — Dex ID tokens/access tokens are never accepted as platform bearer tokens; the platform JWT/refresh/session model and Δ-MT/Δ-RBAC authorization are unchanged.
- `RULE-SSO-02`: authorization requests use single-use state + nonce + PKCE S256 with a 5-minute TTL; state is tenant/redirect-bound; callback replay is rejected (`400 SSO_STATE_INVALID`).
- `RULE-SSO-03`: ID tokens are validated strictly (issuer exact, audience = connection client_id, JWKS signature, exp/iat, nonce, `email_verified`); redirect URIs must match the configured allowlist; Dex/JWKS outages return `503 SSO_IDP_UNAVAILABLE` and never fall back to local login for members of an enforced-SSO tenant.
- `RULE-SSO-04`: JIT creates exactly one global identity + exactly one ACTIVE membership for that tenant + `default_role_ids` roles + link — never memberships in other tenants; JIT off → `403 JIT_PROVISIONING_DISABLED` with the invitation path.
- `RULE-SSO-05`: group→role mappings are bounded by `design/permissions.json` assignable roles, cannot grant platform-only/service-only scopes, cannot create an SoD pair, and are audited with role diffs; changes apply on the next login/session.
- `RULE-SSO-06`: secrets are write-only: responses/logs/audit never contain client secrets, SAML private keys or LDAP bind credentials (only `*_secret_ref` ids); secret rotation is audited.
- `RULE-SSO-07`: local password fallback is allowed only where the tenant has no ACTIVE enforced connection (or for audited platform-admin break-glass); enforced-SSO tenants reject password logins for their members.

State machines (per `DATA-MODEL.md` §19 + Δ-MT/Δ-RBAC addenda; FS-00 owns these twelve):

- `tenant`: `ACTIVE → SUSPENDED [platform-admin suspend; revokes all sessions]`, `SUSPENDED → ACTIVE [platform-admin reactivate]`, `ACTIVE/SUSPENDED → OFFBOARDING [offboard command, export produced]`, `OFFBOARDING → (terminal)`. Guard: no writes when not ACTIVE; login/refresh on non-ACTIVE tenant → `403 TENANT_SUSPENDED`.
- `user_identity` (global): `ACTIVE ↔ LOCKED [failed-login/lock policy, admin unlock]`; `ACTIVE/LOCKED → DISABLED [admin/erasure]`; DISABLED is terminal for login; erasure pseudonymises PII while retaining the id for audit/membership history.
- `app_user` membership: `INVITED → ACTIVE [invitation accepted]`; `ACTIVE ↔ SUSPENDED [tenant admin/platform admin; suspend revokes sessions + token_version++]`; `INVITED → (revoked invitation) / ACTIVE → (tenant offboarding retains row)`; no hard delete; exactly one row per `(tenant, identity)`.
- `tenant_invitation`: `PENDING → ACCEPTED [single-use accept]`; `PENDING → REVOKED [admin revoke]`; `PENDING → EXPIRED [expiry job/check]`; terminal states immutable; at most one PENDING per `(tenant,email)`.
- `user_session`: `ACTIVE → REVOKED [logout/admin revoke/replay/suspension/tenant suspend]`; `ACTIVE → EXPIRED [expires_at]`; terminal states immutable; session is bound to one `(tenant, app_user)` and one rotated refresh-token hash at a time.
- `role` (Δ-RBAC): `ACTIVE ↔ INACTIVE [custom role inactivate/reactivate; never hard-deleted]`; system templates are `ACTIVE` and immutable (no transitions except a new plan version); role permission/data-scope mappings are versioned by audit diff, not deleted.
- `user_role` assignment (Δ-RBAC): `SCHEDULED [effective_from > now] → ACTIVE [effective_from ≤ now < effective_to] → EXPIRED [effective_to ≤ now]`; union evaluated per request; ending an assignment sets `effective_to=now` (never hard delete); `admin` removal guarded by `RULE-RBAC-02`.
- `tenant_sso_connection` (Δ-SSO): `DRAFT → TESTING [test start] → ACTIVE [discovery/JWKS test passes]`; `TESTING/ACTIVE → ERROR [health/config failure]`; `ACTIVE → DISABLED [admin]`; `DISABLED → TESTING [re-enable/config change]`; delete only when no ACTIVE links (else DISABLED). Guard: only `platform.sso.manage`; issuer/config changes re-enter TESTING.
- `user_identity_link` (Δ-SSO): `ACTIVE → REVOKED [admin/link removal/connection disable]`; `REVOKED → ACTIVE [re-link explicit]`; never hard-deleted; revocation revokes sessions and blocks new SSO logins.
- `approval_request`: `PENDING → APPROVED [all steps approved]`; `PENDING → REJECTED [any step rejects]`; `PENDING → CANCELLED [document withdrawn / cancelled/superseded]`; terminal states immutable; a document with a terminal request can start a new request only when the prior one is CANCELLED (unique active-request constraint).
- `job_run`: `QUEUED → RUNNING → SUCCEEDED | FAILED`; `QUEUED/RUNNING → CANCELLED [admin]`; `FAILED → RUNNING [retry attempt++ while attempt ≤ max_attempts]`. Side effects: attempt/error/cursor updates, DLQ on terminal failure.
- `finance_journal_intent`: `RECORDED → ACKNOWLEDGED | REJECTED | SUPERSEDED` (finance adapter only, monotonic; `acknowledged_at` set once when applicable; no `ACKNOWLEDGED → REJECTED`). Rows are created only inside a posting transaction and are never deleted.
- Internal (non-document) state transitions: `idempotency_key IN_PROGRESS → COMPLETED`; `outbox_event unpublished → published` (published_at set once).

## 6. API surface

Base path `/api/v1` (see §14.3 C-02). JSON; UTC timestamps (`Z`); quantities/money as **decimal strings**
(`"12.500000000000"`); dates `YYYY-MM-DD`. Auth: `Authorization: Bearer <JWT>` or `X-API-Key`; every
admin endpoint requires its scope; `/internal/*` requires `platform.internal` and internal network
binding. Authentication for humans is the **Dex OIDC broker** (per-tenant connections) with **local password fallback**; the platform remains the only JWT/refresh token issuer (Dex tokens are never accepted as platform bearer tokens). Three auth classes: **public/rate-limited** (`/api/v1/auth/login`, `/auth/select-tenant`, `/auth/providers`, `/auth/sso/start|callback`,
`/api/v1/admin/invitations/{token}/accept`), **tenant-authenticated** (bearer JWT: active tenant is the
`tid` claim; every query RLS-scoped), and **platform-admin** (`/api/v1/platform/*`, global
`is_platform_admin` + `platform.tenant.manage`, audited with `SYSTEM_TENANT_ID`). Tokens: access JWT
claims `sub/uid/tid/tv/jti/iat/exp/scopes`; refresh token opaque/rotating; selection token identity-scoped
≤5 min. Errors use the problem+json envelope (`code`, `message`, `details[]`, `correlation_id`,
`trace_id`). All non-public endpoint rows declare exactly **one** capability scope from `design/permissions.json`; the only scopeless routes are the catalogue allowlists (public / self-service, labelled `none (public allowlist)` / `none (self-service allowlist)`). Cross-tenant ids return **404** (never 403 — no existence leak). Auth error codes:
`TOKEN_INVALID`, `TOKEN_EXPIRED`, `TOKEN_VERSION_STALE`, `SESSION_REVOKED`, `NO_ACTIVE_MEMBERSHIP`,
`TENANT_SELECTION_REQUIRED`, `MEMBERSHIP_INACTIVE`, `TENANT_SUSPENDED`, `FORBIDDEN_PLATFORM_ADMIN`,
`INVITATION_INVALID/EXPIRED/PENDING`, `MEMBERSHIP_EXISTS`; Δ-RBAC error codes: `FORBIDDEN_SCOPE`, `SCOPE_NOT_ASSIGNABLE`, `SOD_CONFLICT`, `LAST_TENANT_ADMIN`, `PRIVILEGE_ESCALATION`, `TEMPLATE_IMMUTABLE`, `ROLE_IN_USE`; Δ-SSO error codes: `SSO_PROVIDER_NOT_FOUND` (404), `SSO_DISABLED`/`SSO_ENFORCED_LOCAL_DENIED`/`SSO_EMAIL_DOMAIN_NOT_ALLOWED`/`JIT_PROVISIONING_DISABLED` (403), `SSO_STATE_INVALID` (400), `SSO_IDP_UNAVAILABLE` (503 + `Retry-After`), `IDENTITY_LINK_CONFLICT` (409), `SSO_GROUP_MAPPING_INVALID` (422), `CONNECTION_HAS_ACTIVE_LINKS` (409). Idempotency: `Idempotency-Key` **required** on
all POST creating/mutating resources or triggering jobs; replay-safe (invitation accept/login are
token-idempotent instead).

`evt.finance`, `evt.document`; Δ-MT identity/session/tenant events use `evt.platform`); `event_id` is the
stream message id; per-aggregate ordering by `aggregate_version` + relay order; at-least-once;
additive-only within a major event version. Δ-MT event payloads carry ids only (no email/password/
display PII, RULE-PLAT-03); `auth.login.failed`/identity-scoped rows use `SYSTEM_TENANT_ID` and are
consumed only by security monitoring/FS-15.

| Job | Schedule | Purpose | Idempotent? | Failure handling |
|---|---|---|---|---|
| `platform.outbox.relay` | continuous (worker `outbox` queue; 1–4 replicas) | Batch-publish unpublished outbox rows to Redis streams (`FOR UPDATE SKIP LOCKED`) | yes (per event id; `published_at` set once) | backoff retry, `attempts++`; poison after 10 attempts → `evt.dlq` + alert; relay restarts safe |

Job definitions for domain sets are seeded by the owning set's migration (§4 migration note). Retries:
`max_attempts` per definition, exponential backoff with jitter, stuck-run watchdog marks RUNNING >
`timeout_seconds*2` as FAILED (attempt++). All jobs are per-tenant scoped; `singleton=true` uses
`pg_advisory_lock(hashtext('job:<name>:'||tenant_id))`.

## 12. Rollback

- Flip `platform.core.enabled` off: all domain write paths return `409 DOMAIN_DISABLED`; reads remain.
  Platform admin reads (`/api/v1/admin/*`, audit, reference, journal intents) remain available for diagnosis.
- Redeploy the prior image; migrations are additive + N-1 compatible (no prod down-migration).
- Forward-fix only for data: append-only tables are never updated/deleted; corrections are new
  audit/approval/document-link rows. `idempotency_key`/`job_run` purges are retention-governed.
- Snapshot restore only if the outbox/audit integrity gate fails (`FEATURE-SETS.md` §7.1 rollback);
  restore is a full-environment action coordinated with the Lead, never a per-tenant edit.
- Dependants are automatically blocked by `check-env` while status ≠ verified.

### 14.2 Assumptions recorded

- `SYSTEM_TENANT_ID = 00000000-0000-0000-0000-000000000000` reserved; never provisionable.
- JWT access tokens (Δ-MT): short-lived 15 min, claims `sub`=identity_id, `uid`=app_user_id,
  `tid`=tenant_id, `tv`=token_version, `jti`, `scopes`; access tokens are **stateless** (no Redis
  revocation list) and are revalidated against `token_version` + membership/tenant status on every write
  and refresh. Refresh tokens: 30-day, opaque, hashed at rest, rotated on use; presenting a rotated token
  revokes the session (replay detection). Selection tokens: 5 min, identity-scoped, single-use.
- **Δ-MT identity assumptions (EXT):** one global identity per real email; local `PASSWORD` mode uses
  Argon2id; `SSO` mode stores `sso_subject` and leaves `password_hash NULL` (SSO/OIDC/SCIM integration is
  Phase 2); invitations are the only onboarding path (no self-service signup); bootstrap admin invitation
  token is delivered out-of-band and expires in 7 days; service accounts are tenant memberships with
  `is_service_account=true` and cannot log in interactively.
- **Δ-MT isolation assumption:** `user_identity` has no `tenant_id`/RLS tenant policy and is auth-role-only;
  tenant business tables never FK to it except `app_user.identity_id` (documented cross-scope exception,
  DM-PLAT-12); tenant admins may read identity display fields through membership APIs only.
- Internal module calls use in-process contracts, not HTTP; `/internal/*` is network-restricted and
  requires a service principal token.
- Audit events are written in the same transaction as the change (fail-closed for business writes).
- `NullFinanceAdapter` persists intents synchronously in the caller transaction (durability over
  "never fails posting"): a DB write error aborts the posting, because silently losing an intent would
  break D2 evidence. External adapters (Phase 2) may buffer, but must be durable.
- Event payloads carry ids, not names/PII (`ARCHITECTURE.md` §5.7).
- Custom field `entity_type` allowlist in Phase 1: `ITEM`, `LOT`, `SERIAL`, `WORK_ORDER`, `VENDOR`,
  `PURCHASE_ORDER`, `ITEM_RECEIPT`, `VENDOR_BILL`, `CUSTOMER_PART`, `UPC`; other values rejected `422`.
- Outbox/audit `SYSTEM_TENANT_ID` rows: only platform-generated events (e.g. finance sync) may use the
  system tenant; read visibility for tenants is blocked by RLS.
- **Δ-SSO assumptions (EXT/ASSUMPTION):** Dex (`2.4.x` pinned) is the human-authentication broker and the
  platform stays the only authorization/token issuer (Dex tokens never accepted as platform bearer tokens);
  reference deployment = one isolated Dex issuer + storage per ACTIVE `tenant_sso_connection` (shared Dex
  allowed dev/test); secrets live only in the secret manager (`*_secret_ref` pointers in DB);
  local-password fallback retained for non-SSO/break-glass; SCIM/IdP-initiated SAML/single-logout/
  multiple-IdPs-per-login are deferred; per-company SSO is per-tenant (never cross-tenant).
- **Δ-RBAC/Δ-SSO assumptions:** `design/permissions.json` (plan version 1.3.0) is the **only** catalogue
  authority — FS-00 seeds 255 scopes (241 assignable + 13 service-only + 1 platform-only), 7 templates,
  14 SoD pairs, allowlists; the `platform.user.manage` alias lives only in the JSON `aliases` map (not
  seeded); capability scopes are frozen strings (additive only); effective permissions resolve from the
  DB per request (no long TTL cache); role templates are non-editable/clone-only; the `admin` template is
  break-glass and SoD-exempt but audited; `platform.tenant.manage` is reachable only by global platform
  admins and 13 service-only scopes only by internal jobs/service principals.
